## 1. CPU 속도: 미스터 드릴러 2 / G에는 하프 레이트 데이터 캐시로 부족함

### 증상

미스터 드릴러 2 및 미스터 드릴러 G의 넓은(13열) 플레이필드가 나오는 후반 스테이지에서 플레이 중 짧고 미세한 스터터링(끊김)이 발생합니다. 저희 역시 초기 빌드에서 동일한 터보 설정(Turbo High + 하프 레이트 캐시)을 사용했을 때 정확히 같은 증상을 겪었으나, 풀 레이트 캐시로 변경한 후 해결되었습니다.

### 실제 클럭 스펙

* System 10 CPU (CXD8606)는 101.4912 MHz / 2 = **50.7456 MHz**로 동작하며, 이는 플레이스테이션의 1.5배 속도입니다 (MAME `namcos10.cpp` 기준). System 12 (CXD8661R, 텐코모리 슈팅 코어)는 **50 MHz**로 동작하므로 System 10이 약 0.75 MHz (1.5%) 더 빠릅니다.
* 저희 코어와 귀하의 코어 모두 CPU 클럭으로 **33.8688 MHz** (`clk_1x`)를 사용합니다. 귀하의 README에도 이 내용이 올바르게 명시되어 있습니다. 터보 플래그 (`TURBO_MEM`, `TURBO_COMP`, `TURBO_CACHE`, `TURBO_CACHE50`)는 클럭 자체를 바꾸는 것이 아니라 메모리 대기 상태 및 연산 스톨을 제거하고 데이터 캐시를 추가하는 방식입니다. 이를 통한 성능 향상 폭은 실행되는 코드(캐시 히트율, 메모리 접근, GTE 사용 여부 등)에 따라 달라집니다.
* 따라서 "System 12 터보/캐시 프로필"이 "50 MHz"와 동일한 것은 아닙니다. `Namco_S10.sv:930-934` 주석 및 커밋 메세지 742fa82 ("CPU turbo for 50 MHz")에서는 이를 실기 보드 속도와 동일하다고 보고 있으나, 이는 System 10 게임들에 맞추어 보정된 값이 아닙니다. 텐코모리 코어가 하프 레이트 캐시를 채택한 이유는 하프 레이트가 50 MHz와 같아서가 아니라 아래에서 설명할 `VSync()` 타임아웃 문제 때문이었습니다.

### 풀 레이트 캐시를 단순히 켜기만 하면 안 되는 이유

`TURBO_CACHE50 <= 1'b0`으로 설정하면 스터터링은 사라지지만, 또 다른 버그가 발생합니다. 장면이 전환되는 일부 구간(미스터 드릴러 G 어트랙트 모드, BIOS 화면 진입 후 약 45~47초 및 1분 06초 시점, 480i)에서 1프레임 동안 화면 깜빡임/글리치가 관찰됩니다. 원인은 다음과 같습니다:

* 게임들은 PSY-Q libetc의 `VSync()` 함수를 사용합니다. 이 함수의 내부 대기 루프인 `v_wait`에는 반복 타임아웃 명령어가 포함되어 있습니다: `sll a1,a1,15` (32,768회 루프, 명령어 워드 **0x00052BC0**, mrdrilrg 기준 0x8027CD70 위치).
* MAME 환경에서 이 루프는 필드당 32,768회 중 약 28,800~29,500회의 루프를 소비합니다. 마진이 약 10%에 불과합니다.
* Turbo High 및 풀 레이트 캐시 상태에서는 루프가 MAME보다 약 13% 더 빠르게 실행됩니다. 32,768회 루프가 16.65ms 내에 끝나버리므로 1필드 채 되지 않는 시간에 완료됩니다. 결과적으로 거의 매 필드의 VBlank 바로 직전에 타임아웃이 발생하며(이는 무해함), 로딩 프레임 직후에는 필드 중간에 타임아웃이 터지게 됩니다. 이로 인해 게임이 필드 중간에 디스플레이를 플립하고 드로우 리스트를 시작하여 인터레이스 필드가 꼬이게 됩니다 (글리치 발생).
* 하프 레이트 캐시 환경에서는 루프가 더 천천히 돌기 때문에 타임아웃이 거의 발생하지 않습니다. 즉, 하프 레이트 설정은 스터터링을 대가로 이 글리치를 숨기고 있었던 것입니다.

저희는 실기 GPU 명령어 트레이스 및 MAME 디버거를 통해 이 원인을 규명했습니다. 자세한 내용은 저희 코어의 `docs/fixes-2026-10-19.md`를 참고하시기 바랍니다.

### 해결책 (저희 코어 `rtl/cpu.vhd:654-661` 참고)

풀 레이트 캐시를 유지하면서 `VSync()` 타임아웃을 2배로 늘립니다. 캐시 터보가 켜져 있는 동안 CPU가 i-cache 패치 및 언캐시드 페치 경로 양쪽 모두에서 `sll a1,a1,15` (0x00052BC0) 명령어를 `sll a1,a1,16` (0x00052C00)으로 대체하도록 합니다:

```vhdl
   -- NS10: PSY-Q VSync waits for the next vblank with an iteration timeout (v_wait, "sll a1,a1,15" =
   -- 32768 loops). With the cache turbo the loop runs faster than on the real CPU and the timeout
   -- expires before vblank (frame flip mid-field, mrdrilrg scene cut glitch). Double it while the
   -- cache turbo is on; the word only occurs in v_wait in the NS10 games checked (MAME RAM dumps).
   fetch_dataRead     <= x"00052C00" when (TURBO_CACHE = '1' and mem_dataRead = x"00052BC0") else mem_dataRead;
   cache_data_patched <= x"00052C00" when (TURBO_CACHE = '1' and cache_data   = x"00052BC0") else cache_data;
```

* `cache_data_patched`는 i-cache RAM의 `data_a` (SDRAM으로부터의 인필, `clock_a => clk3x`)로 `cache_data`를 대체합니다.
* `fetch_dataRead`는 페치 프로세스(민감도 리스트 및 `opcodeNext <= unsigned(fetch_dataRead);`)에서 `mem_dataRead`를 대체합니다.
* 이후 `Namco_S10.sv`에서 `TURBO_CACHE50 <= 1'b0`으로 설정합니다.

실제 하드웨어 적용 결과 (저희 코어 커밋 21a5eea): 미스터 드릴러 G 68초 트레이스 측정 시 VBlank 이전 타임아웃 발생 횟수가 160회에서 0회로 감소, 필드 중간 플립 1회에서 0회로 감소, 스테이지 13 스터터링 해소, 어트랙트 모드의 화면 글리치 현상이 완전히 사라졌습니다.

### 22개 게임 적용 시 주의사항

저희가 지원하는 게임들(미스터 드릴러 2 전체 세트, 미스터 드릴러 G, 감샤라, 스타 트라이곤 MAME RAM 덤프)을 확인한 결과, 0x00052BC0 워드가 `v_wait`에만 존재하는 것을 확인했습니다. 귀하의 코어는 더 많은 게임을 지원하므로, 이 패치를 적용하기 전 MAME 실행 중 각 게임의 메인 RAM을 덤프하여 0x00052BC0 워드가 다른 곳에 쓰이지 않는지 검색해 보시길 권장합니다. 만약 `v_wait` 외의 다른 곳에서도 쓰인다면 패치가 해당 코드까지 변경할 수 있으므로 주소 체크 조건(예: 다음 워드가 `v_wait` 루프 바디일 때만 작동하도록)을 추가해야 합니다.

디버그 OSD에 캐시 전환 스위치(Full / Half)를 만들어두면 하드웨어 A/B 테스트에 매우 유용합니다. 저희는 디버그 빌드 전용으로 `O[83] Turbo Cache (High)` 항목을 배치해 두었습니다.

## 2. HDMI: 480i 화면의 수직 해상도가 절반으로 저하됨

### 증상

HDMI 평판 디스플레이 연결 시 480i 화면(스타 트라이곤 타이틀, 미스터 드릴러 G, 감샤라, 코노에타코 등)이 저해상도로 거칠게 보이고 화면이 약 반 픽셀 정도 어긋난 듯한 느낌을 줍니다. 동일한 화면이 15kHz CRT에서는 정상적으로 출력되며, 240p 화면은 양쪽 디스플레이 모두에서 이상이 없습니다.

동일한 HDMI 모니터에서 촬영한 스타 트라이곤 타이틀 화면 비교 (저희 코어 vs Namco_S10):

사진: `user_image/hdmi_bug.png` (빨간 표시는 비교할 부분)

* 윗줄과 오른쪽 위 확대: 저희 코어 - 세밀한 픽셀 표현, 선명한 외곽선
* 아랫줄과 오른쪽 아래 확대: Namco_S10 - 큼직하고 뭉개진 픽셀, 계단 현상이 심한 대각선

![HDMI 480i 비교](../user_image/hdmi_bug.png)

### 원인

`Namco_S10.sv:2327` 코드:

```verilog
assign VGA_F1 = 1'b0;
```

MiSTer 스케일러(`sys/ascal.vhd`, `VGA_F1`으로부터 전달받는 입력 `i_fl`)는 인터레이스 신호를 인식하고 두 개의 240라인 필드를 하나의 480라인 프레임으로 엮어주기(weave) 위해 인터레이스 필드 비트를 필요로 합니다. 그러나 `VGA_F1`이 로우(0)로 고정되어 있기 때문에:

* 각 240라인 필드가 하나의 완전한 프로그레시브 프레임으로 처리되어 수직 해상도가 절반으로 깎입니다.
* 홀수 필드와 짝수 필드가 동일한 라인 위치에 겹쳐서 쓰여 필드마다 화면이 반 라인씩 움직이게 됩니다 (이로 인해 "반 픽셀 밀림" 현상이 느껴짐).
* 240라인을 정수가 아닌 배율(1080p 기준 4.5배)로 출력 높이에 맞추어 스케일링하므로 라인 높이가 불균일해지고 픽셀 도트가 거칠어집니다.

필드 비트 신호 자체는 이미 존재합니다: `video_aspect.interlace` 신호가 `Namco_S10.sv:2214`에서 `psx_interlace`로부터 레지스터링되고 있습니다 (`videoout_out.interlace = GPUSTAT_VerRes and GPUSTAT_InterlaceField`로, 480i에서는 매 필드마다 토글되고 240p에서는 0이 됨). 다만 이 신호가 스케일러로 전달되지 않고 있을 뿐입니다.

아날로그 출력의 경우 CRT 자체가 자체적으로 인터레이스를 처리하는 15kHz 네이티브 신호이므로 이 문제의 영향을 받지 않습니다.

`MISTER_SMALL_VBUF`가 원인은 아닙니다. 스케일러 버퍼당 2MB의 용량은 픽셀당 4바이트(1.2MB) 설정에서도 640x480을 충분히 처리합니다.

### 해결책

저희 코어(`NAMCOS10.sv:1137`)에서는 다음과 같이 처리했습니다:

```verilog
assign VGA_F1 = video_aspect.interlace;
```

귀하의 코어는 영상을 `video_mixer` (Scandoubler Fx)를 거쳐 보냅니다. 스캔다블링된 신호는 프로그레시브 신호이므로, 스캔다블러가 꺼져 있을 때만 필드 비트를 전달해야 합니다:

```verilog
assign VGA_F1 = sd_enable ? 1'b0 : video_aspect.interlace;
```

`HDMI_BOB_DEINT = status[41]` 신호는 이미 연결되어 있습니다 (`Namco_S10.sv:181`). 필드 비트가 제대로 전달되면 스케일러는 기본적으로 Weave 방식으로 동작하며, 해당 설정이 켜지면 Bob 방식을 사용하게 됩니다. 원하신다면 OSD 항목 `O[41],Deinterlacing,Weave,Bob;`을 추가하여 노출할 수 있습니다 (저희 코어에서는 Video & Audio 메뉴에 위치함).

### 부작용: `vsync_adjust=2` 사용 시 HDMI 블랙아웃 현상

`vsync_adjust=2` 옵션 사용 시 HDMI 출력은 코어의 비디오 타이밍을 그대로 따르므로 입력 모드가 변경될 때마다 모니터가 다시 동기화를 잡습니다 (블랙 스크린 발생). 하드웨어 상에서 귀하 코어의 해상도 변경 시 블랙아웃 시간이 저희 코어보다 짧습니다.
아직 정확히 측정해보지는 않았으나, 원인은 `VGA_F1`이 로우로 고정되어 있어 스케일러가 480i와 240p를 동일한 ~240라인 프로그레시브 입력으로 간주하여 240p <-> 480i 전환을 모드 변경으로 인식하지 않았기 때문으로 추정됩니다. `VGA_F1`이 정상 전달되면 이 전환들이 실제 모드 변경(인터레이스 On/Off, 240 <-> 480 라인)으로 인식되어 블랙아웃 시간이 다소 길어질 수 있습니다. 저희 측에서도 이 부분을 살펴보고 있습니다 (섹션 4.3 참조). 그러나 화질 개선을 위해서는 이 수정 작업을 기본으로 적용하는 것이 맞습니다.

### 검증 방법

* HDMI 연결, Scandoubler Fx = None 설정 후 스타 트라이곤 타이틀 화면이나 미스터 드릴러 G 게임플레이 진입: 화면이 위 첨부 사진 중 첫 두 장처럼 선명하게 나와야 합니다.
* MiSTer OSD 정보 (또는 `vsync_adjust` 로그) 상에서 240p가 아닌 480i 입력으로 표시되어야 합니다.
* 240p 게임들: 변동 사항 없음.

## 3. 미스터 드릴러 2 / G 입력 레이트: IRQ10을 VBlank의 2배속으로 설정

### 배경

실기 아케이드 기통에서는 미스터 드릴러 실행 시 "동기화된" 연사(2프레임당 1회 입력, 초당 30회)를 사용하면 블록을 깔끔하게 팝니다. 그러나 MAME 방식의 100Hz IRQ10 환경에서는 동기화가 깨지는 현상이 발생합니다. 이를 추적해 보았습니다.

* 드릴러 게임들은 IRQ10 핸들러 내에서 IN1 (0x1FBA0004)을 읽어오지만, 입력 라이브러리는 매 2번째 호출마다만 이 값을 저장합니다 (MAME나 코어 문제가 아닌 게임 ROM 자체 코드: mrdrilr2j 0x8016CEB4, mrdrilrg 0x80296C08). 그리고 게임은 VBlank 직후 프레임당 단 한 번, 가장 최근에 저장된 값을 복사해 옵니다.
* 100Hz IRQ10 환경에서는 초당 60프레임 대비 초당 50회의 입력 샘플만 게임에 전달됩니다. 이로 인해 일부 프레임에서 동일한 샘플이 중복 처리되면서 연사가 프레임 레이트와 엇박자를 일으킵니다 (MAME 측정 결과: 매 2번째 IN1 읽기마다 토글 = 초당 25.01회, 테스트당 약 160프레임 중복 발생).
* MAME의 100Hz 설정은 임시(placeholder) 값입니다. 이는 2023년 드라이버 리팩토링 커밋(MAME commit ec6b3d2b5542, "TODO: Trace main PCB to see where JAMMA I/O goes and/or how int10 can be triggered" 주석 참고) 당시에 들어간 것으로 실기 하드웨어 근거가 없습니다.
* 라이브러리 구조상 120Hz가 가장 적합합니다. "매 2번째 호출" 페이즈는 PSX libpad의 프레임별 VBlank 에뮬레이션 부분이며, 그 외 IRQ10의 유일한 쓰임새는 120틱(120Hz 기준 1초) 타임아웃 통신 기능뿐입니다. 게임이 시간 측정 용도로 IRQ10을 사용하지 않으므로 이 비율을 바꿔도 게임 실행 속도에는 영향을 주지 않습니다.

### 저희 코어의 적용 방식 (`rtl/ns10/ns10_io.sv`)

IRQ10이 매 GPU VBlank 발생 후, 직전에 측정된 프레임 길이를 기준으로 1/4 시점과 3/4 시점(게임이 VBlank 직후 입력을 복사하는 시점을 피함)에 프레임당 총 2번 발생하도록 설정했습니다. 이렇게 하면 게임은 프레임당 정확히 1개의 샘플을 저장하게 됩니다.

```verilog
// 2x VBlank: IRQ10 at 1/4 and 3/4 of the last frame length after each VBlank
localparam integer FRAME_NOM = 565050;               // 33868800 / 59.94
reg        vbl_1;
reg [19:0] fcnt, fper;
wire       vbl_rise = vblank & ~vbl_1;
wire       vbl_tick = (fcnt == {2'b00, fper[19:2]}) || (fcnt == {2 me2'b00, fper[19:2]} + {1'b0, fper[19:1]});
...
		vbl_1 <= vblank;
		if (vbl_rise) begin
			fcnt <= 0;
			fper <= fcnt;
		end else if (~&fcnt)
			fcnt <= fcnt + 1'd1;

		if (irq10_vbl ? (vbl_tick && !vbl_rise) : (tcnt == TIMER_PERIOD - 1)) begin
			intr[3]  <= 1;
			irq10    <= 1;
		end
```

`vblank`는 `psx_top`으로부터 익스포트된 PSX `irq_VBLANK` 라인입니다 (`vblank_irq <= irq_VBLANK;`). `fper`는 `FRAME_NOM`으로 초기화됩니다. 100Hz 타이머는 디버그 옵션(`O[87] IRQ10 (Input),2xVBlank,100Hz`)으로 남겨두고 정식 릴리즈 빌드에서는 2x VBlank를 사용하도록 했습니다.

결과:

* 시뮬레이션: 입력 읽기에 동기화된 연사 기능 동작 시, 프레임 씹힘/중복 0회로 초당 29.97회 기록. 40회의 짧은(17ms) 입력 탭 테스트 중 입력 분실 0회 (100Hz 기준에서는 40회 중 7회 분실 발생).
* 동일하게 2x VBlank IRQ10을 패치한 MAME 환경: 드릴러 2 및 G에서 중복 1회에 초당 29.91회 기록 (100Hz에서는 중복 ~160회, 초당 25회 기록). 메뉴, 인게임, 테스트 모드 작동 방식 모두 양쪽 모드에서 동일하며, 감샤라 및 스타 트라이곤 역시 동일하게 잘 작동함.
* 실기 하드웨어: 눈에 띄게 부드러워졌으며 실제 아케이드 캐비닛 작동 영상과 일치함.

자세한 분석 내용은 저희 코어의 `docs/rapid-fire-irq-eng.md` 문서에 기술되어 있습니다.

### 귀하의 코어 적용 가이드

* `rtl/s10_io.sv` 파일 내부에서 CD-ROM 인터럽트 발생 시에도 IRQ10을 올리는 로직이 있습니다 (태고의 달인, 150번 줄). 이 경로는 그대로 유지하고 타이머 소스(status bit 3) 부분만 변경해 주시면 됩니다.
* 입력을 위해 IRQ10을 사용하는 다른 게임들도 각 모드별로 최소 한 번씩 작동 확인을 거치시길 권장합니다. 저희는 4개 게임에 대해서만 검증을 마친 상태입니다.

## 4. 귀하 코어의 우수한 점

### 4.1 더 빠른 부팅 속도 (컬러 바 화면)

실체 하드웨어 테스트 시, 귀하의 코어가 저희 코어보다 컬러 바가 출력되는 부팅 화면을 수 초 더 빠르게 통과합니다.

소스 코드 분석 결과 원인: System 10 BIOS 모듈은 캐시가 가능한 kseg0 (0x9FC2xxxx) 영역에서 실행됩니다. 귀하의 `rtl/memorymux.vhd:768-795` 코드는 부트 프로그램 영역에서 캐시 가능한 페치가 일어날 때 i-cache 라인 필드(`ram_cache <= '1'`, 버스트, 태그 유효)를 수행합니다. 반면 저희 코어는 해당 주소 영역의 이전 i-cache 버그를 수정하는 과정에서 태그를 유효로 마킹하지 않도록 처리해버려 모든 BIOS 명령어가 25~26 사이클짜리 언캐시드 리드로 동작하고 있었습니다. 귀하의 방식이 올바른 구조입니다. 저희도 kseg0 BIOS 페치 시 버스트 라인 필드를 수행하도록 수정할 예정입니다.

### 4.2 로딩 화면 표시 방식

귀하의 MRA는 `address=` DDR3 파트 이전에 BIOS 파트를 ioctl index 0으로 스트리밍합니다. 이로 인해 MiSTer 메뉴 상에서 일반 ROM 로딩 바가 먼저 나타난 후 어셈블리 바가 이어서 진행됩니다. 저희는 하나로 합쳐진 `address=` ROM을 통해 전부 로드하므로 어셈블리 바만 움직입니다. 이는 단순한 시각적 차이일 뿐이므로 별도로 수정하지 않을 예정입니다.

### 4.3 `vsync_adjust=2` 설정에서의 더 짧은 HDMI 블랙아웃 시간

게임 해상도가 변경될 때 귀하 코어의 HDMI 화면 복구 속도가 저희보다 빠릅니다. 섹션 2에서 설명했듯 원인의 일부는 `VGA_F1` 고정 코드 때문일 가능성이 큽니다. 귀하 코어의 스케일러 입력은 인터레이스 및 프로그레시브 간 전환이 일어나지 않기 때문입니다. 확정을 내리기 전에 양쪽 코어의 모드 전환 횟수와 시간을 직접 측정해 볼 예정입니다. 다만 인터레이스 플래그를 제거하는 것은 480i 해상도가 반토막 나버리기 때문에 저희 쪽에서 채택할 수는 없는 옵션입니다.

## 5. 기타 노트

* **ascal 타이밍 매크로.** 귀하의 qsf 설정에는 `MISTER_SMALL_VBUF`, `MISTER_DISABLE_ADAPTIVE`, `MISTER_DISABLE_YC`가 지정되어 있습니다. 이들은 스케일러 로직을 줄여 HDMI 클럭 타이밍 클로저를 돕는 역할을 하며, 480i 문제를 일으키는 원인은 아닙니다.
* **`rtl/cpu.vhd`** 내부에는 여전히 많은 System 11 초기 진단용 코드(첫 번째 파울트 라치, 64-엔트리 트레이스 링, 256-엔트리 MAME 테이블, 2개의 추가 MLAB 레지스터 파일, 그리고 현재 `value1` / `value2`에 데이터를 공급하는 32x32 플립플롭 섀도 레지스터 파일)가 남아있습니다. 이 플립플롭 레지스터 파일은 `clk_1x` 대역의 ALU 앞단에 거대한 리드 멀티플렉서를 추가하게 됩니다. System 10에서 이것이 필요 없다면 (원래 문제는 System 11 디콤프레서 문제였음) 이를 제거하여 로직 자원을 확보하고 타이밍 마진을 늘릴 수 있습니다.
* 귀하 `cpu.vhd` 파일의 **`dcache_write_clear`**는 RAM 주소 영역(`< 0x800000`)에 대해서만 동작하도록 되어 있습니다. 매우 좋은 수정 사항입니다. 저희 코어는 I/O 쓰기 시에도 클리어를 수행하고 있습니다 (무해하지만 약간 더 느림).
* **GP1(01) 홀드 (`memorymux`의 `gp1_hold`) 및 필드 락.** 감샤라 / 스타 트라이곤의 480i 문제 해결을 위해 귀하의 코어는 GPU가 아이들 상태가 될 때까지 CPU를 GP1(01)에 홀드시킵니다. 반면 저희는 GPU가 아이들 상태가 될 때까지 현재 필드를 유지하고(`gpu.vhd`의 `fieldLock`), 텍스처 로우를 버스트로 가져옵니다. 두 방식 모두 정상 작동합니다. 참고로 GP1(01) 홀드는 CPU를 최대 약 15ms 동안 스톨시키므로, 1.5배 느린 GPU 상에서 프레임 지연이 발생할 가능성이 있습니다.
* **세이브 스테이트.** 저희는 지원하는 4개 게임에 대해 정상 작동하는 세이브 스테이트를 구현해 두었습니다 (4개 슬롯, DDR3 0x3C000000 영역의 8MB 용량: RAM 4MB, VRAM 2MB, 보드 스테이트 및 NVRAM). 세이브 기능을 복구하고자 하실 때 저희의 보드 스테이트 코드가 좋은 참고 자료가 될 수 있습니다.
