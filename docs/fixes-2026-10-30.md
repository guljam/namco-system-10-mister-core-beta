# 2026-10-30 작업 기록: Mr. Driller G AI 봇 - 빔 탐색 플래너

코어(FPGA) 코드는 바꾸지 않았다. GroovyMAME(원본 mrdrilrg)에서 Lua 봇 + C 플래너로 작업했다. 이전 기록은 docs/fixes-2026-10-29.md, 계획은 docs/drillerg-ai-plan.md.

## 목표
규칙 봇(클리어 5/12) 대신 RAM을 읽어 미래를 시뮬레이션하는 플래너로 바꾼다. 평가는 타이조, India, 확정 지연(OB_CDELAY, 테스트 데이터 전용) 12개 맵으로 한다.

## 구조 (해결/결과물)
- tools/drgai/planner/blocksim.c/h: 블록 시뮬. 전날 검증한 모델(India 비교 셀 1.7M 중 불일치 33, America 0)을 그대로 쓴다.
- psim.c/h: 플레이어 시뮬(입력 지연 3, 걷기 728/프레임, 낙하, 파기, X블록 5회, 산소). pvalidate.c로 실제 기록과 비교한다.
- plan.c: 빔 탐색. 매크로 7개(대기, 아래/왼쪽/오른쪽/위 파기, 왼쪽/오른쪽 이동) x 8프레임, 깊이 10(80프레임), 폭 48. 마지막에 90프레임 대기 시뮬로 안전 검사. 출력 "PLAN m 8개 입력 점수". 약 0.25~0.35초/호출.
- tools/drgai/drgbot.lua OB_PLAY=plan: 8프레임마다 RAM 상태를 <OB_OUT>_state.txt로 쓰고 plan.exe 실행(OB_PLANEXE), 받은 입력을 누름. 상태 4(밀려남)에서도 계획. OB_REC=<파일>이면 매 프레임 기록, OB_ST4MASK는 상태 4 입력 시험용.
- scripts/: conv.py(기록 -> frames 텍스트), frlib.py / plib.py(읽기), evalplan.sh(12맵 병렬 평가, DRG_WORK 작업 폴더에 plan.exe).
- 디버그 환경변수: PLAN_FORCE(매크로 재생), PLAN_INPUTS(원시 입력 재생), PLAN_DEBUG, PLAN_TRACE, PLAN_DEPTH/BEAM, 점수 조정 PLAN_DIJ/RCW/XW/DROWS/CAPT/AIRMODE/MINAIR/QKEY/GOAL.
- 빌드: gcc -O2 -std=c99 -Wall -o plan.exe plan.c psim.c blocksim.c

## 가설과 확인 결과
1. 플래너가 계속 대기만 함(미루기).
   - 증상: 매크로가 계획을 내도 매번 "대기"를 골라 내려가지 않는다.
   - 원인: 끝 깊이만 보면 지금 파나 나중에 파나 점수가 같고, 동점이면 대기가 선택됐다.
   - 해결: 깊이 증가를 매 단계 누적한다(빨리 내려갈수록 점수). 첫 매크로별 상위 4개를 빔에 보존한다.

2. X블록 위에서 영원히 대기.
   - 증상: X블록에 막히면 그 위에서 계속 대기한다.
   - 원인: X 비용(공기 20%)은 바로 빠지는데 이득은 80프레임 너머에 있다.
   - 해결: 1번과 같은 누적 깊이 + 진행 중 낙하/파인 칸 점수를 넣어 미루기를 없앴다.

3. 실제 게임 사실(MAME 측정).
   - 확인: 캡슐 = 23프레임 동안 프레임당 +1000(최대 152000).
   - 확인: X블록 = 20프레임 동안 프레임당 -1000(즉시 아님).
   - 확인: 산소 50000에서 사망.

4. 밀려남 상태 4(새로 발견).
   - 확인: 블록이 플레이어 칸에 떨어질 때 플레이어가 중심에서 |x| >= 2912 벗어나 있으면 깔리지 않고 그쪽 옆 칸으로 밀려난다(x=0).
   - 확인: P+0x10C가 60에서 프레임당 1씩 줄고, 좌/우 입력 중에는 2씩 줄어 0이면 상태 1. 그동안 다시 깔릴 수 있다. |x| 1504에서는 깔린다.
   - 해결: drgbot.lua가 상태 4에서도 계획하도록 했다.

5. 파는 중인 칸(상태 8/9/10)으로는 걸어 들어갈 수 없다.
   - 확인: 빈 칸이 된 프레임부터 걷는다. 플레이어 시뮬에 반영했다.

6. 늦은 파기(사용자 지적).
   - 증상: 착지 후 파기까지 230줄 중 116줄이 3~4프레임 늦다.
   - 원인: 공중 입력을 무시하는 중복 제거에서 B 예약이 버려졌다.
   - 해결: 착지 동기 파기(사용자 규칙: 착지 1프레임 후가 이상적, Drill(Auto)와 같은 원리). 매크로 안에서 B는 새 엣지일 때만, 3프레임 앞을 시뮬해 서 있고 쿨다운이 끝났을 때만 누른다. X블록은 1프레임 on/off로 2프레임마다 1회.

7. 다익스트라 휴리스틱(사용자 제안): 정지한 격자에서 최소 비용(프레임). 낙하 10240/속도, 걷기 14, 색블록 6, X블록 12 + 공기 비용. 결과는 "목표 깊이까지 비용", "가장 가까운 캡슐까지 비용".
   - 원인(버그 2개): 목표 줄이 500m X 바닥 아래였고(목표는 골 깊이에서 멈춤), 목표가 플레이어와 함께 내려가 내려갈수록 비용이 늘었다.
   - 해결: 목표 = 탐색 시작 깊이 + 12로 고정.
   - 효과: 412m X 함정 사망과 제자리 대기가 사라졌다.

8. 산소 가치.
   - 원인: 깊은 곳(300m 이후)은 1m당 약 12프레임 x 소모 37~40 = 약 480 공기, 남은 200m에 96000 필요 > 가진 양. 캡슐이 필수다. 이전 식(a*부족분)은 공기가 늘면 점수가 줄어드는 버그였다.
   - 해결: 남은 구간에 필요한 양까지는 공기 1단위 = 1000/(12*소모) 점(시간 가치), 넘치는 양은 0.1점. 캡슐 잠재력 = 그 캡슐 공기의 가치를 거리(프레임)에 따라 200프레임까지 줄여 더한다.
   - 효과: 산소 사망 13~17 -> 3~4.

9. 반복되던 38m 깔림.
   - 원인: 시뮬에서 옆 칸을 팔 때, 같은 프레임에 플레이어 칸으로 착지한 같은 색 블록까지 함께 파서 살아남는다고 예측했다. 실제 게임은 그 프레임에 착지한 블록을 파기 그룹에 넣지 않는다.
   - 해결: bs_step이 이번 프레임 착지 칸을 Grid.landed에 기록, 파기 탐색이 건너뛴다. 실제와 같은 프레임(2918)에 사망을 예측한다.

10. 속도.
   - 해결: 블록 시뮬의 지지 고정점 반복을 아래에서 위로 순회하도록 바꿔 2배 빨라졌다(검증 결과 동일).

11. 실패한 시도(다시 하지 말 것).
   - 확인: 산소를 항상 선형 시간 가치로 두면 느려진다(p8).
   - 확인: 입력 큐 전체를 중복 제거 키에 넣으면 빔이 같은 노드로 막힌다(p14).

## 후반 작업: 목표 변경(퍼펙트 에어 우선)과 RCSP 평가

목표 변경(사용자, 같은 날): 맵이 랜덤이라 완전한 플레이는 없다. 우선순위 = 퍼펙트 에어(캡슐 56개 전부, 30초 안에 먹을 수 있으면 돌아가서라도 먹는다) > 노미스 > 시간. 패턴상 피할 수 없는 미스는 허용하고 계속 진행한다(봇은 남은 목숨으로 계속 진행). 평가에 판 끝 캡슐 수(P+0x8A)를 추가했다. India 전체 캡슐 = 56.

p26 깔림 6회 중 5회는 390m 2열 같은 지점(air 55215, X 파기 직후 산소 사망일 가능성, 분석 중).

1. X블록을 깬 직후 옆 캡슐을 지나침(d90 480m, d104 469m 사망).
   - 원인: X블록 산소 감소는 20프레임에 나뉘어 들어오는데 플래너는 남은 감소분을 몰랐다. 그래서 산소가 충분하다고 보고 캡슐 가치를 1/10로 계산했다.
   - 해결: P+0x164(s32, 산소 변화 대기량: 캡슐 +23000, X -20000, 매 프레임 1000씩 적용)를 drgbot이 A줄 5, 6번째 값(증가/감소 남은 프레임)으로 넘긴다.

2. 캡슐 옆에서 무한 대기(d90 343m, d40 49m).
   - 원인: 정지 격자 평가가 캡슐을 약속하지만 실제로는 갈 수 없다(옆 칸을 파면 위 블록이 그 칸으로 떨어짐, 또는 칸을 파면 같은 색 덩어리가 함께 파여 캡슐이 떨어짐). 빔은 실제로 못 먹으므로 약속만 유지하는 대기가 최고점.
   - 해결 2가지:
     - (a) 정체 재탐색: 서 있고 최선 계획이 내려가지도 캡슐을 먹지도 않으면, 평가의 캡슐 점수와 캡슐 산소를 끄고 다시 탐색(BEST 줄 끝 " R"). 실제 시뮬에서 먹은 캡슐 점수는 그대로.
     - (b) 처음 시도한 "위에 블록 있는 옆 파기 금지"(PLAN_UPEN)는 깊이 경로까지 막아 오히려 산소 사망 10회(p22). 캡슐 비용에만 적용하도록 바꿨다.

3. RCSP 잎 평가(사용자 제안: 산소를 점수가 아니라 자원으로). PLAN_LEAF=1.
   - 정지 격자에서 칸마다 (시간, 산소, 캡슐 수) 파레토 라벨 다익스트라. 캡슐 칸은 산소 +23000, 캡슐 +1, X칸은 -20000. 같은 줄 좌우 왕복 금지(캡슐 중복 방지).
   - 목표 깊이(탐색 시작 + 12줄) 도달 라벨을 air_value - 시간*70 + 캡슐*CAPV 로 평가해 최댓값.
   - 효과: 이전 방식(다익스트라 2회 + 산소 점수 + 캡슐 잠재력)의 가중치 문제를 없앤다.

4. 캡슐 가치 CAPV = 126000 (1800프레임 x 70 = 30초). 빔 시뮬에서 먹은 캡슐(Player.caps)과 잎 라벨 캡슐 모두에 준다.
   - 효과: 캡슐 20.3 -> 50.8.

5. 산소 바닥 완화: 산소가 바닥 아래로 가는 라벨을 버리지 않고 부족분 1당 20점(PLAN_SOFTK) 감점.
   - 원인: 모든 경로가 산소 부족이면 평가 차이가 없어져 X 상자 함정(426m, 6개 맵)에 그대로 들어감. 이미 갇히면 X를 깨고 나간다.

6. 지붕(사용자 규칙): 파려는 칸 위 블록이 정착(상태 4)한 같은 색 덩어리이고 그 덩어리가 다른 칸 위에 얹혀 있으면 지붕 = 안전, 비용 0. 아니면 위에 쌓인 블록 1개당 30프레임(PLAN_STACKF). 덩어리에 파는 칸이 포함되면 지붕 아님.
   - 덩어리 검사는 잎 평가마다 칸별로 1번만(캐시, 레벨 구분 블록 0x6F15 큰 덩어리에서 6초 걸리던 문제).

7. 위쪽 캡슐(사용자 규칙): 위 캡슐 아래 열을 파내면 캡슐이 떨어져 내려온다. 플레이어 줄의 그 열에 가상 캡슐(비용 = 사이 블록 수 x (흔들림+10) + 10프레임, 사이에 X가 있으면 제외). 아래쪽 탐색 범위 밖 캡슐은 그 열에 가까울수록 보너스(CAPV/10).

8. 결정적 탐색: 시간 제한 2초가 PC 부하에 따라 탐색 깊이를 바꿔 결과가 매번 달라졌다. 빔 폭이 고정이므로 시간 제한은 비상용 10초(PLAN_TLIMIT)로. 평가 제한 시간 1700초(DRG_TIMEOUT). MAME 평가에서는 plan.exe 실행 중 에뮬레이션이 멈추므로 탐색 시간은 게임 시간에 영향이 없다.

9. 도구: scripts/mkstate.py(기록 프레임 -> 플래너 상태 파일), scripts/recair.py(OB_REC 기록의 P 구조체에서 실제 산소 +0x160과 대기량 +0x164 읽기). 상태를 만들 때 산소는 추정하지 말고 recair 값을 쓸 것(추정값 때문에 426m 분석을 한 번 잘못했다).

9. 결론(사용자 기준).
   - 사용자 기준: 생각 때문에 게임이 1프레임이라도 멈추면 실패. MiSTer(ARM, 이 PC보다 훨씬 느림)에서도 돌아야 한다.
   - 지금 구조(8프레임마다 게임을 멈추고 plan.exe를 기다림, 결정마다 약 5만 프레임 시뮬)는 이 기준에서 실패다. 10시간 넘게 탐색의 벌점과 옵션만 조정했고 구조를 바꾸지 않은 것이 원인이다.
   - 다음 구조: docs/continue/handoff.md 1-2절.

10. 다음 구조 결정(사용자, 세션 끝).
   - 원인: 플레이 중에 계속 탐색하는 구조라 게임을 멈추고 자원을 낭비한다.
   - 가설: 게임은 결정론적이고 맵 전체가 스테이지 시작 때 메모리에 있다(플레이 중 안 바뀜, 같은 확정 시점이면 같은 맵). 시작부터 첫 조작까지 약 2.7초, 계산은 실시간의 2.6배.
   - 해결 방향: 스테이지 시작 때 맵을 읽어 게임 전체 버튼 순서를 백그라운드에서 미리 계산하고, 플레이 중에는 그 버튼만 누른다. 매 프레임 실제 상태와 예측을 비교해 어긋나면 그 시점부터 다시 계산. 먼저 시뮬을 게임과 정확히 같게 만든다(남은 x ±256 차이). 자세한 순서는 docs/continue/handoff.md 2-1.
