# 2026-10-31 수정 기록: Mr. Driller G 패치 롬 성능 비교 (프레임 시간 변동) - 결론: 문제 없음

## 배경 (사용자 보고)

- 2026-10-25 코어에 유령 블록 패치를 넣은 디버그 빌드(`Arcade-SYSTEM10_20261025`, 브랜치 `drillerg-ghost-block-fix`)에서
  북극 스테이지 프레임 시간 표시가 16.68 대신 16.80~16.66 으로 흔들렸다.
- 그래서 패치가 성능을 떨어뜨리는지 의심되어 코어 패치는 무효 처리했다.
- 이후 별도 프로젝트(`D:/My_App_Project/driller-rom-patch`)에서 같은 수정 15워드 + BGM 스트림 크래시 수정 5워드 = 20워드를
  롬(`mrdrilrg_patch`)에 직접 넣었다.
- 질문: 패치 롬이 순정 롬보다 느린가? 순정 롬에서도 흔들리는가? 33.8688 MHz + CPU Turbo 로 버거운가?

## 가설

| # | 가설 | 결론 |
|---|---|---|
| 1 | 패치 코드가 CPU 시간을 더 쓴다 | 아님 (MAME 통제 실험에서 차이 없음) |
| 2 | 순정 롬도 프레임 표시가 흔들린다 (게임 기본 상태) | **맞음** |
| 3 | 33 MHz 코어 CPU 가 부족해 프레임을 놓친다 | 아님 (최악 프레임도 3.4 ms 여유, 놓친 프레임 0) |

## 프레임 시간 표시가 흔들리는 이유

- 좌상단 표시(`rtl/gpu_frametime.vhd`)는 1초 동안 게임이 매 프레임 쓰는 GP1(05) 사이 간격의 평균이다.
- 한 필드 길이 자체가 인터레이스 262/263 라인 때문에 16.654 / 16.718 ms 로 번갈아 바뀐다.
- GP1(05) 쓰기 시점도 vblank 후 0.23~1.54 ms 사이에서 매 프레임 달라진다.
- 그래서 놓친 프레임이 없어도 1초 평균이 16.66~16.70 사이에서 움직인다.
- 실제로 프레임을 놓치면 표시가 빨간색이 되고 평균이 약 16.97 로 올라간다.
- 16.80 은 2026-10-25 코어 패치 빌드에서 본 값이며, 이번 순정/패치 롬 측정에서는 나오지 않았다.

## 측정 방법 (새 디버그 프로브)

- `rtl/cpu.vhd`: 디버그 출력 `dbg_vsync` = 디코드 단계 PC 가 PSY-Q libetc `VSync()` + `v_wait` 범위
  [sll - 0x17C, sll + 0x90) 안에 있음.
- 기준 주소는 `v_wait` 의 `sll a1,a1,15` 명령(`00052BC0`, TURBO_CACHE 패치 후 `00052C00`)을 처음 디코드할 때 자동으로 잡는다.
  Driller G `0x8027CD70`, Driller 2 `0x801AF8A8` 로 두 게임 배치가 같다.
- 이 시간 = CPU 가 할 일이 없어 vblank 를 기다리는 시간(여유 시간).
- 신호 경로: `cpu.vhd` -> `psx_top.vhd` -> `psx_mister.vhd` -> `NAMCOS10.sv` -> `rtl/ns10/ns10_gtrace.sv`.
  디버그 빌드만이며 릴리스에서는 쓰이지 않아 합성에서 제거된다.
- GPU 트레이스(OSD 'Trace GPU 10 s') 새 항목:
  - F/7 = VSync() 진입(data bit0 = 1) / 이탈(0).
  - F/8 = vblank 마다 직전 필드에서 VSync() 안에 있던 clk2x 수(유휴 시간).
- 분석: `python tools/gputrace.py fetch <out.bin>` 후 `python tools/gputrace.py frames <out.bin> [out.txt]`.
  - 필드별 유휴 ms, GP1(05) 지연, 놓친 프레임, 유휴 최소/백분위/히스토그램, 좌상단 표시 1초 평균 재계산.
- 단위 테스트: `sim/ns10/run_gtrace.sh` (ModelSim, `tb_gtrace.sv`) PASS.
  - 필드당 유휴 130 clk 정확, 진입/이탈 214/214, 손실 0.
- 빌드: 디버그(SEED 2), main(=릴리스 20261024 소스) + 프로브.
- hold 위반은 기존 디버그 빌드와 같은 경로뿐이다(SPU `RamVoiceRecord` -0.118 ns, DMA `fifoOut` -0.168 ns, slow -40C).
  변경 코드와 무관하다.

## 결과 2: MAME 통제 실험 (같은 상태, 같은 입력, 코드만 다름)

- GroovyMAME `namcos10.exe mrdrilrg`, MAME 세이브스테이트 `F:/global_mame/cfg/sta/mrdrilrg/3.sta`.
- Lua 로 같은 파기 입력(아래 260프레임 / 왼쪽 20 / 오른쪽 20 반복, 버튼 2프레임마다) + 공기 고정(`0x80369CA0`).
- 두 번째 실행은 상태 로드 직후 20워드를 RAM 에 써서 패치 코드로 만든다. 매 프레임 20워드가 유지되는지 확인했다.
- 측정: VSync()/v_wait 안에서 Vcount(`0x802E3804`)를 읽은 횟수 = 대기 루프 반복 수(유휴에 비례).
- 결과: 2996 프레임, 깊이 38m -> 319m, 매 프레임 게임 상태(깊이) 동일.
- 대기 루프 반복 수가 2995 프레임에서 완전히 같고, 1 프레임만 패치 쪽이 3회 더 기다렸다(약 2 us 더 빠름).
- 패치 내용상으로도:
  - 유령 블록 수정은 위쪽 재귀 전에 상태를 검사해 '낙하 중이고 미방문' 칸에만 들어가므로 원본보다 재귀가 같거나 적다(검사당 +2~3 명령).
  - BGM 수정은 디버그 명령 5개를 분기 2개로 바꾼 것이다.

## 결론

- 패치 롬은 성능에 영향이 없다.
- 프레임 표시 변동(16.66~16.70)은 순정 롬에도 있는 게임 기본 상태다(인터레이스 필드 길이 + GP1(05) 쓰기 시점).
- 33.8688 MHz + CPU Turbo High 로 가장 바쁜 프레임에서도 약 3.4 ms(프레임의 약 20%) 여유가 있고 프레임을 놓치지 않는다.
- 코어 성능 개선이나 프레임 고정 트릭은 필요 없다.
- 최종 결론(사용자 확인): 특별한 문제 없음.
