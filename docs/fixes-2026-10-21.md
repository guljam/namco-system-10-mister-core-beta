# Star Trigon 부팅 멈춤 (SPU 전송 교착) - 원인 / 가설 / 해결 / 교훈

작성 2026-10-21. 관련 파일: `rtl/spu.vhd`, `sim/spu/`, `tools/ns10trace.py`.
이전 기록은 `docs/fixes-2026-10-19.md`, 현재 상태와 작업 방법은 `docs/handoff.md`에 있다.

## 요약

| 항목 | 내용 |
|---|---|
| 증상 | Star Trigon(startrgn)이 부팅 화면(왼쪽 흰색 / 노랑 / 하늘색, 오른쪽 검정) 뒤 검은 화면에서 멈춤. 디버그 빌드는 좌상단에 `EA` 표시. OSD는 정상. 릴리스 / 디버그 빌드 모두 같음 |
| 종류 | 회귀 버그. Gamshara의 EA를 고친 커밋 7577f5b가 원인 |
| 원인 | 7577f5b는 "SPU가 밀려 있으면(stash > 0) SPU RAM 전송 금지"로 바꿨다. Star Trigon 부팅 중에는 SPU가 전송이 없어도 계속 밀려 있어 stash가 0이 되는 일이 없다. 그래서 전송이 영원히 막히고, 게임은 사운드 데이터 업로드가 끝나기를 기다리며 멈췄다 |
| 해결 | 전송을 제한하되 완전히 막지는 않는다. stash가 0 또는 15이면 전체 속도, 그 사이에서는 샘플당 1워드 |
| 검증 | GHDL SPU 테스트벤치로 교착을 재현하고 수정안 확인. 실기에서 4개 게임(startrgn, gamshara, mrdrilrg, mrdrilr2j) 확인 |

## 1. 배경 지식

외부 개발자를 위해 필요한 배경만 정리한다.

### 1.1 SPU 샘플 예산
- 이 코어는 PSX_MiSTer를 기반으로 한 Namco System 10(NS10) 코어다. SPU(사운드 칩)는 PSX SPU 로직을 그대로 쓴다.
- NS10의 SPU(CXD2938Q)는 50.75 MHz로 돌고, 샘플당 768클럭, 66.15 kHz로 출력한다. 코어 SPU는 33.8688 MHz(`clk1x`)에서 돈다. 샘플레이트를 맞추려고 샘플당 클럭을 768에서 **512**로 줄였다(`sampleticks < 511`).
- 그 결과 샘플당 연산 예산이 실기의 2/3다. PSX SPU 상태기계는 24개 보이스를 처리하는 데 아무 일이 없어도 샘플당 약 460~500클럭을 쓴다. 여유가 거의 없다.

### 1.2 stash와 EA
- `stashedSamples`(0~15)는 "처리가 밀린 샘플 수"다. 샘플 시각(`sampleticks = 0`)이 됐는데 아직 이전 샘플을 처리 중이면 1 늘고, 밀린 샘플을 연달아 처리하면서 줄어든다.
- 15에서 더 밀리면 그 샘플은 버려지고 `sound_timeout`이 켜진다. 디버그 빌드의 PSX 오류 오버레이는 이것을 **EA**로 표시한다. 오버레이는 처음 생긴 오류 하나만 래치하므로, EA가 보인다고 지금도 계속 샘플을 버리고 있다는 뜻은 아니다.

### 1.3 SPU RAM 전송
- CPU / DMA가 SPU RAM에 샘플 데이터를 올릴 때 데이터는 FIFO(`FifoIn`)에 들어간다. SPU 상태기계는 보이스 슬롯 하나가 끝날 때(`VOICE_END`)마다 FIFO에서 1워드를 꺼내 RAM에 쓴다. 샘플 하나에 보이스가 24개이므로 최대 24워드다.
- DMA는 FIFO가 비었을 때만 다음 블록을 요청한다. 따라서 SPU가 FIFO를 비우지 않으면 DMA가 끝나지 않고, DMA 완료를 기다리는 게임은 멈춘다.
- SPU RAM은 DDR3에 있고 보이스 캐시를 거친다. DDR3는 GPU와 공유하므로, 캐시 미스가 나면 GPU가 쉬는 지점까지 기다린다(psx_top 중재기 `WAITGPUPAUSED`). 그래서 GPU 부하가 크면 SPU 처리 시간이 늘어난다.

### 1.4 7577f5b (2026-10-19)가 한 일
- Gamshara는 로드 후 24~26초에 샘플을 업로드한다. 이때 보이스 슬롯마다 RAM 쓰기가 붙어 샘플당 약 536클럭이 됐고, stash가 15에 닿아 EA가 났다.
- 7577f5b는 stash가 0일 때만 전송하도록 바꿨다. 밀려 있으면 전송을 쉬고, SPU가 따라잡은 뒤 다시 전송한다. Gamshara의 max stash는 15에서 1로 줄었다.
- 이 수정 뒤 Gamshara, Driller G, Driller 2만 테스트했고 **Star Trigon은 테스트하지 않았다.**

배제한 것:
- GPU / 그래픽 문제: 화면이 검은 채로 멈췄지만 OSD는 동작했고, 프로브상 SPU 전송이 멈춰 있었다. 수정 후 그래픽은 이전과 같이 정상이다.
- b5efdaa(리비전 분리): 릴리스와 디버그가 똑같이 실패했고, SPU 로직은 건드리지 않았다.

## 3. 원인 (정리)

```
게임: 사운드 데이터 DMA → SPU FIFO → (SPU가 VOICE_END마다 1워드씩 RAM에 씀)
7577f5b: if (FifoIn_Empty = '0' and stashedSamples = 0) then RAM_WRITE
Star Trigon 부팅: SPU 처리 540~577 clk/샘플 > 512 → stash가 0으로 돌아오지 않음
→ FIFO가 비지 않음 → DMA가 다음 블록을 요청하지 않음 → 게임이 업로드 완료를 기다리며 멈춤
```

핵심은 "SPU가 밀려 있으면 전송을 잠깐 쉰다"는 스로틀이 **SPU가 전송과 상관없이 밀려 있는 경우**를 고려하지 않았다는 점이다. 그런 경우에는 쉬어도 따라잡지 못하므로 스로틀이 영구 차단이 된다.

## 4. 해결 (`rtl/spu.vhd`, `VOICE_END`)

```vhdl
if (CNT(5 downto 4) = "11" and FifoOut_NearFull = '0' and (stashedSamples = 0 or stashedSamples = 15 or index = 23)) then
   -- RAM_READ (전송 읽기)
elsif (FifoIn_Empty = '0' and (stashedSamples = 0 or stashedSamples = 15 or index = 23)) then
   -- RAM_WRITE (전송 쓰기)
```

| stash | 전송 | 이유 |
|---|---|---|
| 0 | 전체 속도(샘플당 최대 24워드) | 여유가 있을 때는 원래 PSX 동작 |
| 1~14 | 샘플당 1워드(마지막 보이스 슬롯) | 업로드 때문에 SPU가 더 밀리지 않게 하면서도(Gamshara EA 방지) 진행은 보장. 추가 부하는 샘플당 수 클럭 |
| 15 | 전체 속도 | 이미 샘플을 버리는 중이라 전송을 막아도 소리가 나아지지 않음. 7577f5b 이전 동작과 같음 |

함께 넣은 디버그 도구(디버그 리비전 전용, 릴리스에서는 합성되지 않음):
- 프로브 "SPU2": 전송 워드 수, 버려진 샘플 수(clear 이후), 현재 stash, FIFO 상태. `python tools/ns10trace.py spu2 [clear]`. 업로드가 진행 중인지 멈췄는지 바로 보인다.
- GHDL 테스트벤치 `sim/spu`: 24개 보이스 재생(피치를 달리해 캐시 미스를 고르게 분산), 고정 지연 DDR3 모델(GPU 대기의 대용), FIFO가 비면 다음 64워드를 보내는 DMA, 업로드 데이터 검사.
  - `sh ghdl.sh compile <이름> [spu.vhd 경로]`
  - `sh ghdl.sh sim <이름> <LAT> [SAMPLES]`
  - `sim/gpu/ghdl.sh compile`로 만든 altera_mf / mem 라이브러리가 필요하다.

## 6. 교훈

1. **스로틀(조절)은 절대 완전 차단이 되면 안 된다.** "조건 X일 때만 진행"이라는 규칙을 넣을 때는 X가 영원히 거짓이 될 수 있는지 먼저 따진다. 최소 진행량(여기서는 샘플당 1워드)을 보장하는 경로를 둔다.
2. **"막는 쪽"의 원인이 다른 곳에 있을 수 있다.** 7577f5b는 "전송 때문에 밀린다"는 Gamshara 관찰을 일반화했다. Star Trigon은 전송이 없어도 밀렸다(GPU / DDR3 부하). 수정의 전제가 모든 게임에 맞는지 확인해야 한다.
3. **경계값만으로 탈출구를 만들지 말 것.** "0 또는 15"는 그럴듯해 보였지만, 값이 중간에서 맴도는 평형 상태를 놓쳤다. 이 결함은 빌드 전에 시뮬레이션에서 잡혔다(빌드 1회, 20분 절약).
4. **수정 후 회귀 테스트는 지원하는 모든 게임으로.** 이번 회귀는 Star Trigon만 테스트하지 않아서 생겼다. SPU / 공통 로직을 바꾸면 startrgn, gamshara, mrdrilrg, mrdrilr2j를 모두 부팅해 본다.
5. **실기 프로브가 가장 빠른 진단이었다.** 이미 올라가 있던 디버그 빌드의 SPUT 프로브만으로, 새 빌드 없이 원인을 확정했다. 프로브는 최대값뿐 아니라 "지금 진행 중인가"(전송 카운터, 현재 상태)를 보여 주도록 만들어 두면 좋다. 그래서 SPU2를 추가했다.
6. **시뮬레이션은 실기 수치에 맞춰 조건을 고른다.** 테스트벤치의 DDR3 지연은 GPU 대기를 흉내 낸 대용값이다. 실기 프로브(샘플당 클럭, 보이스 대기)를 보고 "정상 / Gamshara형 / 만성 과부하" 구간을 지연 8 / 70 / 250으로 대응시켰다.

## 7. 남은 과제

- SPU 예산 자체가 부족하다(512클럭, 실기 768 상당). 부팅이나 GPU 부하가 클 때 샘플을 버리는 일이 남아 있다. Star Trigon 부팅 때의 EA가 그 예다(무음 구간이라 들리지 않음).
- 근본 개선 후보는 `docs/spu-fix.md`의 안 A(SPU를 `clk2x`에서 샘플당 1024클럭으로 구동)와 DDR3 중재기의 SPU 우선순위다. 둘 다 타이밍 / GPU 속도에 영향이 있어 별도 작업으로 다룬다.

# NVRAM(하이스코어) 저장 / 불러오기 조사, MEM(M) 플래시 프로그램 AND 동작

작성 2026-10-21. 관련 파일: `rtl/ns10/ns10_romboard.sv`, `tools/ns10model.py`, `rtl/ns10/ns10_nvram.sv`.

## 요약

| 항목 | 내용 |
|---|---|
| 증상(사용자) | Mr. Driller 2(mrdrilr2j): 테스트 모드 설정은 저장 / 복원되지만 게임 안의 최고 점수는 불러오지 못하는 것 같음 |
| 조사 결과 | 저장: MiSTer `.nvm`에 사용자 점수(1위 "A" 663770, 2위 "AAA" 273085 등)가 들어 있음. 불러오기: 코어 부팅 직후 DDR3의 플래시 영역(0x35040000, 16 KB)이 `.nvm`과 md5 일치. 같은 `.nvm`을 MAME 플래시에 넣으면 **TOTAL RANKING**에 사용자 점수가 나옴 → 데이터 형식과 내용은 게임이 받아들인다 |
| 참고 | 어트랙트의 **TODAY'S RANKING**은 RAM에만 있고 전원을 켤 때마다 기본값(DAI / NKT / OIS)으로 돌아간다. MAME도 같다. 저장되는 기록은 TOTAL RANKING 쪽이다 |
| 결론 | 수정 전 빌드도 저장 / 로드가 정상이었다. 아래 플래시 AND 수정은 원인이 아니라 잠재된 정확도 버그 수정이다 |
| 발견한 차이 | MEM(M) Intel 28F640J5 플래시의 워드 프로그램(0x40 / 0x10)과 write buffer(E8 … D0)가 RTL / Python 모델에서 **덮어쓰기**였다. MAME intelfsh와 실제 플래시는 `data &= 새 값`(1→0만 가능, 0→1은 지우기로만) |
| 수정 | RTL: 프로그램을 DDR3 read-modify-write(`S_FPROG_RD` / `S_FPROG_RDW`)로 바꿔 기존 워드와 AND. write buffer 커밋도 워드마다 같은 경로. Python 모델도 AND |
| 검증 | 합성 트레이스(지우기 → 프로그램 → 같은 워드 재프로그램 → write buffer)를 ModelSim `sim/ns10`에 재생: 수정 전 7개 불일치, 수정 후 0. MAME 빈 NVRAM 첫 부팅 트레이스(2200만 벡터) 회귀 |

## 1. 배경

- MEM(M) 보드(Mr. Driller 2)는 설정 / 랭킹 / 집계를 프로그램 플래시 0x40000-0x43FFF에 쓴다. 코어는 이 16 KB를 `.nvm`으로 저장한다(MRA `<nvram index="2">`). 게임이 이 영역에 쓰면 저장 요청이 생기고, MiSTer는 **OSD를 열 때** 저장한다. 점수를 낸 뒤 OSD를 열지 않고 전원을 끄면 그 점수는 저장되지 않는다.
- MEM(N) 보드(Mr. Driller G, Star Trigon)는 NAND0 블록 1(ROM 바이트 0x4200-0x83FF)을 쓴다. NAND 프로그램은 이미 AND였다(`S_PROG_AND`).

## 2. 원인 가설

1. 저장이 안 됨 → 아님. `.nvm`에 점수가 있다.
2. 로드가 안 됨 → 아님. DDR3 내용이 `.nvm`과 같다.
3. 데이터가 깨져 게임이 거부 → 아님. MAME에서 같은 데이터로 TOTAL RANKING이 표시된다.
4. 플래시 쓰기 동작이 실기와 다름 → 사실. 프로그램이 덮어쓰기라서, 게임이 이미 쓴 워드 위에 다시 프로그램하면(실기에서는 비트가 1→0만 바뀜) 결과가 달라진다. 빈 NVRAM 첫 부팅 경로에는 이런 쓰기가 없었다(0건). 점수 저장 경로에서 쓰이는지는 플레이 트레이스가 없어 확인하지 못했다.
5. 사용자가 본 화면이 TODAY'S RANKING이었을 가능성 → 실기 확인 필요.

## 3. 수정 내용

- `ns10_romboard.sv`: `FM_WRITE`는 바로 쓰지 않고 `fp_word` / `fp_data`를 잡아 `S_FPROG_RD`(beat 읽기) → `S_FPROG_RDW`(해당 16비트 lane을 `& fp_data` 해서 바이트 인에이블로 쓰기)로 간다. `S_WB_COMMIT`은 버퍼 워드마다 같은 경로를 돈다. `ns10_nvram`은 이 쓰기를 엿보므로 `.nvm`에도 AND된 값이 들어간다.
- `tools/ns10model.py` `IntelFlash`: `WRITEPART1`, write buffer 커밋을 `&=`로.
- 쓰기 하나가 DDR3 읽기 1회만큼 길어진다(EXP1 wait). 실기 플래시 프로그램 시간(수 µs)보다 짧다.

## 4. 교훈

- 플래시 / EEPROM 에뮬레이션은 "쓰기 = 저장"이 아니다. 프로그램은 비트를 지우기만 한다. MAME 장치 코드(`intelfsh.cpp`의 `&=`)를 그대로 따라야 한다.
- "불러오지 못한다"는 보고는 저장 → 파일 → 로드 → 게임 해석 단계를 나눠 확인한다. 이번에는 MAME에 실기 `.nvm`을 넣어 보는 것만으로 데이터 / 로드 경로를 한 번에 배제했다(빌드 없이).

## 4.1 최종 결론 (사용자 재확인 후)

- 사용자 보고: 스테이지 선택 화면(인도 500m)의 최고 기록이 재부팅하면 공장 초기값으로 돌아간다.
- MiSTer의 최신 `.nvm`에는 새 기록(500m 표 0x230, 이름 "A//", 500m)이 들어 있고, 부팅 후 DDR3 플래시 영역도 `.nvm`과 md5가 같다.
- 같은 `.nvm`을 MAME에 넣고 코인 → 1인 드릴러 → 인도(500m)를 고르면 패널 제목이 **「本日のベストドリラー」(오늘의 베스트 드릴러)**이고 값은 기본값 DAI / 200m / 30000pts다. 실기 코어와 같다.
- 즉 스테이지 선택 패널은 **오늘의 기록**(RAM, 전원 투입 시 초기화)을 보여 주는 것이 원래 게임 동작이다. 영구 기록은 어트랙트의 TOTAL RANKING에 나온다(MAME에서 사용자 점수 표시 확인). 코어 버그가 아니다.
- 저장된 기록 전체를 빨리 보는 방법(사용자 팁): DIP 스위치 1번을 올렸다가 내리면 A.D.S. 화면에서 모든 기록을 바로 확인할 수 있다. 어트랙트 TOTAL RANKING을 7분 넘게 기다릴 필요가 없다.
- 플래시 AND 수정(9e838e4)은 MAME / 실제 플래시와 맞추는 정확도 수정으로 유지한다.
- MAME 입력 자동화 팁: lua에서 같은 입력 필드에 이벤트가 여러 개면 필드별로 OR해서 `set_value` 해야 한다(마지막 이벤트가 0을 덮어써 입력이 사라졌다). 스테이지 선택은 30초 제한이 있어 빨리 눌러야 한다.

## 4.2 수정 값 주입 검증 (빌드 없이)

사용자 제안 방식: `.nvm`의 값을 일부러 바꿔 넣고 게임 화면에서 그대로 나오는지 본다.

1. A.D.S.가 읽는 집계 영역: BOOT 시간 = 0x194(초, u32 LE), OPE 시간 = 0x198. 각각 2:03:04, 1:02:03으로 바꿨다.
2. MAME(`nvram/mrdrilr2j/nand`의 0x40000에 바이트 스왑해 넣음)에서 A.D.S.를 열어 확인했다. 결과 BOOT 2:03:17(+13초 가동), OPE 1:02:03. 체크섬 거부는 없었다.
3. 같은 수정본으로 MAME 부팅 버스 트레이스를 떠서 `tools/ns10cfg.py tbvec <game> <trace> <nvdir>`와 `sim/ns10/run.sh`로 보드 RTL에 재생했다. 165만 벡터, 164만 회 읽기에서 불일치 0.
4. MiSTer: 메뉴 코어로 나간 뒤(실행 중인 코어가 덮어쓰지 않게) `.nvm`을 백업하고 수정본을 올린 다음 MRA를 로드했다. DDR3 0x35040000 덤프의 md5가 수정본과 같았다. 실기 A.D.S. 결과 BOOT 2:03:49, OPE 1:02:03.
5. 실기에서 A.D.S.에 들어간 뒤 코어가 저장한 `.nvm`은 BOOT가 7384초에서 7429초가 되어 있었다. 게임의 플래시 쓰기와 `.nvm` 저장도 정상이다. 확인 후 원본 `.nvm`으로 되돌렸다(MiSTer에 `.nvm.bak_20261021` 백업 있음).

A.D.S. 집계가 0인 이유 (정정된 내용): MAME 플래시 쓰기 탭으로 한 판(랭킹 미진입) → 30분 어트랙트 → 테스트 모드 진입을 기록했다.
- 게임 종료(311~312초): 플래시 블록 전체를 지우고 다시 쓴다(쓰기 약 2400건). MiSTer OSD를 열 때 "Saving..."이 나오는 이유가 이것이다. 그런데 다시 쓴 내용은 **이전과 1바이트도 다르지 않다**. A.D.S. 판 수 / 시간은 이전에 저장된 값 그대로다.
- 테스트 모드 진입(2100초): 다시 블록을 쓰고, 이때 RAM의 집계(1000m Num 1, TOTAL 2, BOOT / OPE, 0x1A0 체크섬)가 들어간다.
- 즉 집계는 게임마다 RAM에서 올라가지만 **플래시에 반영되는 것은 테스트 모드에 들어갈 때**다. 랭킹은 이름 입력 때 저장된다. 실기 500m 판들은 테스트 모드에 들어가기 전에 재부팅해서 집계가 남지 않았다. 게임 프로그램의 동작이며 MAME와 같다.
- 정정: 처음에는 "게임 종료 때 플래시 쓰기가 없다"고 적었다. 이는 고장 난 lua 탭(`state["PC"]`가 nil이라 콜백이 조용히 실패) 때문이었다. `GENPC`와 pcall로 고친 뒤, 빈 NVRAM 부팅(약 2.4초에 쓰기 발생)으로 탭이 동작하는지 먼저 확인하고 다시 측정했다.
- MAME 자동 실행: 시작 시 경고 화면이 키 입력을 기다린다. 사용자 `ui.ini`는 건드리지 않고 `-inipath <scratch>/ini`(ui.ini에 `skip_warnings 1`)로 실행한다.

시뮬레이션 범위: 게임 화면까지 가는 전체 시스템(CPU/GPU) RTL 시뮬레이션은 게임 시간 수십 초가 수십억 사이클이라 현실적이지 않다. 대신 (a) 게임 로직은 MAME, (b) 보드 RTL의 플래시 / NVRAM 읽기는 MAME 트레이스 재생(`tb_ns10`, nvdir에 수정 NVRAM), (c) HPS 다운로드 경로는 실기 DDR3 덤프로 나눠 확인하면 빌드 없이 전 구간을 검증할 수 있다.

# SPU를 67.7 MHz(clk2x)로 이동 - 샘플당 예산 512 → 1024클럭 (브랜치 spu-fix)

관련 파일: `rtl/spu.vhd`, `rtl/spu_ram.vhd`, `rtl/spu_gauss.vhd`, `sim/spu/`, `tools/ns10trace.py`. 계획은 `docs/spu-fix.md` 안 A.

## 요약

| 항목 | 내용 |
|---|---|
| 목적 | SPU 연산 예산 부족(샘플당 512 clk1x, 실기 768) 해소. Star Trigon 부팅 중 드롭(135샘플, EA), GPU 부하 시 잦은 1샘플 오버런 |
| 변경 | SPU 전체(상태기계, 보이스 MLAB, ADPCM / gauss RAM, SPU RAM 캐시 / FIFO)를 clk2x(67.7376 MHz)로. 샘플당 1024 clk2x = 66.15 kHz(샘플레이트 그대로). CPU 버스 / DMA / 세이브스테이트는 clk1x 그대로 |
| 결과 (실기, 4게임 각 2분) | 드롭 0, 최대 stash 1. 무부하 640~755 clk2x / 1024. 이전: Star Trigon 부팅 드롭 135, 부하 540~577 clk1x / 512 |
| 시뮬 | 기존 clk1x SPU와 출력이 비트 단위로 같음(DDR3 지연 8 / 40, 업로드 포함 3992샘플) |
| 타이밍 | 디버그 빌드 setup / hold 모두 양수. 릴리즈 빌드 SEED 2는 hold -0.021 ns(-40C에서 -0.048) 1곳: SPU `RamVoice_addrA` → 보이스 레지스터 MLAB(배치 문제). SEED 3으로 다시 빌드해 hold 해소(아래 5) |

## 1. 배경

- 실기 SPU(CXD2938Q)는 50.75 MHz, 샘플당 768클럭. 코어는 33.8688 MHz(clk1x)에서 샘플레이트를 맞추려고 512클럭으로 줄였고, PSX SPU 상태기계는 아무 일이 없어도 샘플당 약 490클럭을 쓴다. 보이스 캐시 미스(DDR3, GPU가 쉬는 지점까지 대기)가 조금만 겹쳐도 밀렸다.
- 같은 PLL의 clk2x(67.7376 MHz)로 옮기면 샘플당 1024클럭이 되고, 연산 부분은 클럭 수가 같으므로 시간으로 절반이 된다. DDR3 대기는 같은 시간이므로 여유는 약 7.8 µs / 샘플 늘어난다.

## 2. 경계 처리 (clk1x ↔ clk2x)

- clk1x와 clk2x는 같은 PLL에서 위상이 맞는다. `clk2xIndex = '0'`인 clk2x 엣지가 clk1x 엣지와 겹친다(GPU와 같은 규칙).
- clk1x에서 오는 입력(CPU 버스 쓰기 / 읽기, DMA, 세이브스테이트 쓰기, `SS_reset`)은 `clk2xIndex = '0'`일 때만 처리한다. 한 clk1x 동안 두 번 처리되지 않는다.
- clk1x로 나가는 펄스(`irqOut`, `spu_tick`, `sound_timeout`, `SS_RAM_done`)는 `clk2xIndex = '0'` 엣지에서만 지운다. clk1x가 반드시 한 번 본다.
- 세이브스테이트 MLAB 읽기는 CPU 포트(포트 0) 쪽으로 옮겨 clk2x 처리 포트의 주소 mux를 줄였다.
- 67.7 MHz에서 걸리던 긴 경로 2개는 레지스터를 하나 넣었다. 피치 모듈레이션 곱셈은 `VOICE_APPLYADSR`에서 값만 잡고 `VOICE_APPLYVOLUME`에서 곱한다. 리버브 주소 계산은 `reverb_issue` 다음 클럭에 요청을 낸다.

## 3. 시뮬레이션에서 찾은 문제 (빌드 전에 모두 수정)

`sim/spu` 테스트벤치를 확장했다. DDR3 모델이 실제 ADPCM 블록을 돌려주고, 리버브 / 피치 모듈레이션 / 노이즈를 켜며, 매 샘플 출력 L / R을 파일로 남긴다. 그래서 기존(clk1x, `sim/spu/gen/base` = 21a4960) SPU와 출력을 `cmp`로 비교할 수 있다.

1. **리버브 RAM 요청이 나가지 않음 (멈춤).** `reverb_issue <= '1'`을 상태 case 안에서 쓰고, case 뒤에서 기본값 `'0'`을 썼다. VHDL은 같은 클럭에 마지막 대입이 이기므로 요청이 한 번도 나가지 않았다. 상태기계가 `REVERB_READ1`에서 RAM 응답을 영원히 기다렸다. 기본값을 case 앞으로 옮겼다.
2. **캐시 데이터를 한 클럭 일찍 받음 (소리 틀림).** `spu_ram`은 캐시 히트에서 `cache_addr_b`와 완료(`ram_processed`)를 같은 클럭에 낸다. 예전에는 요청 쪽이 clk1x, 캐시 RAM이 clk2x라 그 사이에 읽기가 끝났다. 둘 다 clk2x가 되자 SPU가 이전 워드를 받았다(0437, 8EDD 대신 0437, 0437). 히트 완료를 한 클럭 늦췄다(`ram_processed_hit`).
3. **WAITWRITE에 출구가 없음 (원본 PSX 코어 버그, 멈춤).** DDR3 쓰기 FIFO가 거의 차면(20 / 32) 쓰기 요청은 `WAITWRITE`로 가는데, 이 상태에는 IDLE로 돌아가는 조건이 없었다. 기존 SPU는 이 조건까지 가지 않았을 뿐이다. 2배 빠른 SPU는 DDR3 지연 250 업로드에서 FIFO를 채워 영원히 멈췄다. FIFO가 비면 완료하도록 고쳤다(쓰기 데이터는 요청 시점에 이미 받아 둔다).
4. **테스트벤치 문제 2가지 (RTL과 무관).** (a) TB의 clk2x가 clk1x보다 1/4주기 어긋나 있었다. 그래서 반 clk1x 길이의 `spu_tick` 펄스를 놓쳤다. 실기 PLL처럼 엣지를 맞췄다. (b) TB가 SPU 처리 도중 아무 때나 레지스터를 써서, 처리 속도가 다른 두 SPU에서 쓰기가 다른 샘플에 반영됐다. 모든 쓰기를 샘플 끝의 유휴 구간(clk1x 500 / 512)에서 하도록 바꿨다.

| DDR3 지연 | 재생 | 업로드 (500블록) |
|---|---|---|
| 8 | 최대 596, 오버런 0, 출력 비트 일치 | 최대 742, 드롭 0, 데이터 오류 0, 출력 비트 일치 |

## 5. 남은 일

- 릴리즈 빌드 hold -0.021 ns: SPU 보이스 레지스터 MLAB 쓰기 주소. 이전 디버그 빌드에서 clk1x일 때도 같은 종류(MLAB 주소 레지스터)가 나왔던 배치 문제다. SEED를 바꿔 다시 빌드하는 것이 첫 시도다.
  - 해결(RTL 변경 없음): `NAMCOS10_release.qsf` SEED 2 → 3. 4개 코너(slow/fast × 100C/-40C) 모두 hold 양수(최소 +0.092 ns), 코어(emu) setup 양수. 남은 것은 HDMI 스케일러 `ascal` setup -0.047 ns(slow 100C) / -0.275 ns(slow -40C)뿐으로, SEED 2 릴리즈(-0.128 ns, 실기 화면 정상)와 같은 MiSTer 프레임워크 경로다. rbf: `releases/_Arcade/cores/Arcade-SYSTEM10_20261021-rev1.rbf`.
- `useSDRAM`(SPU RAM을 SDRAM에 두는 모드)은 clk2x SPU에 맞춰 고치지 않았다. NS10은 쓰지 않는다(시도했다가 되돌린 모드, handoff 참고).
- CPU 1.5배(clk2x에 4클럭 중 3클럭 enable) 검토는 별도 단계.

## 1. 왜 기존 FPS 카운터를 쓰지 않았나 (원인)

- 업스트림 PSX 코어의 FPS 카운터는 "표시 시작 주소(GP1(05))의 값이 바뀐 횟수"를 센다. 더블 버퍼 게임을 가정한 방식이다.
- 실기 GPU 트레이스(`tools/gputrace.py`, 4게임 각 10초): 네 게임 모두 GP1(05)에 매 프레임 **같은 값 0**을 쓴다. 인터레이스 필드를 번갈아 그리는 단일 버퍼라서 주소가 바뀌지 않는다. 그래서 기존 카운터는 항상 0이 된다.
- 대신 쓰기 자체는 게임 루프마다 한 번씩, vblank 뒤 0.2~3.7 ms 안에 온다(정상 간격 15.5 / 17.9 ms 교대, 평균 16.686 ms = 59.94 Hz). 프레임을 놓치면 간격이 33.4 / 66.7 ms로 늘어난다(Mr. Driller 2 / G 데모에서 관찰).

## 2. 동작 (가설 → 설계)

- 시간: 10 µs 단위 카운터(33.8688 MHz에서 338.688클럭마다 1, 분수 누산). 쓰기 사이 간격을 1초 창 안에서 합산하고 나눠 평균을 낸다(순차 나눗셈 + BCD 변환, 1초에 한 번).
- 누락 판정: 쓰기가 vblank와 겹치지 않는 위치에 오므로, "vblank가 지났는데 이번 프레임 쓰기가 없었다"를 그 vblank에서 바로 판정할 수 있다. 기준은 직전 1초 창에서 쓰기 사이 vblank 수의 최솟값(60 fps 게임은 1, 30 fps 게임은 2). 그래서 30 fps 게임도 1초 뒤에는 정상 기준으로 바뀐다.
- 색: 겹친 두 개의 글자 오버레이(파랑 / 빨강) 중 하나를 켠다. 오버레이 색 값은 `x"BBGGRR"` 순서다(R이 하위 바이트).
- 일시정지(`ce = 0`) 중에는 시간도 멈춘다.

## 3. 검증

- GHDL 단위 테스트(`sim/gpu/tb_frametime.vhd`, 실제 클럭 속도, 9초): 60 fps 16.68 / 1프레임 누락 시 다음 vblank에서 즉시 빨강, 그 창 평균 16.96, 1초 뒤 파랑 / 30 fps 전환 시 빨강 후 1초 뒤 기준이 2로 바뀌어 파랑, 33.36 / 쓰기 중단 시 즉시 빨강, 다음 창 `--.--`.
- 실행: `cd sim/gpu; ghdl -a --std=08 -frelaxed -fsynopsys --workdir=ghdl/ft ../../rtl/gpu_frametime.vhd tb_frametime.vhd; ghdl -e ... tb_frametime; ./ghdl/tb_frametime.exe` (MSYS2 mingw64 GHDL). GPU 시뮬(`ghdl.sh compile`)도 새 파일을 포함하도록 `gen.sh` 수정.
- 빌드: 디버그 4개 코너 setup / hold 모두 양수(최소 hold +0.079 ns).
- 실기(각 게임 2분, 30/45/60/90/120초 캡처): 위 요약 표. SPU 프로브 드롭 0(4게임).
