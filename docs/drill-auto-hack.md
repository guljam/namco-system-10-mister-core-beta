# Mr. Driller 2 / G 스마트 싱크로 연사 (Drill (Auto)) 핵 — 어떻게 찾고 만들었나

이 문서는 게임에 대한 사전 정보가 거의 없는 상태에서 Mr. Driller 2 / G(Namco System 10)의 입력·드릴 판정 구조를
알아내고, "착지 동기" 연사를 GroovyMAME에 만든 뒤 MiSTer FPGA 코어로 옮긴 과정을 기록한다.

- 대상 독자: 이 게임을 처음 보는 개발자나 AI. 이 문서만 보고 같은 조사를 재현하거나 다른 에뮬레이터/코어에 옮길 수 있게 쓴다.
- 기준 환경: **GroovyMAME** (`D:\github_clones\GroovyMAME`, 브랜치 `autofirefix`, 커밋 `2a226d2c064`).
  다른 MAME 변종(0.28x 계열)도 Lua 콘솔과 디버거가 같으므로 거의 그대로 쓸 수 있다.
- FPGA 쪽: 이 저장소 `main` (`39d0b4b`). 작업 일지는 `docs/fixes-2026-10-24.md`, 이전 연사 기록은 `docs/rapid-fire-irq.md`.

## 1. 문제

사용자 보고 (MiSTer 코어와 GroovyMAME 모두, 2xVBlank IRQ10 + 30/s Drill (Auto) 상태):

- Drill (Auto)를 누르고 있으면 손으로 리듬 있게 연타할 때보다 일반 블록을 느리게 판다.
- X 블록(5번 쳐야 깨지는 블록)은 30연사 그대로 빠르다.
- 북극 스테이지 1700 m 근처처럼 낙하 속도가 바뀌는 곳에서는 갑자기 아주 빨라지기도 한다.
- 사용자 추정: "착지 순간에 바로 파야 하는데 타이밍이 딱 맞아서 다음 프레임에 파진다. 1틱 늦추면 좋을 것 같다."

사용자는 "기분 탓일 수도 있다"고도 했다. 그래서 체감이 아니라 **게임 코드가 실제로 무엇을 보는지**를 측정하는 것부터 시작했다.

---

## 2. 가설

1. **사용자 가설:** 연사 위상이 1틱 어긋나 있다 → 1틱 늦추면 해결.
2. **조사 전 세운 가설:** 게임이 "누르고 있음"이 아니라 "새로 누름(에지)"만 받는다면, 판 순간부터 다시 판정 가능해질 때까지의
   프레임 수가 홀수일 때 2프레임 주기(켬/끔) 연사는 항상 "끔" 프레임에 걸린다. 그러면 위상을 바꿔도 짝수일 때 같은 손해가 생기므로
   1틱 지연으로는 해결되지 않는다. 낙하 속도(=프레임 수)가 깊이에 따라 바뀐다는 사용자 관찰과도 맞는다.
3. X 블록은 착지 없이 그 자리에서 연속으로 치므로 홀짝 문제가 없을 것이다.

검증해야 할 것: (a) 드릴 판정이 에지인가 레벨인가, (b) 판정이 언제 가능해지는가(착지, 쿨다운), (c) 패턴별 실제 프레임 수.

## 3. 조사 과정 (GroovyMAME 기준, 재현 가능한 순서)

### 3.1 준비: 헤드리스 MAME와 복사본

- 실행 파일: GroovyMAME `namcos10.exe` (빌드: MSYS2 UCRT64에서
  `make SUBTARGET=namcos10 SOURCES=src/mame/namco/namcos10.cpp,src/mame/namco/namcos12.cpp REGENIE=1 -j16`).
- **사용자 NVRAM, cfg, 세이브스테이트는 절대 직접 쓰지 않는다.** 실행마다 scratch 폴더에 복사해서
  `-nvram_directory`, `-cfg_directory`, `-state_directory`, `-snapshot_directory`를 그 복사본으로 준다.
- 공통 옵션: `-nothrottle -video none -sound none -skip_gameinfo -noplugins -autoboot_script <lua>`
  (`-noplugins`: autofire 플러그인 등이 입력을 건드리지 않게. `timeout 900`으로 15분 제한.)
- 화면 확인이 필요하면 Lua에서 `manager.machine.video:snapshot()`을 찍고 PNG를 본다(메뉴 위치, 게임 시작 시각 확인).

### 3.2 입력 넣기: 부팅부터 게임 시작까지 스크립트로

두 가지 방법을 썼다.

1. **IN1 읽기 탭으로 비트 지우기** (가장 확실): `install_read_tap(0x1fba0004, 0x1fba0007, ...)`에서 돌려줄 값을
   `d & ~mask`로 바꾼다(입력은 active low). IN1 비트(MAME `INPUT_PORTS_START(mrdrilr2)`):
   P1 우/좌/하/상 = 0x1/0x2/0x4/0x8, **P1 Button1(드릴) = 0x10**, P2 = 각 `<< 8`(P2 드릴 0x1000), 코인 0x20000000, 1P 스타트 0x80.
   - Driller 2 1P 예: `10~10.3 s 코인, 12 s 스타트, 14/16/18/20 s 드릴(메뉴 결정)` → 약 41 s부터 실제 조작 가능.
   - 대전: 코인 2개(10, 11 s), 스타트, `15 s 아래(2P PLAY)`, `16 s 결정`.
2. **ioport 필드 값 설정**: `manager.machine.ioport.ports`에서 이름으로 필드를 찾아 `field:set_value(1)`
   (드라이버에 추가한 "P1 Drill (Auto)" 키를 누를 때 사용).

Driller G는 사용자가 저장한 세이브스테이트(`-state 1`, 북극 183 m)를 복사해서 쓰면 바로 게임 중에서 시작할 수 있어 편했다.

### 3.3 코드 보기: RAM 덤프 + MIPS 디스어셈블

NS10은 롬이 암호화/압축되어 있어 롬 파일을 직접 디스어셈블하기 어렵다. 대신 **게임이 RAM에 풀어 놓은 코드**를 본다.

```lua
-- 30 s에 메인 RAM 4 MB 덤프 (kseg0 주소로 읽음)
dr = {}
dr.n = emu.add_machine_frame_notifier(function()
  if emu.time() >= 30 and not dr.done then
    dr.done = true
    local sp = manager.machine.devices[":maincpu"].spaces["program"]
    local f = io.open(os.getenv("NS10_DUMP"), "wb")
    f:write(sp:read_range(0x80000000, 0x803fffff, 8)); f:close()
    manager.machine:exit()
  end
end)
```

- 덤프를 아무 MIPS R3000(리틀 엔디언) 디스어셈블러로 푼다. 우리는 작은 파이썬 디스어셈블러로
  `80010000~803F0000`을 한 줄에 한 명령(`801327C8: lhu $v0, 0x7310($v0)`) 형식의 텍스트로 만들어 grep/awk로 검색했다.
  MAME 디버거의 `dasm` 명령을 써도 된다.
- 텍스트로 만들어 두면 "이 주소에 쓰는 코드"(`sw ..., -0x1980(`), "이 패턴"(`xor`+`and` = 에지 계산) 같은 검색이 쉽다.

### 3.4 가장 중요한 도구: "누가 이 주소를 읽나" 집계

어떤 변수의 의미를 모를 때, 그 변수를 **어느 코드(PC)가 얼마나 자주 읽는지**를 세면 구조가 드러난다.

```lua
pr.seen = {}
pr.sp:install_read_tap(0x8023F900, 0x8023F9FF, "pad_r", function(o, d, m)
  local k = string.format("%08X %08X", pr.pc.value, o)   -- (PC, 주소)
  pr.seen[k] = (pr.seen[k] or 0) + 1
end)
-- 끝날 때 pr.seen을 파일로 덤프
```

- `pr.pc = manager.machine.devices[":maincpu"].state["GENPC"]`.
- 몇 초 동안 모은 뒤 "횟수 = 프레임 수"인 항목은 매 프레임 실행되는 코드, 적은 횟수는 특정 사건(드릴, 착지)에서만 도는 코드다.
- **함정 2개 (중요):**
  1. 부팅 직후 설치한 RAM 탭은 BIOS/게임이 RAM 매핑을 다시 설치하면서 사라진다. → **게임 중(측정 시작 0.5 s 전)에 frame notifier 안에서 설치.**
  2. 물리 주소(0x0023F900)로 건 탭은 안 걸렸다. → **kseg0 주소(0x8023F900)로 설치.** (CPU가 쓰는 가상 주소 기준)
  3. Lua 지역 변수에만 탭 핸들을 두면 가비지 컬렉션으로 탭이 사라진다 → 전역 테이블에 보관.

### 3.5 따라간 순서 (Driller 2, mrdrilr2j)

1. **IN1을 누가 읽나:** 이전 작업(`docs/rapid-fire-irq.md`)에서 IRQ10 핸들러(입력 라이브러리 0x8016CEB4)가 IN1을 읽고
   두 번 중 한 번만 저장, 매 프레임 vblank 뒤 패드 구조체로 복사한다는 것을 알고 있었다. 게임용 패드 값은 `0x8023F94E`.
2. **패드 구조체를 누가 읽나:** 0x8023F900~9FF 탭 → 매 프레임 `0x80162010~0x80162088`이 읽음 = **패드 함수 0x80161FE0**.
   디스어셈블해 보니 플레이어마다 cur/prev/edge(`cur & (cur ^ prev)`)/repeat를 계산한다.
   구조체: P1 `0x8023F948`, 간격 0x10, `+6 cur, +8 edge, +A repeat, +C prev`. IN1 bit 4(드릴) → 패드 0x200.
3. **실제 게임 중에** 다시 모으자(스크린샷으로 게임 시작 시각 확인 후 36~42 s) `0x80133B94`가 새로 나타남.
   그 코드는 패드 값을 게임용 전역 변수로 복사한다: **edge `0x80227310`, held `0x80227312`, repeat `0x80227314`**.
   (모드 값 `0x80271690`이 0xe 이상, 즉 데모일 때는 다른 경로)
4. **전역 변수를 누가 읽나:** 0x80227300~1F 탭 → `0x801327C8`(15회), `0x801323E4` 등 →
   `0x801327C8` 주변 디스어셈블:

```
801327A4: lw   $a3, -0x1980($v0)    ; a3 = 현재 플레이어 구조체 포인터 (*0x8023E680)
801327AC: lbu  $v0, 1($a3)          ; 쿨다운 바이트 (구조체 +1)
801327B4: beqz $v0, 801327C4
801327B8: addiu $v0, $v0, -1
801327BC: j    801329BC             ; 쿨다운 중: 1 줄이고 판정 건너뜀
801327C0: sb   $v0, 1($a3)
801327C8: lhu  $v0, 0x7310($v0)     ; edge
801327D0: and  $v0, $v0, $a1        ; & 0x200 (드릴)
801327D4: beqz $v0, 801329BC        ; 새 누름이 없으면 아무 일도 없음
```

   → **드릴 판정은 에지만 본다. 쿨다운이 0일 때만.** 이 코드는 플레이어 상태(구조체 `+0xA4`)가 1(서 있음)일 때만 돌고
   2(낙하 중)일 때는 돌지 않는다(트레이스로 확인).

### 3.6 프레임별 트레이스로 측정

frame notifier에서 매 프레임 `cur, edge, 구조체 포인터, +1(쿨다운), +A4(상태)`를 기록하고, `0x80227310` 읽기 탭에서
`PC == 0x801327C8`일 때(=판정이 실제로 실행된 프레임) "CHK"를 기록했다. 입력은 IN1 탭에서 패턴("10" = 켬/끔, "100" = 켬/끔/끔 …)으로 넣었다.
같은 장면에서 패턴만 바꿔 착지→다음 낙하 프레임 수를 셌다.

| 패턴 (Driller 2) | 착지 → 다음 낙하 | 블록당 |
|---|---|---|
| 10 (30/s) | 항상 8 | 16 |
| 01 (30/s, 1틱 늦춤) | 항상 8 | 16 (변화 없음) |
| 100 (20/s) | 대부분 7 | 15 (최소) |
| 예전 100 Hz IRQ10의 25/s | 7, 8, 9 섞임 | 평균 비슷 |

**가설 2 확인.** 1틱 지연은 효과가 없다. 이 장면에서는 판 순간부터 다음 판정 가능 프레임까지가 홀수라서
30/s는 착지 프레임이 늘 "끔"이다. 낙하 속도가 바뀌어 짝수가 되는 구간(사용자가 말한 북극 1700 m)에서는 반대로 손해가 없다.

### 3.7 Driller G로 옮기기: 코드 시그니처

주소는 다르지만 같은 회사의 같은 라이브러리 계열이라 **명령 패턴**으로 찾을 수 있다.

- 에지 계산 패턴 `xor $v1,$v0,$v1` → `and $v0,$v0,$v1`를 drg.asm에서 검색 → **패드 함수 0x80242A08**, 구조체 `0x80337DF0`.
- 세이브스테이트에서 0x80337DF0 근처 읽기 집계 → 게임용 복사 `0x801F8934` → 전역 **edge `0x8031B7E0`**(held +2, repeat +4).
- 전역 읽기 집계 → `0x801F6CD4` = Driller 2와 **똑같은 구조의 드릴 판정**(쿨다운 +1, 플레이어 포인터 `*0x80336B08`). 상태 오프셋만 `+0xD8`.
- 측정(세이브스테이트 183 m, 3.5 s): 30/s 두 위상 모두 13번 착지 중 4번만 착지 프레임에 판정, 나머지는 1프레임 손해.

### 3.8 플레이어 구조체, 대전, 1P의 P2쪽

연사를 플레이어별로 하려면 "P1/P2 버튼이 어느 구조체를 움직이는가"를 알아야 한다.

- `sw ..., -0x1980(`(= 현재 플레이어 포인터 0x8023E680에 쓰기)를 검색 → 구조체 배열 `0x80271698`, 간격 **0x180**
  (`index*3 << 7`). Driller G는 `0x80369B40`, 간격 **0x1B4**.
- 포인터를 정하는 코드를 읽어 보니:
  - **대전 모드**(모드 워드 Driller 2 `0x80271690` = 0x0A, Driller G `0x80369B38` = 0x0A Survival / 0x12 Race)는 구조체 n = 플레이어 n.
  - **1P 게임**은 구조체 0 하나만 쓰고, 어느 쪽 패드로 조작하는지는 **side 플래그**(s16, Driller 2 `0x8020AD0C`, G `0x802EF0E4`)가 정한다.
- 메뉴 화면 위치는 스냅샷 몇 장을 이어 붙인 contact sheet로 확인했다("2P PLAY"는 아래 + 결정).

### 3.9 지역판 비교

Driller 2 World/Japan/US의 RAM 덤프를 비교: 패드 함수, 복사, 드릴 판정, 포인터 선택 코드가 같은 주소에서 완전히 같고,
0x80010000~0x80200000에서 다른 워드는 25~32개(문자열)뿐. → **Driller 2는 주소표 하나, Driller G는 하나.**

### 3.10 덤: Driller G 테스트 모드 "DRILL CON SPD"

사용자가 "숨겨진 자동 파기 기능이 아닐까?" 물었다. Driller G 패드 함수 안에 `cur |= 0x200; prev &= ~0x200`(강제 에지) 코드가 있었다.

- 간격: 설정 바이트 `0x803C58B5` → 표 `0x802A4A20` = [0, 10, 20, … 70] 프레임.
- 설정 `0x803C58B4 != 0`일 때만 켜지고, 이 값은 버튼 배치도 바꾼다. Button4/5(IN1 0x20000/0x40000 → 패드 0x40/0x20)에 걸린다.
- 메모리를 써서 켜 보니 최소 10프레임 간격(6회/s)이라 느리다. 표를 1로 고치면 결과가 우리 해결책과 **완전히 같았다**(14/14).
- G 전용이고 게임 설정을 바꿔야 해서 쓰지 않았지만, "착지 프레임에 새 에지를 주면 된다"는 결론의 좋은 확인이 되었다.

### 3.11 어느 IRQ10 읽기가 저장되나, P2는 언제 갱신되나

대전에서 P1은 착지 프레임 파기 91/92인데 **P2는 0/88**이었다. 원인 조사:

- vblank 뒤 첫 번째 IN1 읽기에만 드릴을 넣어 보니 게임이 봄, 두 번째에만 넣으니 안 봄 → **프레임의 첫 IRQ10(1/4 프레임 ≈ 4.2 ms) 읽기가 저장된다.**
- 프레임 시작(GP1(05)) 뒤 드릴 판정 시각: P1(구조체 0) 0.18 ms, **P2(구조체 1) 3.3~6.5 ms** (중앙값 5.1 ms).
- 즉 P2의 착지가 RAM에 기록되기 전에 입력이 읽혀서, P2는 항상 한 프레임 늦은 상태를 보고 있었다.
- 해결: Driller 세트만 IRQ10을 **5/8, 7/8 프레임**으로 옮김(저장되는 읽기 ≈ 10.4 ms). 두 플레이어 갱신 뒤이고, 입력 지연도 약 6 ms 준다.

## 5. 구현 (GroovyMAME, `src/mame/namco/namcos10.cpp`)

플레이어 p마다, IN1을 읽을 때:

```cpp
// 게임이 이미 눌림으로 봤으면 뗀다 (다음에 새 에지를 만들려고)
if (rd16(g.cur[player]) & 0x0200) return false;
// p의 구조체: 대전 = 구조체 p, 1P = side가 p쪽이면 구조체 0, 아니면 게임에 없음 → 단순 켬/끔
...
const s32 state = rd32(p + g.state);
return !(state == 2 || (state == 1 && ram[(p + 1) & mask] != 0));   // 낙하 중, 쿨다운 중이면 뗌
```

- 결과: 서 있는 동안은 프레임마다 켬/끔(30/s, X 블록 그대로), 낙하/쿨다운 동안은 떼고, **판정 가능한 첫 프레임에 반드시 새 에지**.
- `in1_r`에서 Drill (Auto) 키가 눌린 플레이어만 Button1 비트를 지운다. 다른 게임에는 `m_drill_game`이 없어 영향 없음.
- IRQ10: `m_io_vbl2_timer[0]->adjust(period * 5 / 8)`, `[1]->adjust(period * 7 / 8)` (Driller 세트만).
- 게임 데이터는 `m_ram->pointer()`로 직접 읽는다(물리 주소 & (크기-1)).
- 이전 커밋의 저장 항목(`m_drill_act/fire/cnt`)은 쓰지 않지만 **save_item 등록을 남겨 둠** → 사용자의 기존 .sta가 그대로 열림.
- 재현 스크립트: GroovyMAME `docs/ns10_autofire_tests/drill_landing.lua`(같은 알고리즘의 Lua 참조 모델, `SM_MODE=smart|alt|port`),
  `run_drill_landing.sh`, `drill_landing_an.py`. 설명: `docs/NS10_DRILL_AUTO_LANDING_20261024.md`.

**왜 "프레임 패턴"이 아니라 "게임이 본 값"을 기준으로 했나:** 프레임 수, 처리 지연(프레임 드롭), CPU 속도, IRQ10 모드와 무관하게
"게임이 눌림을 봤으면 떼고, 판정 가능하면 누른다"는 규칙 하나로 끝난다. 낙하 속도표를 찾아 레벨마다 위상을 바꾸는 방법(사용자가 제안한 대안)보다
찾아야 할 주소가 적고 캐릭터/스테이지/모드에 상관없다.

## 8. MiSTer FPGA 코어로 옮기기

### 8.1 가장 큰 차이: FPGA 로직은 게임 RAM을 "읽을" 수 없다

MAME는 `m_ram->pointer()`로 언제든 RAM을 읽는다. FPGA 코어에서 PSX 메인 RAM은 **외부 SDRAM**에 있고, SDRAM 포트는 CPU/DMA가 쓴다.
연사 로직이 따로 SDRAM을 읽으려면 중재기를 고쳐야 하고 CPU 타이밍에 영향을 준다. 그래서 다른 방법이 필요했다.

**가설:** 필요한 값은 8개 워드뿐이고(패드 cur P1/P2, 모드, side, 상태 0/1, 쿨다운 워드 0/1), 게임이 이 값들을
**매 프레임 스스로 읽거나 쓴다**. 그렇다면 CPU↔SDRAM 버스를 **엿보기만** 해서(쓰기 데이터와 읽기 결과) 8개의 그림자 레지스터를 유지하면
항상 최신 값을 갖게 된다. SDRAM 접근을 추가하지 않으므로 코어 타이밍에 영향이 없다.

**가설 검증 (MAME에서 먼저):** GroovyMAME에서 8개 워드에 읽기/쓰기 탭을 걸어 게임 중 프레임마다 접근 여부를 셌다
(Driller 2 1P/대전, G 세이브스테이트, G Race).

| 워드 | 결과 |
|---|---|
| 패드 cur, 모드 | 게임 중 거의 매 프레임 |
| side | 1P 모드에서 매 프레임 (대전에서는 거의 안 읽지만 대전에서는 안 씀) |
| 상태 0/1 | 그 구조체가 쓰이는 모드에서 매 프레임 |
| 쿨다운 워드 | 서 있는 프레임마다 판정 직전에 읽음 (필요한 순간에는 항상 최신) |

→ 가설 성립. 세이브스테이트를 불러와 그림자가 틀려도 1프레임 안에 다시 맞는다.

### 8.2 이식하면서 부딪힌 문제와 결정

1. **어느 신호를 엿볼까.** `memorymux`(CPU 쪽)보다 `psx_top`에서 CPU/DMA가 합쳐진 뒤 SDRAM 컨트롤러로 가는 채널
   (`sdram_req/rnw/dma/cache/addr/be`, `sdr_sdram_din`, `sdram_readack`, `sdr_sdram_dout32`)을 골랐다. `NAMCOS10.sv`에 이미 있는 와이어라
   PSX 코어(VHDL)를 고칠 필요가 없었다.
2. **걸러야 할 접근.** DMA(`ram_dma=1`)와 i-cache 라인 읽기(`ram_cache=1`)는 무시. CPU 데이터 읽기는 `ram_cache=0`. 쓰기는 `ram_be` 바이트 마스크를 적용
   (패드 cur는 16비트 저장이라 워드의 상위 절반만 바뀜, 쿨다운은 바이트 저장).
3. **읽기 데이터 타이밍.** SDRAM 컨트롤러 코드를 확인: `ch1_ready`와 `ch1_dout32`가 같은 `clk_base` 에지에 래치되고 ready는 1클럭 펄스.
   CPU 요청은 한 번에 하나라서 요청 때 주소를 기억해 두고 ready에 데이터를 받으면 된다.
4. **주소.** 게임은 kseg0(0x80xxxxxx) 주소를 쓰고 SDRAM 버스는 물리 바이트 주소(4 MB 미러, `[24:23]=00`이 메인 RAM). 표는 물리 워드 주소로 저장
   (`0x8023F94E` → 워드 `0x23F94C`의 비트 31:16, 드릴 = 비트 25).
5. **게임 구분.** MRA 설정의 Driller 플래그(`af_b2`, 이미 있음) + 보드 종류(MEM(M) = Driller 2, MEM(N) = Driller G). 새 설정 비트가 필요 없었다.
6. **IRQ10 위치.** `ns10_io.sv`에 `irq10_late` 입력: 1이면 5/8, 7/8 프레임(직전 프레임 길이 기준). Driller 세트만 켬.
7. **세이브스테이트.** 그림자 레지스터는 저장하지 않는다(8.1 검증대로 1프레임 안에 복구).
8. **빌드가 20분.** 실기에서 이상하면 다시 빌드하지 않고 원인을 볼 수 있게 디버그 트레이스(OSD "Trace GPU 10 s")에
   Drill (Auto) 상태(그림자 값, fire, 버튼)를 변경 시마다 기록하는 항목을 같이 넣었다(`tools/gputrace.py drill`).

### 8.3 시뮬레이션으로 먼저 확인 (빌드 전)

`sim/ns10/tb_autofire.sv` (ModelSim, `run_autofire.sh`): `ns10_io` + `ns10_autofire` + **RAM 버스 위의 Driller 게임 모델**.

- 모델: IRQ10 ISR가 IN1을 읽고 한 번 걸러 저장, vblank 뒤 패드 복사(패드 워드 16비트 쓰기), P1 갱신, P2 갱신(프레임의 20~39 %),

  시뮬 시간 제한, vblank 워치독, 15분 실행 제한.

시뮬레이션 시행착오 (모두 테스트벤치 쪽 문제였다):

| 증상 | 원인 | 해결 |

## 9. 다른 개발자/AI를 위한 빠른 길잡이

이 게임(또는 비슷한 PSX 기반 아케이드 게임)을 처음 볼 때 가장 빨리 구조를 잡는 순서:

1. **입력 레지스터에서 시작한다.** 드라이버 소스에서 IN 포트 주소와 비트를 확인하고, 읽기 탭으로 "누가(PC) 언제 읽나"를 본다.
2. **값이 흘러가는 RAM을 한 단계씩 따라간다.** "(PC, 주소) 읽기 횟수" 집계 → 횟수가 프레임 수인 곳 = 매 프레임 처리, 적은 곳 = 사건 처리.
   그 PC 주변을 디스어셈블해 다음 변수를 찾고 반복한다. 우리는 IN1 → 패드 구조체 → 게임용 전역 → 드릴 판정까지 4단계였다.
3. **판정 코드를 찾으면 조건을 읽는다.** 에지/레벨, 쿨다운, 상태 조건. 여기서 문제의 본질이 보인다.
4. **가설은 측정으로 확인한다.** 프레임별 트레이스 + 입력 패턴만 바꾼 반복 실행. 체감이 아니라 "착지→다음 낙하 프레임 수" 같은 숫자로.
5. **두 번째 게임/지역판은 시그니처로.** 명령 패턴(예: `xor` 다음 `and` = 에지)으로 함수를 찾고, RAM 덤프 비교로 지역판 차이를 확인.
6. **플레이어별 데이터는 "포인터에 쓰는 코드"로.** 현재 플레이어 포인터에 저장하는 `sw`를 찾으면 구조체 배열과 간격, 모드별 배정이 나온다.
7. **타이밍 경합을 의심한다.** 같은 로직이 한 플레이어에만 안 먹으면 "입력이 저장되는 시각"과 "그 플레이어 갱신 시각"을 둘 다 잰다.

MAME Lua 체크리스트:
- 탭은 게임 중에, kseg0 주소로, 전역 테이블에 보관.
- `emu.add_machine_frame_notifier`로 매 프레임 기록, `emu.time()`으로 구간 제어, 끝나면 `manager.machine:exit()`.
- `cpu.state["GENPC"].value`로 PC, `screen:frame_number()`로 프레임 번호, `scr.vpos`는 속성.
- 사용자 파일(NVRAM/cfg/sta)은 항상 복사본, `-noplugins`, `timeout 900`.

FPGA로 옮길 때 체크리스트:
- 필요한 게임 값이 몇 개인가, 게임이 그 값을 매 프레임 읽고 쓰는가(MAME 탭으로 먼저 확인) → 그렇다면 버스 엿보기 + 그림자 레지스터.
- CPU 데이터 접근만(DMA, 명령 캐시 제외), 바이트 마스크, 읽기 데이터가 유효한 클럭, 가상→물리 주소, 메모리 미러.
- 게임 구분은 기존 설정(MRA, 보드 종류)으로 할 수 있는지 먼저 본다.
- RAM 버스 위의 게임 모델로 시뮬레이션하고, 실기용 트레이스를 같은 빌드에 넣어 둔다.
