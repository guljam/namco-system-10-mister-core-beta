## 2. 사용자 목표와 이번 세션의 지시

목표(순서대로): 1 노미스 클리어, 2 퍼펙트 에어(타임어택은 더 빠르게, 우주는 더 깊게), 3 더 빠르게, 4 최고 점수. 실시간 성능 유지.

사용자가 이번 세션에서 분명히 한 것:
- AI는 보이는 패턴을 메모리에서 읽어 직접 판단해야 한다. **확률이나 타이머 휴리스틱을 쓰지 말 것.** 보이는 칸은 15열이면 세로 약 20칸, 9열이면 약 10칸(사용자 추정).
- 사람은 전체 패턴을 다 읽지 않는다. 같은 색 지붕이 생기는지와 부분 패턴을 보고 빠르게 판다. **연쇄는 예측하지 않고**, 일어난 뒤나 아주 짧은 미래만 보고 판단한다.
- 행동 비율은 핵심이 아니다. **실시간으로 패턴을 어떻게 대처해 클리어하는지**를 .inp에서 뽑아야 한다.
- .inp의 대기는 사람의 사고 시간이다. 일부 녹화는 X에 둘러싸인 캡슐을 보여 주려고 일부러 천천히 했다. 대기 길이 통계를 행동으로 해석하면 안 된다.

## 3. 이번 세션의 핵심 발견

### 3-1. 사람과 AI의 진짜 격차 (아메리카 1000 m)
| | 사용자 녹화 4판 | 기존 AI |
|---|---|---|
| 캡슐 | 79~80 / 80 | 약 57 / 80 |
| X 부수기/판 | 0~2 | 약 17 |
| 사망/판 | 0~2 | 약 1.8 (시뮬) |
| 프레임 | 약 24,000~25,000 | 약 16,900 |

| 아래와 양옆이 막힌 착지 | 0.11 % | 0.61 % |

X 회피 자체는 격차의 주원인이 아니다. 사람은 **시간을 더 써서 캡슐을 끝까지 먹는다**.

캡슐 2줄 위에 왔을 때의 상황별 비교(`diag/capep.h`, 사람은 4판 265개, AI는 24맵 1834개):

|---|---|---|---|
| 열림, 옆으로 0~1칸 | 100 % | 94.5 % | 33 f |
| 열림, 2~3칸 | 98.5 % | 71.7 % | 73 f |
| 열림, 4칸 이상 | 100 % | 37.2 % | 155 f |
| X에 막힘, 0~1칸 | 100 % | 81.7 % | 267 f |

### 3-2. 기존 AI가 캡슐을 놓친 이유 (12맵, 놓친 250개)
| 정밀 확인 결과 | 개수 |

"먹지 못함"의 대표 장면(프레임 추적으로 확인): 옆으로 파 들어가 캡슐 바로 옆 칸에 도착했는데, 그 칸의 블록이 아래 칸과 같은 색이라 함께 사라져 바닥이 꺼진다. 떨어지는 순간 경로를 못 찾아 캡슐 목표를 버린다. **얼어붙은 격자 경로 탐색이 "같은 색은 함께 사라진다"를 몰랐다.**

## 4. 코드 변경 (모두 환경변수로 켬, 기본은 기존 동작)

`tools/drgai/rtai/agent.c`:
| 파라미터 | 기본 | 내용 |
|---|---|---|
| `RT_GFLOOR` | 0 | 파낼 블록이 바로 아래 칸과 같은 색이면 함께 사라지므로 서 있을 수 없는 칸으로 처리(`standable`). **단일 수정 중 효과 최대** |
| `RT_LEAVE` | 0 | 시작 때 보이던 캡슐을 먹지 않고 닿을 수 없게 두면 프레임 벌점 |
| `RT_KEEPGOAL` | 0 | 낙하 중 캡슐 경로가 없어도 목표를 버리지 않고 착지 후 재탐색 |
| `RT_GCOST` | 0 | 같은 색 덩어리는 한 번만 파면 된다고 경로 비용 계산(`same_group`) |
| `RT_STALL` | 150 | 깊이가 늘지 않아도 시뮬을 계속하는 프레임. 옆으로 파기는 칸당 약 31프레임(타이조 외)이라 150이면 5칸에서 잘린다 |
| `RT_REROUTE` | 10 | 시뮬당 경로 재탐색 횟수 (효과 없음) |
| `RT_CAPFIRST` | 0 | 캡슐 후보를 먼저 검증 (효과 없음) |

`RT_REROUTE`, `RT_CAPFIRST`는 효과가 없었으니 채택 시 제거를 검토할 것.

`game.c/h`: 맵 파일의 target으로 스테이지 판별(500 인도 W7, 1000 아메리카 W9). 아메리카 시작 패턴, 레벨 표, 값 19 = 화이트, `GAME_WALK` 추가. 인도 결과는 수정 전과 같음을 2맵으로 확인.
- 아메리카 레벨 표는 사용자 녹화 h10에서 실측했다. 산소 소모(33, 38, 40, 50)는 그 캐릭터 기준이라 캐릭터마다 다를 수 있다.

`run.c`: `RUN_LAND=1`이면 LAND 줄(착지 통계)과 K 줄(캡슐 에피소드) 출력.

새 도구 `rtai/diag/`:

## 6. 계속한다면 다음 작업

1. **X를 안 부수고 막힌 캡슐 열기.** 사람은 막힌 캡슐에 200~400프레임을 쓰며 X를 거의 안 부순다. `capep.h` 에피소드에서 그 구간의 실제 행동(파기 위치, 대기, 연쇄 시점)을 뽑아 후보로 만든다. 사용자 말대로 연쇄를 길게 예측하지 말고, 짧은 미래만 정확히 계산할 것. 기존 RT_XTALL은 켜도 효과가 작았다(XPEN 기본에서 71.54 → 72.08).
2. **800 m 이후 사망.** 대부분 이 구간이고 c5는 산소 사망이 많다. 산소 표는 `handoff-2026-11-06.md` 단계 1 참고.
3. **캐릭터 1의 압사.** MAME에서 판당 약 2회, 시뮬 평균은 약 0.46회. 0~200 m에서도 죽는다(c5는 0건). 원인 미조사. 캐릭터별 차이를 시뮬에 반영할 것(CLAUDE.md: 실기와 시뮬 차이를 시뮬에 반영).
4. **시뮬에 목숨 제한 반영.** 시뮬은 죽어도 계속되지만 MAME는 게임 오버가 있어 클리어 수가 다르다.
5. **MiSTer 확인.** 아직 시험 안 함. RT_LEAVE는 평가마다 Dijkstra를 한 번 더 돌리고 RT_XTALL도 켜므로, ARM 시간을 재야 한다. PC에서 안 늘었다고 ARM도 괜찮다고 단정하지 말 것.
6. **남은 캡슐.** P 설정에서 놓친 149개(12맵)의 분류: 먹지 못함 80, 점수에서 짐 21, 후보 없음 24, 선택 후 실패 18, 항상 죽음 6. 약 절반이 X에 안 막힌 캡슐이다. (이 수치는 RT_XTALL, RT_GFLOOR 적용 전 `RT_STALL=300 RT_LEAVE=2500` 기준이다. 다시 잴 것.)

### 실시간 MAME (최종 시험)
- 실행: `D:/scratch_drgai/mev/capfix.sh`(세트당 12판, 숨김, 9세트 약 10분), 집계: `cd mev; python capsum.py`. 결과 `mev/ev/`.
- 이름은 `namcos10ai_capfix.exe` 기준이다.

**빌드 순서 (순서를 지킬 것):**
1. `rtai/agent.c`를 `GroovyMAME/src/mame/namco/drgai/`로 복사.
2. `namcos10.exe` 백업.
3. `namcos10.cpp` **2387번 줄**을 `m_drgai_game = true;`로 변경.
   사용자 작업 트리는 AI 끈 빌드용으로 `false`다. `false`로 빌드하면 AI가 움직이지 않아 모든 판이 depth=0으로 똑같이 나온다.
   `sed`로 파일 전체를 바꾸지 말 것. 767번 줄 선언도 `= false`라 같이 바뀐다.
4. 빌드:
   ```
   OS=Windows_NT MSYSTEM=UCRT64 /c/msys64/usr/bin/bash -lc 'export OS=Windows_NT MINGW64=/ucrt64; cd /d/github_clones/GroovyMAME && make SUBTARGET=namcos10 SOURCES=src/mame/namco/namcos10.cpp,src/mame/namco/namcos12.cpp,src/mame/namco/ns10_drgai.cpp -j16'
   ```
   Git Bash에서 바로 make를 부르면 OS 판별에서 실패한다.
5. `namcos10.exe`를 시험용 이름으로 복사하고, 사용자 exe를 백업에서 복원.
6. 2387번 줄을 다시 `false`로 복원.

### 함정
- **Git Bash에는 `pkill`이 없다.** 시험을 멈추려면 PowerShell에서 명령줄로 찾아 종료한다(`Get-CimInstance Win32_Process`에서 `capfix.sh|evalrt.sh|namcos10ai_capfix` 매치 후 `Stop-Process`). 안 그러면 스크립트가 MAME를 계속 새로 띄우고 실행 파일이 잠겨 복사가 실패한다.
- 시험 스크립트가 쓰는 결과 파일을 다른 명령에서 지우면 앞부분 출력이 사라진다. 원본은 `mev/ev/*.txt`.
- 첫 세트 결과가 12판 모두 똑같으면 AI가 꺼진 빌드다.
- `\n`이나 백슬래시가 든 코드는 Bash heredoc 대신 Write/Edit로 쓴다.
- 실행 중인 exe는 덮어쓸 수 없으니 새 이름으로 빌드한다.

## 9. 지켜야 할 규칙

- 커밋, 푸시는 요청 시에만. 릴리스 빌드는 승인 후에만.
- 시뮬레이션은 15분 제한 + 워치독.
- MAME 시험은 숨김(`hidrun.exe`), 최대 12개 동시, `-window -nomaximize -mouseprovider none -lightgunprovider none -joystickprovider none`.
- 난수 조작 금지, 게임은 절대 멈추면 안 됨.
- 여러 캐릭터로 시험(타이조만으로 판단 금지). GroovyMAME 먼저, 그다음 MiSTer.
- 판정은 실시간 MAME 기준. 시뮬 이득이 실시간에서 사라진 적이 있다.
- 용어: "시뮬레이션 테스트" = 독립 게임 시뮬, "MAME 테스트" = 최종 시험.
- 추측을 파라미터로 맞추지 말고, 사람과 AI를 **같은 기준으로 재서** 원인을 찾을 것. 이번 개선은 그렇게 찾았다.
- 사용자에게는 한국어로, 쉽게, 나쁜 결과도 그대로 보고한다.
