# 2026-11-02 — Driller G real-time AI (tools/drgai/rtai)

## Problem (cause)
The previous Driller G AI (tools/drgai/planner, beam search) needed ~50,000 simulated frames per
decision (~350 ms on one PC core). On the MiSTer ARM (Cortex-A9, measured ~37x slower than one PC
core) that is far above the 16.6 ms frame budget, so it could not play in real time.
It did **not** read the whole stage: it only saw the 32-row RAM grid window (the same view the
game keeps). The cost came from the search method, not from the amount of data.

## Hypothesis
A decision does not need to try every input sequence. A few sensible goals ("eat this capsule",
"go down this column", "dig the cell under the X ring, step aside, wait, eat from the side") can be
proposed by a cheap route search, and only those few are checked with the exact game simulation.
That makes the AI 10-20x cheaper, so it fits the ARM.

## What was done
New folder `tools/drgai/rtai` (stand-alone C, no OpenMP, builds for PC and ARM):

| File | Role |
|------|------|
| game.c/h | stand-alone game (map file -> playable game, events: capsule, X break, death, goal) |
| psim.c/h, blocksim.c/h | player + block physics, copied from planner/ and made faster: block support is only recomputed when something changed (dirty flag), ~2.9x faster |
| ref.c, difftest.c | exactness test: new physics vs planner/ originals, 2.89 M frames, 0 differences |
| agent.c/h | the new AI |
| run.c | plays whole games, prints clears/capsules/deaths/time per frame and the ARM budget estimate |
| bench_sim.c | physics speed benchmark |

AI (agent.c):
1. Decides when the player enters a new cell (also while falling), every 2 cells or when the game
   did something the AI did not predict.
2. Proposes up to 32 goal plans with Dijkstra route costs (capsules, target row, side waits under
   X-enclosed capsules, dig-in-place triggers, the previous plan, the rest of the last verified input
   sequence).
3. Checks each plan with the exact simulation (the same controller that plays for real), scores:
   depth, frames, concave air value, capsules, air-dependent X penalty, capsules still in reach.
4. Plays the recorded inputs of the best plan and checks the real state against the predicted one.
5. Budget: (frames since the last decision) x 180 simulated frames (= what the second ARM core can
   do in that time at 79 us per simulated frame).

## Results (simulation test, 17 maps, India 500 m)
17/17 clears, 46.5 of 56 capsules per game, 0.12 deaths per game, mean 7916 frames.
MiSTer ARM (zig cross-compile `python -m ziglang cc -target arm-linux-musleabihf -mcpu=cortex_a9`):
identical results to PC, 77 us per simulated frame, search uses ~47% of one A9 core on average.

## Not done yet
- The runner still decides synchronously (one decision ~185 ms on ARM); the real-time version must
  search ahead on a second thread while the last verified inputs keep playing.
- GroovyMAME and MiSTer integration.
- Most missed capsules are X-enclosed ones in 300-500 m.

## Build
```
cd tools/drgai/rtai
gcc -O2 -std=gnu99 -Wall -I. -o run.exe run.c agent.c game.c psim.c blocksim.c
./run.exe [-v] maps/*.txt          # map files from the eval map set (tools/drgai)
```
Tuning knobs are environment variables `RT_*` (see `load_params()` in agent.c).

# Driller G AI: real time (pipelined) + GroovyMAME integration + versus player 2

## Goal
Play the main game in real time without lag (a little less intelligence is acceptable), in GroovyMAME
and later on MiSTer. GroovyMAME: from launch, a single player game is played by the AI (user input
ignored on that side); in versus (race / survival) the AI is player 2 as soon as the stage starts,
the user plays player 1. MiSTer: OSD "AI Driller" On/Off (not done yet).

## Real-time pipeline (agent.c)
- Cause of lag in the old runner: one decision took ~185 ms on the ARM and blocked the frame.
- Fix: a decision started at frame f plans from the state predicted at f+L (L = 12 frames, the inputs
  for those frames are already committed). A worker thread searches; the result takes over at f+L.
  If it is late, the old input sequence keeps playing. Budget L x 180 sim frames and a deadline of
  0.75 x L frames. On a big surprise the running job is aborted and a short (L = 4) replan starts.
- RT_THREAD=0 / NS10_AI_THREAD=0: the same pipeline decided inside the frame (deterministic tests).
- Results: simulation 17/17 clears, 0 deaths; MiSTer ARM threaded real time: main thread max 2.1 ms
  per frame, 0 late results.

## GroovyMAME bridge (rtai/drgbridge.c, GroovyMAME branch drgai-rt)
- Reads the same RAM fields the Lua calibration used, builds the World, calls the agent at vblank.
- Input timing: the controls get the output from 1 call before (delay 1, measured against the Lua
  model). Frames where the game skips its logic (play timer P+0x98 stands still) are skipped.
- The face before a fall is remembered (not in RAM) because the fall x-centring depends on it.
- MAME: Machine Configuration "AI Driller" (default On). The AI replaces only its own side's 5 input
  bits; Drill (Auto) stays for the user's side.
- MAME tests use the window mode and no mouse/joystick providers: the earlier hidden runs locked the
  cursor to the top-left of the main monitor.

## Versus (player 2) - cause of the first failures, and the fix
- Entering versus: coin, Start, "select a menu" second item, race or survival, both players pick a
  character (the user's savestate t is just before that; Button 1 = Drill).
- First test: player 2 died 15+ times. Hypothesis: the versus field is laid out differently.
- Measured in MAME (tools/drgai/vsprobe.lua):
  - Both fields share the grid rows: player 1 columns 1..9 (walls 0 and 10), player 2 columns 12..20
    (walls 11 and 21). Player 2 struct = P0 + 0x1B4, its column is in grid columns.
  - Cells are smaller: walk step 576 (P+0x18C), column change at +-3072, fall row at 6144
    (single player: 728 / 5120 / 10240).
  - The player stands in grid row 22 (single player 17); after a landing the grid scrolls ~3 frames
    late (row 21 for those frames). The RAM grid has 32 rows only.
- Fix: Grid.cell (cell size, 0 = 10240) used by the sim instead of the constants; the bridge reads
  player 2 at column offset 11, the rows 5 down (4 during the late scroll), fills the rows below the
  RAM grid with solid blocks that cannot chain, and blanks the other field.
- Result (MAME race from savestate t, player 1 = test script): player 2 reached 500 m first with
  0 deaths, both in-frame and threaded at 100% speed. Prediction misses are still frequent around
  landings (the late scroll is not modelled), which costs some time but not lives.

## Open
- Model the versus late scroll; survival mode not tested yet.
- MiSTer: FPGA RAM mirror to DDR3 + input injection + ARM daemon from user-startup.sh (user agreed).

# Driller G AI on MiSTer: FPGA RAM mirror, ARM daemon, HW fixes (1000 m clear on real HW)

## How it works
- `rtl/ns10/ns10_aimirror.sv` copies the CPU writes and data reads of the RAM the AI reads (grid,
  player structs, mode/target/side words) into DDR3 at 0x39000000 + physical address, through a FIFO
  and a new lowest-priority client `m_` of `ns10_ddram_arb.sv`. At each VBLANK a header word
  `{A1D5, frame, overflows, late, enable}` goes to 0x39400000 through the same FIFO.
- `tools/drgai/rtai/drgaid.c` (ARM daemon, started from `/media/fat/linux/user-startup.sh`) runs the
  same bridge + AI as GroovyMAME on that mirror and writes `{5A1D, frame, active, side, buttons}` to
  0x39400008. The core latches it at the next VBLANK; 8 frames without an answer = the user plays.
- OSD "AI Driller" On/Off (status bit 90). The AI only changes its own side's inputs.
- AI updates need no core rebuild: replace `/media/fat/linux/drgaid` and restart it.

## Problem 1: the AI played very badly on HW, mirror log said "overflows 65535"
- Cause: every row scroll the game copies the whole grid (~15,000 words) in a burst; the 512-entry
  FIFO overflowed and the AI saw broken blocks/capsules.
- Fix: pass only the 5 of 22 cell words the AI reads (word index in the grid -> row/cell/field by
  exact reciprocal multiplies), FIFO 2048, data reads dropped while the FIFO is half full, wrapping
  overflow counter, per-frame stats word at 0x39400010 (`{A1D6, writes, reads, 0, FIFO max}`).
- ModelSim test (scratch tb_aimirror.sv): a back-to-back write of all 15,488 grid words with the DDR3
  30% busy and the ROM cache client active -> 0 overflows, every AI field correct, the others not
  written. HW: 0 overflows, FIFO max fill ~9.

## Problem 2: still bad on HW with 0 overflows (prediction wrong on ~50% of frames)
- Measured: half the frames looked "frozen" (play timer unchanged) and the next one moved 2 frames
  (walk step 1088 = 2 x 544).
- Hypothesis: the daemon read the mirror right after the header while the game was still writing
  this frame's state. Probe (`drgtime`, polls the mirror after each header): the game writes its
  state 1-4 ms after VBLANK (97% done by 4 ms).
- Fix: read 5 ms after the header (`-w`, default 5000 us). That is the same moment GroovyMAME's
  vblank callback sees, so the input delay is 1 as in GroovyMAME (`-d`). Prediction misses
  50% -> 12% (MAME ~9%).

## Problem 3: never took capsules, always "hasty", dug X blocks
- Cause A (biggest): the dug-cell timer depends on the character. Taizou 3 frames, the others 15
  (8:15..8:11, then 9:10..9:1; the player falls through as soon as the cell turns 9). The model had
  only Taizou, and every MAME test script forced Taizou (`run1.sh` set OB_CHAR=4 after the caller's
  settings), so this was never seen in MAME. With 15 the AI thought digging was 4-5x cheaper than it
  is, so going back for a capsule always looked worse than digging on.
  Fix: the bridge measures the timer in the game (largest value seen when a cell turns 8), the route
  cost of a dig = timer + 3, psim falls through state 9 (also at a row boundary). 20-frame prediction
  misses with character 0: 41.6% -> 15%.
- Cause B: plan check order. Each decision checks plans with the exact sim until the budget runs out.
  The target-row plans came first; on open ground they used the whole budget, so the capsule plans
  (including "climb one block to eat the capsule beside you") were never checked.
  Fix: check order = cheapest target plan, capsule / trigger / shaft plans, first-step escapes, the
  other target plans. Unit test (capsule on a one-high step beside the player): 0/8 -> 8/8 eaten.
- Also: walk step measured from the real x steps (two equal steps in a row; follows speed items);
  low-air weighting RT_LOWF 900 -> 2200; X-chain trigger plans (dig a plain block under an X column
  so the X falls onto X, joins and vanishes, then eat the capsule; blocks-only sim per candidate).

## Other modes
- Time attack (mode 16, target word 0 while playing): AI enabled; grey X 0x0916 cannot be dug;
  clocks (cell 0x0003) valued RT_TA_CAPV (180) instead of air capsules.
- Space (mode 14): endless mode; "?" blocks are cell type 0x0C13 (effects not decoded yet).
- Wide fields (W 15) and versus: cell size / player row from the field width.

## Result
User test on MiSTer: 1000 m (America) cleared by the AI in real time. Takes capsules and climbs onto
blocks for them. Still weak: X-enclosed capsules and pure air recovery, gets hasty after ~500 m.
