# 2026-10-23 기능 추가 기록: Mr. Driller 2 / G "Drill (Auto)" 싱크로 연사 키

## 요구

- Mr. Driller 2, Mr. Driller G에서만 동작하는 연사 키 **Drill (Auto)**를 키매핑 항목으로 추가한다.
  누르고 있는 동안만 Drill이 연사되고, 떼면 바로 멈춘다. OSD 설정 항목은 없다.
- MiSTer 내장 연사(시간 기반)가 아니라 **게임에 완벽히 동기된** 연사여야 한다.
- 일반 Drill과 동시에 누르면 OR(일반 Drill을 누르고 있으면 계속 눌림). 기본 매핑 키는 없다.
- OSD가 열려 있는 동안에는 연사하지 않는다.

## 조사: 게임이 입력을 받는 방식 (MAME 0.289, Lua 탭)

처음 계획은 실기 연사기처럼 vsync(게임 프레임, GP1(05) 쓰기)마다 켬/끔을 바꾸는 30연사였다.
구현 전에 MAME에서 게임의 입력 읽기를 측정한 결과 이 방식이 게임에 맞지 않았다.

- IN1 레지스터는 `0x1FBA0004`(하위 16비트, P1 Drill = bit 4) / `0x1FBA0006`이다
  (`0x1FA00004`가 아니다).
- 두 게임 모두 같은 입력 라이브러리를 쓴다(mrdrilr2j 0x8016CEB4, mrdrilrg 0x80296C08).
  **100 Hz IRQ10 핸들러**가 IN1을 읽지만, 인자 `a0&1`이 1인 호출(한 번 걸러 한 번)은 값을
  저장하지 않고 건너뛴다. 그래서 **게임이 보는 입력은 50 Hz(20 ms 간격)**이다.
  - 검증: 10 ms짜리 1샘플 펄스를 여러 위상에 넣었더니 한쪽 순번 43개는 전부 무시,
    다른 쪽 42개는 위상과 관계없이 전부 인식(mrdrilr2j). ISR 단계 측정에서도 두 게임 모두
    100개 중 정확히 50개만 저장.
- 게임은 매 프레임 vblank 직후(GP1(05) 쓰기 전)에 마지막 저장 샘플을 게임용 패드 변수
  (mrdrilr2j 0x8023F94E)로 복사한다.
- 결과: 60 fps 프레임 중 초당 약 10프레임은 새 샘플이 없어 직전 값을 다시 읽는다.
  따라서 **게임이 프레임마다 켬/끔을 번갈아 보는 30연사는 어떤 외부 회로로도 불가능**하다.
  실기에 vsync 카운터 연사기를 달아도 같은 게임 코드이므로 결과는 같다.

| 연사 방식 | 게임이 인식한 연사 (MAME, 실제 게임 코드, 플레이 중) |
|---|---|
| vsync(GP1(05))마다 토글, 30 Hz | 19.98회/초, 불규칙 (30 Hz를 50 Hz로 샘플링한 앨리어싱) |
| IN1 읽기 2회마다 토글 (채택) | **25.01회/초, 빠짐 없음** |
| IN1 읽기마다 토글 | 0 (저장되는 샘플이 항상 같은 값) |

사용자 결정: 게임 입력 샘플 동기 25회/초로 구현하고 실기 연사 경험과 체감 비교.

## 구현

- `rtl/ns10/ns10_autofire.sv` (새 파일)
  - CPU의 IN1 하위 읽기(`exp3_read`, 주소 0x1A0004)의 상승 에지를 센다.
    누르는 순간 바로 켬, 읽기 2회마다 반전. 게임이 두 읽기 중 어느 쪽을 저장하든 저장되는
    샘플은 항상 직전과 반대 값이 된다. 첫 켬은 읽기 2회 동안 유지되므로 첫 발이 빠지지 않는다.
  - 반전은 그 읽기가 값을 래치한 같은 클럭에 일어나므로, 읽힌 값은 반전 전 값이다
    (`ns10_io`가 `rd` 클럭에 `rdata`를 래치).
  - 떼거나 OSD가 열리면 즉시 끔. OSD를 닫았을 때 계속 누르고 있으면 새로 누른 것으로 보고 켬부터.
  - P1/P2 각각 독립.
  - 프레임이 아니라 게임의 실제 입력 샘플에 맞추므로 CPU Turbo, 처리 지연(프레임 드롭)과 무관하다.
- `NAMCOS10.sv`: `J1`에 11번째 버튼 `Button1 (Auto)`(joy bit 14) 추가(맨 끝에 추가해서 기존 매핑의
  비트 번호는 그대로). `af_fire`를 IN1의 Button1 비트(P1 bit 4, P2 bit 12)에 OR.
- `tools/mkmra.py`: Driller MRA(mrdrilr* 5종)만 `<buttons>` 끝에 `Drill (Auto)` 추가.
  다른 게임 MRA는 그대로라서 그 게임에서는 매핑할 버튼이 없다.
- `files.qip`: 새 파일 등록.

## 검증

1. `sim/ns10/run_autofire.sh [seed]` (ModelSim, `tb_autofire.sv`): MAME에서 측정한 입력 모델
   (10 ms 읽기 ±0.3 ms, 한 번 걸러 저장, 저장 순번 랜덤, 59.94 Hz 프레임에서 최신 샘플 소비).
   검사: 10 s 유지 시 게임 인식 249~250회(약 25/s), 저장 샘플이 매번 반대 값, 300회 랜덤 짧은
   누름에서 첫 저장 샘플이 항상 켬, 떼기/OSD/리셋 즉시 끔, P1+P2 동시 각 25/s.
   시뮬 시간 제한 120 s, 1 s 무입력 워치독, 실행 시간 15분 제한. 시드 1~6 PASS.
2. `tools/mame/tap_input.lua`: 같은 알고리즘(`NS10_AFMODE=read`)과 vsync 30 Hz(`vbl`)를
   실제 게임에 넣고 게임 패드 변수에서 누름 횟수를 셌다(위 표).
3. Quartus 디버그 빌드: 코어 클럭 setup/hold 통과(HDMI ascal 경로만 setup -0.214 ns, 디버그
   리비전에서 전에도 있던 HDMI 출력 전용 경로). `Arcade-SYSTEM10_20261023.rbf`로 MiSTer에 올림.
4. 실기 (사용자, Driller 2 / G): MAME나 MiSTer 내장 연사와 달리 실기 연사기 느낌과 비슷하다.
   다만 빠르게 파지다가 중간중간 1프레임이 비어 살짝 느려지는 느낌이 있다.
   이것은 50 Hz 샘플을 60 fps로 읽어서 생기는 현상이다(초당 약 10프레임이 직전 값을 다시 읽음).

## 남은 의문: IRQ10은 실기에서 정말 100 Hz인가

- 100 Hz는 MAME `namcos10.cpp`의 `attotime::from_hz(100)`뿐이고 근거 주석이 없다.
  `rtl/ns10/ns10_io.sv`는 이 값을 그대로 가져왔다.
- 인터럽트 자체는 실기에도 있다(게임 ROM의 핸들러가 인터럽트 상태 bit 3을 보고
  0x1FBA0018로 확인한 뒤 IN1을 읽는다). 확인되지 않은 것은 주기다.
- 실기 주기가 vblank의 2배(119.88 Hz)라면 게임은 정확히 프레임당 한 번 입력을 받고,
  vsync 연사기는 완벽한 30연사가 된다. 사용자의 실기 경험과 맞는 가설이다.
  "한 번 걸러 저장"하는 게임 코드도 120 Hz → 60 Hz 프레임 동기로 보면 자연스럽다.
- 이 주기는 다른 타이밍(게임이 이 틱을 쓰는 곳)에도 영향을 주므로 근거 없이 바꾸지 않는다.
  근거 후보: 핸들러가 올리는 틱 카운터를 게임이 초당 몇으로 쓰는지(타임 어택, 테스트 모드 시계)
  정적 분석, MAME에서 100 Hz와 119.88 Hz 비교.
- 사용자에 따르면 MAME autofire 플러그인도 이 게임에서 정확하지 않았다. 연사 체감의 기준은
  MAME가 아니라 실기 경험이다.

## 참고 / 주의

- MAME에서 psxcpu RAM 읽기/쓰기 탭은 동작하지 않는다. RAM 값은 I/O 탭 콜백에서 `read_u16`로
  폴링해서 바뀐 시점을 잡았다.
- 이 입력 라이브러리의 `+0x22` 필드(누적 OR)는 게임 중에 지워지지 않아 프레임 소비와 관계없다.
- MiSTer에서 같은 버튼에 MiSTer 자체 연사를 함께 켜면 서로 간섭한다.
- 기존에 SYSTEM10 키매핑을 저장한 사용자는 Drill (Auto)를 한 번 매핑해야 한다.

## 추가: IRQ10 주기 조사와 OSD "IRQ10 (Input)" 2xVBlank 시험 옵션

### 조사 결과

- **MAME의 100 Hz는 근거 없는 임시값이다.**
  - 2023년 드라이버 정리 커밋(ec6b3d2b5542)에서 들어왔다.
  - 바로 위에 `TODO: Trace main PCB to see where JAMMA I/O goes and/or how int10 can be triggered`
    주석이 있다. IRQ10이 실기에서 무엇으로 발생하는지 모른다는 뜻이다.
  - 웹에서도 관련 자료를 찾지 못했다.
- **IRQ0과 IRQ10은 별개다.** GPU VBLANK(IRQ0)는 NS10에서도 PS1과 같은 59.94 Hz다.
  IRQ10은 PS1의 외부 핀이고, NS10에서는 기판 로직이 구동한다. 그래서 VBLANK 주기로 IRQ10 주기를
  알 수 없다.
- **롬 분석 (Driller 2 `0x8016BB64` / G `0x80297DF8` 부근, 두 게임 같은 라이브러리)**
  - 인터럽트 상태 `0x1FBA001A` bit 3이면 호출 횟수를 인자로 입력 라이브러리를 부르고
    `0x1FBA0018`로 해제한다.
  - 라이브러리는 2단계로 번갈아 동작한다.
    - 짝수 회: 입력 저장, PS1 패드 라이브러리 형식의 버퍼 정리, 출력 처리.
    - 홀수 회: 출력 자동 꺼짐 카운트다운(64틱).
  - 게임 속도와 시간 계산에는 IRQ10을 쓰지 않는다. 그 밖의 용도는 통신 상태 머신 타임아웃
    (120틱 초과, `0x80174634`)과 디버그 출력뿐이다.
  - 120 Hz 쪽 정황(증명은 아님):
    - PS1 패드 버퍼는 원래 프레임마다 갱신된다. IRQ10/2가 프레임 주기라면 IRQ10은 120 Hz다.
    - 통신 타임아웃 120틱은 120 Hz에서 정확히 1초다.
- 사용자의 실기 싱크로 연사 경험은 Driller G 실기였다.
  실기가 100 Hz였다면 vsync 연사기는 약 20/s로 불규칙했을 것이다(MAME 측정).

### 구현 (디버그 빌드 전용, 기본값 100Hz)

- `rtl/ns10/ns10_io.sv`: `irq10_vbl=1`이면 IRQ10을 VBLANK 후 직전 프레임 길이의 1/4, 3/4 지점에서
  발생시킨다(프레임당 2회).
  - VBLANK 직후 게임의 패드 복사 시점과 겹치지 않게 1/4, 3/4 지점을 골랐다.
  - VBLANK에 고정되므로 프레임과 어긋나지 않는다.
  - 결과: 게임이 프레임마다 정확히 한 번 입력을 저장한다.
- `rtl/psx_top.vhd`, `rtl/psx_mister.vhd`: GPU VBLANK 인터럽트 신호(`irq_VBLANK`, irq.vhd 입력과 같은
  신호)를 `vblank_irq`로 꺼냈다.
- `NAMCOS10.sv`: OSD `O[87] IRQ10 (Input),100Hz,2xVBlank`(디버그 전용, status 87).
  릴리스 리비전은 항상 100Hz.
- 연사 모듈(`ns10_autofire.sv`)은 고치지 않았다. "IN1 읽기 2회마다 반전"이라 2xVBlank에서는 그대로
  매 프레임 반전(30/s)이 된다.

### 검증

1. `sim/ns10/run_irq10.sh [seed]` (ModelSim, `tb_irq10.sv`)
   - 구성: 실제 `ns10_io` + `ns10_autofire`, 33.8688 MHz.
   - VBLANK은 263/262라인 필드를 번갈아 만든다.
   - 게임 모델: IRQ10 후 2~52 µs 지연에 IN1 읽기, 한 번 걸러 저장(순번 랜덤), 해제 쓰기.
     프레임마다 VBLANK 후 0.1~3 ms에 패드 복사.
   - 시드 1 PASS:

     | 항목 | 2xVBlank | 100 Hz (참고) |
     |---|---|---|
     | IRQ10 | 119/s, 1/4·3/4 위치 (±300 ns) | 99/s, 주기 10 ms |
     | 연사 | 29.97/s, 반복 프레임 0 | 25.11/s, 3초에 반복 30프레임 |
     | 17 ms 탭 누락 | 0/40 | 7/40 |

   - 제한: 시뮬 40 s, IRQ10 50 ms 없음 워치독, 실행 15분.
2. MAME 0.289 복사본(D:\scratch_mame_irq, 사용자 MAME 폴더는 그대로)
   - 이 복사본은 Driller 2 / G 싱크로 연사, 입력 관련 보완 자료로 보관한다(사용자 요청).
     빌드된 `namcos10.exe`는 `NS10_IRQ10=vbl2` 환경변수로 2xVBlank가 되고, 없으면 원래 MAME와 같다(100 Hz).
   - `tools/mame/irq10_vbl2.py`로 `namcos10.cpp`에 환경변수 `NS10_IRQ10=vbl2`를 넣어 같은 방식(VBLANK 후 1/4, 3/4)으로 빌드했다.
   - `tools/mame/tap_input.lua`(반복 프레임 수 출력 추가)로 실제 게임 코드에서 측정했다.

     | 게임 | 100 Hz | 2xVBlank |
     |---|---|---|
     | mrdrilr2j (게임 패드 복사 `0x8023F94E`, 플레이 중) | 25.01/s, 978프레임 중 반복 163 | 29.91/s, 반복 1 |
     | mrdrilrg (라이브러리 현재값 `0x803C9AF0`, 메뉴~시작) | 24.97/s, 929프레임 중 반복 156 | 29.91/s, 반복 1 |

   - 반복 1프레임은 게임이 200 ms 동안 GP1(05)를 쓰지 않은 장면 전환 구간이다(연사와 무관).
   - 메뉴, 스테이지 선택, 플레이, 테스트 모드 화면은 두 모드에서 같았다.
     JVS CABINET OPTIONS 비활성도 같다. 즉 통신 타임아웃 경로에 차이가 없다.
3. Quartus 디버그 빌드: 코어 클럭 setup/hold 통과(HDMI PLL 경로만 setup -0.308 ns, 디버그 리비전의
   HDMI 출력 전용 경로). `Arcade-SYSTEM10_20261023.rbf`로 교체해 올렸다. 
4. 실기 (사용자): 2xVBlank가 확실히 더 일관되고 부드럽다. 유튜브의 실기 연사 영상과도 2xVBlank 쪽이
   훨씬 가깝다. 게임 플레이 중 동작은 Driller 2 / G 모두 같다.
   - 테스트 모드 SWITCH TEST(1P:0000 / 0200 표시)로 쉽게 비교할 수 있다.
     - Driller 2: 100Hz는 빠르게 깜빡이고, 2xVBlank는 계속 눌린 것처럼 보인다.
     - Driller G: 두 설정 모두 빠르게 깜빡인다.
   - MAME에서 두 게임의 SWITCH TEST를 연속 프레임으로 캡처했다.
     - 2xVBlank: 두 게임 모두 0000/0200이 매 프레임 정확히 번갈아 나온다.
     - 100Hz: 불규칙하다(같은 값이 2프레임 이어지는 곳이 있음).
   - 테스트 화면은 640x480 인터레이스, 단일 버퍼(GP1(05) 05000000)다.
     MAME GPU는 모든 라인을 그리므로 이 차이를 보여주지 않는다. 따라서 실기에서 보이는 차이는
     입력이 아니라 표시 쪽이다.
   - Driller 2 설명 (가설): PSX 인터레이스 그리기는 표시 중인 필드의 라인을 건너뛴다.
     그래서 프레임마다 정확히 반전하면 각 필드에는 항상 같은 값(한쪽 필드는 0200, 다른 쪽은
     0000)만 그려지고, 고정된 그림처럼 보인다.
     100Hz는 위상이 흘러서 깜빡임이 보인다.
     실기에서 정확한 30 Hz 연사를 넣어도 같은 모습일 것이다.
   - Driller G가 항상 깜빡이는 이유(그리기 방식 차이로 추정)는 확인하지 않았다.

### 다른 게임 영향 (기본값 변경 전 확인, MAME 복사본)

- Gamshara, Star Trigon도 IN1을 IRQ10마다 읽는다(100 Hz → 2xVBlank에서 약 120회/초).
- 두 모드에서 70초 동안 다음이 스냅샷 기준으로 같았다: 타이틀/랭킹/데모, 코인과 시작 입력 후
  플레이(Gamshara), 플레이어/모드 선택(Star Trigon).

### 기본값 변경

- 사용자 결정: 2xVBlank를 기본값으로 한다.
- `NAMCOS10.sv`
  - 릴리스 리비전은 항상 2xVBlank (`irq10_vbl = !DEBUG || !status[87]`).
  - 디버그 OSD는 `IRQ10 (Input),2xVBlank,100Hz`(첫 항목 = 기본값)로 순서를 바꿨다.
  - 이전 디버그 빌드에서 OSD 값을 저장했다면 의미가 뒤바뀐다(1 = 100Hz).

# 기능 추가: 세이브스테이트 (Save / Restore state, 4 슬롯)

## 요구

- MiSTer 네이티브 세이브스테이트(PSX 코어의 savestates.vhd)를 NS10 코어에서 쓸 수 있게 한다.
  저장 시점의 CPU와 메모리 기계 상태를 온전히 저장하고 그대로 복원해야 한다. 되감기(rewind)는 없다.
- NVRAM(설정/점수)도 상태에 포함하고 복원한다(MAME 방식: 상태를 불러오면 NVRAM도 그 시점으로 돌아간다).
- OSD는 기존 릴리스 항목(Video & Audio, DIP Switches, CRT Adjust (analog), Pause when OSD is open)을
  그대로 두고 Savestates 페이지와 단축키를 추가한다.

## 원인 / 문제: PSX 세이브스테이트를 그대로 쓸 수 없는 이유

1. **메모리 크기**: PSX 코어 상태는 RAM 2 MB, VRAM 1 MB 기준(슬롯 4 MB)이다. NS10은 RAM 4 MB, VRAM 2 MB
   (행 512-1023은 DDR3 0x30800000)라서 그대로 저장하면 RAM 절반, VRAM 절반이 빠진다.
2. **슬롯 주소**: PSX의 슬롯(DDR3 0x3E000000-)은 NS10의 ROM 이미지(0x35000000-)와 겹치지는 않지만
   8 MB 슬롯 4개가 들어갈 자리가 필요하다.
3. **PSX 밖의 상태**: ROM 보드(보드 RAM 16 KB, NAND 페이지 레지스터, 플래시/NAND 상태 레지스터),
   복호화기(cipher 상태), 메인보드 I/O(IRQ10 타이머, I2C 상태)는 PSX 코어가 모른다. 빠지면 복원 후
   ROM 읽기/복호화/IRQ10 주기가 저장 시점과 달라진다.
4. **NVRAM**: 설정 영역은 DDR3 ROM 이미지 안에 있고(ROM 캐시 경유), ns10_nvram BRAM은 그 사본이다.
5. **SD카드 파일**: Main_MiSTer는 코어가 리셋 때 슬롯 헤더를 검사한 **뒤에** .ss 파일을 슬롯에 넣는다.
   PSX 로직은 리셋 때 유효하다고 본 슬롯만 복원하므로, 코어를 다시 띄운 뒤 파일에서 복원하는 것이 막힌다.

## 해결

- **rtl/savestates.vhd** (PSX 세이브스테이트 엔진)
  - 슬롯 8 MB(SAVESTATESIZE 0x200000 dword), 상태 크기 STATESIZE 1835006 dword(파일 7,340,032 바이트).
    STATESIZE는 헤더 형식 검사 값이기도 해서, 예전 PSX 형식 파일은 복원되지 않는다.
  - RAM 4 MB(SS_Adr 20비트, memorymux 동일), VRAM 2 MB(vram_addr(): 두 번째 512행은 DDR3 +0x800000).
  - SPU RAM: NS10 리버브 영역이 온칩 128 KB(0x60000-)라서 온칩/DDR3 경계를 0x18000 dword로 맞췄다.
  - 새 타입 17 = NS10 보드 상태(9312 dword, SS 버스로 NAMCOS10.sv에서 읽고 씀),
    타입 18 = NVRAM 영역(4224 dword, 저장은 DDR3 ROM 이미지에서 직접 읽고, 복원은 SS 버스로 써서 ROM 캐시 경유).
    리셋 때의 메모리 초기화(resetMode)는 17/18을 건드리지 않는다(ROM 설정 영역이 지워지면 안 된다).
  - **복원 전 헤더 검사**: 유효로 알려지지 않은 슬롯을 복원하면 먼저 리셋 없이 일시정지하고 헤더만 읽는다.
    유효하면 그대로 복원, 아니면 아무 일 없이 재개(리셋 없음). SD카드 파일 복원이 이렇게 된다.
- **rtl/statemanager.vhd / psx_top.vhd / psx_mister.vhd**: 슬롯 크기, 슬롯 주소 DDR3 0x3C000000
  (Softmap 0x3000000 dword), NS10 SS 버스 포트(ns10ss_*) 추가. SS_idle에 NS10 보드 idle을 AND.
- **rtl/ns10/ns10_romboard.sv / ns10_crypt.sv / ns10_io.sv**: 세이브스테이트 읽기/쓰기 포트.
  타입 17 dword 주소: 0x0000-0x1FFF 보드 RAM 워드, 0x2000-0x23FF 페이지 레지스터 바이트,
  0x2400-0x241F ROM 보드 레지스터, 0x2440-0x2444 복호화기, 0x2450-0x2453 I/O. 읽기는 주소 다음 클럭.
- **NAMCOS10.sv**
  - CONF_STR `SS3C000000:800000`, OSD P4 "Savestates" 페이지(SD카드 저장, 슬롯 자동증가, 슬롯 1-4, 저장, 복원).
    기존 페이지/항목은 그대로다.
  - savestate_ui(업스트림): 키보드 Alt+F1-F4 저장, F1-F4 복원. 패드: "Savestates" 버튼(J1 bit 15)을 누른 채
    ↓ 저장, ↑ 복원, ←/→ 슬롯. 누르는 동안 패드 입력은 게임에 가지 않는다.
  - 타입 18 복원: dword 2개를 모아 ROM 캐시에 1 beat 쓰기(rq mux, 다운로드/nvload 다음 우선순위).
    DDR3 ROM 이미지와 ns10_nvram BRAM이 함께 갱신되고 게임 쓰기와 같은 경로라서 다음 OSD 열기에서 .nvm도 따라간다.
    복원이 끝나면 ROM 캐시를 무효화한다.
  - files.qip에 rtl/savestate_ui.sv 추가.

## 동작 메모

- "Savestates to SDCard" On(기본): 저장 후 Main_MiSTer가 파일을 쓰는 동안 약 1초 멈춘다(업스트림 동작,

  미룬다(gpu_videoout_async allowunpause). 정상이다.

# 수정: kseg0 BIOS 코드를 i-cache 라인 채우기로 실행 (부팅 막대 화면 단축), HDMI 스케일러 버퍼 2 MB

## 증상

- 다른 개발자의 Namco_S10 코어와 비교하면 우리 코어는 부팅 막대 화면(왼쪽 흰/노랑/하늘/초록 막대, 오른쪽 검정)이
  몇 초 더 길었다. 실기 측정(로드 명령 기준, 1초 간격 스크린샷): Mr. Driller G는 4개 막대 화면이 7~17초(약 10초),
  Mr. Driller 2는 5~6초(약 2초).

## 원인

- NS10 BIOS 모듈은 kseg0(0x9FC2xxxx, 캐시 가능 영역)에서 실행된다. 2026-10-18 수정(fd08fe5)에서 BIOS fetch가
  i-cache 데이터를 채우지 않는데 태그만 유효로 표시해 오래된 명령어가 실행되는 버그를 고칠 때, BIOS fetch를
  아예 캐시하지 않게(태그 유효 표시 안 함) 했다. 그 결과 kseg0 BIOS 명령어 하나마다 PSX BIOS ROM 타이밍(25~26 clk1x)의
  단일 읽기를 했다. Driller G의 4개 막대 구간(NAND 테이블 검사, 프로그램 적재)이 이 코드에서 오래 돈다.
- Namco_S10 코어는 이 영역의 캐시 가능 fetch를 RAM처럼 i-cache 라인 버스트(ram_cache)로 채운다.

## 해결

- rtl/memorymux.vhd: 명령어 fetch가 BIOS 영역(0x1FC00000 이상)이고 캐시 가능(kuseg/kseg0, `mem_isCache`)이면
  RAM의 캐시 fetch와 같은 방식으로 SDRAM에 128비트 버스트 읽기(`ram_cache = 1`)를 하고, 요청 워드부터 라인 끝까지
  태그를 유효로 표시한다(`mem_tagvalids`). 이제 i-cache 데이터가 실제로 채워지므로 fd08fe5의 버그는 생기지 않는다.
  kseg1(0xBFC, 캐시 불가) fetch와 BIOS 데이터 읽기는 기존 READBIOS 경로 그대로다.
- NAMCOS10.qsf: `MISTER_SMALL_VBUF=1`(ascal 프레임 버퍼 8 MB -> 2 MB, 640x480에 충분). ascal 주소 로직이 줄어
  HDMI 클럭 타이밍에 유리하다. `MISTER_DISABLE_ADAPTIVE`는 HDMI 스캔라인 효과(video processing)에 쓰이므로 켜지 않는다(사용자).
  릴리스 qsf(NAMCOS10_release.qsf)에는 아직 넣지 않았다(사용자의 SEED 5 미커밋 변경이 있음, 릴리스 빌드 때 함께 반영).

## 검증

- GHDL sim/bioscache (`./run.sh compile base; ./run.sh compile new; ./run.sh sim mrdrilr2j 20000`): HEAD의 memorymux와
  새 memorymux로 같은 BIOS를 리셋부터 20 ms 실행, 명령어별 PC/opcode/레지스터 합 비교. 19,932개 명령어 동일.
  새 경로를 탄 kuseg BIOS 코드(0x1FC1A010~)도 같은 명령어를 실행했고 fetch가 약 3.5 us 빨라졌다. 이후 차이는
  GPU 상태 폴링(bit 31) 값이 다른 시각에 읽힌 것뿐이다(cmpboot.py가 타이밍 차이로 판정).
  20 ms는 대부분 kseg1 지연 루프라 kseg0 모듈 구간까지는 시뮬에서 가지 못했다(20 ms에 약 7.7분, 15분 제한). kseg0은
  실기로 확인했다. 시뮬 BIOS 실행 속도는 약 1 us/명령어(kseg1 uncached)다.
- 실기(디버그 빌드, SEED 2), 같은 측정 방법:
  - Mr. Driller G: 4개 막대 7~8초(이전 7~17초), 다음 화면 9초(이전 18초), 타이틀 17초(이전 27초). 약 9~10초 단축.
  - Mr. Driller 2: 막대 5초만(이전 5~6초), 다음 화면 6초(이전 7초). 약 1초 단축.
  - Gamshara, Star Trigon: 부팅 후 어트랙트까지 정상(화면 확인).
- 타이밍(quartus_sta 4코너): HDMI ascal setup slow 100C -0.104 / slow -40C +0.076 ns(이전 디버그 SEED 2: -0.308 / -0.117).
  hold: clk3x memorymux ram_dataWrite -> sdram saved_data slow 100C -0.064 ns(다른 코너 양수), 디버그 전용 JTAG hub(tck)
  -0.228 / -0.517 ns. 릴리스 빌드 때 SEED로 다시 확인할 것.

## 참고 / 주의

- 측정용 스크립트는 저장소 밖(scratchpad)에 있다: MiSTer에서 `load_core` 후 1초마다
  `timeout 1 sh -c 'echo screenshot > /dev/MiSTer_cmd'`, 스크린샷 파일 시각 - 로드 시각으로 구간을 잰다.
  스크린샷 폴더의 기존 파일은 지우지 말 것(이번 측정 중 gamshara 등 폴더의 기존 스크린샷을 지우는 실수가 있었다).
- 디버그 오버레이 "ED"(Gamshara, Star Trigon)는 기존부터 있던 표시다(CPU 정지 >= 512 clk, 롬 버스 대기, docs/handoff.md).
