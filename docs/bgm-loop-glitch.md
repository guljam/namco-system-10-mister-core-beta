# Mr. Driller G 파란 화면 + 음악 반복 버그 (BGM 스트림 경쟁 상태)

## 한 줄 요약

레벨 곡이 끝나는 순간 BGM 전환이 겹치면, 사운드 처리기가 남아 있던 "곡 끝" 요청을 **새 곡 기준으로** 처리해 1KB 버퍼에 새 곡 길이만큼(약 1.1MB)을 밀어 넣고, 넘친 데이터가 그래픽 콜백 주소 표를 덮어 CPU가 엉뚱한 주소로 점프한다. 그 결과가 PS1 BIOS SystemError 화면(파란 화면)이고, CPU가 멈춘 뒤에도 SPU가 마지막 버퍼를 계속 재생해 음악 한 부분이 반복된다.

## 증상 (사용자 보고)

- 보고 시점: 2026-10-28.
- 환경: MiSTer SYSTEM10 코어, 패치 롬 `mrdrilrg_patch` (시리얼 변경 + 유령 블록 수정만 적용), 혼자하기 북극 스테이지, MiSTer 세이브스테이트 슬롯 2.
- 상황: 800m 클리어 후, 레벨 경계에서 큰 블록이 떨어지는 899m 지점.
- 나타난 증상:
  - 화면 전체가 파란색으로 바뀐다.
  - 음악의 한 부분이 계속 반복된다.
  - 게임이 정지한다(진행 없음).
- 파란 화면의 정체: PS1 BIOS SystemError 화면.
  - BIOS SystemError 함수(`0xBFC02708`)가 화면을 그린 뒤 `0xBFC028FC` 에서 무한 루프.
  - 오류 코드 S `0x387`.
  - CPU 예외는 AdEL, 게임 코드가 `0xF13C5002` 로 점프.
  - `0xF13C5002` 는 RAM `0x803C50A8` 에 있던 BGM 데이터 값이다.
- 음악 반복의 정체: CPU가 멈춘 상태에서 SPU가 마지막 스트림 버퍼를 계속 재생하는 것.
- 직접 원인: IRQ가 호출하는 libgpu 콜백 테이블 `0x803C4080`–`0x803C4130` 이 BGM ADPCM 데이터로 덮여 있었다.

## 쉬운 설명

비유로 설명하면 이렇다.

- 게임은 NAND에서 BGM을 **실시간으로 조금씩** 읽어 SPU에 넘긴다. 컵 두 개(각 1KB)에 번갈아 물을 담아 건네는 방식이다.
- 곡이 끝나갈 때, 게임은 "이 곡 끝(되감기 필요)" 이라는 **메모**를 하나 남긴다.
- 나중에 처리기가 그 메모를 보고 "남은 양만큼 채우고, 모자라면 곡 처음부터 다시 채운다" 를 한다. 이때 "남은 양"은 **지금 재생 중인 곡의 길이에서 현재 위치를 뺀 값**으로 계산한다.
- 문제는 이 메모가 **남아 있는 상태에서 곡이 바뀌는** 경우다.
  - 처리기는 메모를 새 곡 기준으로 해석한다.
  - 그래서 "남은 양"이 새 곡 전체 길이(예: 약 1.1MB)만큼 계산된다.
  - 컵 하나는 1KB짜리이므로, 넘친 물이 옆자리에 있는 **중요한 메모(그래픽 콜백 주소 표)** 를 지워 버린다.
- 주소 표가 지워진 뒤 다음 IRQ가 그 표를 읽으면, CPU가 엉뚱한 주소(BGM 데이터 값)로 점프한다. 그래서 BIOS 오류 화면이 뜬다.
- CPU가 죽었으므로 음악을 넘겨줄 사람이 없다. SPU는 마지막으로 받은 버퍼를 계속 재생한다. 그래서 음악 한 부분이 반복된다.

핵심은 **"곡 끝" 메모를 남기는 쪽과 그것을 처리하는 쪽 사이에 곡이 바뀔 수 있다**는 점이다. 처리 코드에는 "남은 양"에 대한 범위 검사가 없다.

## 발생 조건 (세 가지가 동시에)

1. **한 구간에서 레벨 곡이 끝까지 재생된다.**
   - 곡 4/5 길이는 `0x130880` (약 4019프레임, 약 67초)이므로, 한 구간에 67초 이상 머물러야 한다.
   - 곡은 구간마다 처음부터 시작한다고 보고 있으나, 이 부분은 **확인 안 됨**.
2. **곡의 마지막 1KB 구간에서 요청 3(곡 끝/되감기)이 올라가고, 아직 처리되지 않은 0~1프레임(약 17ms)의 창이 생긴다.**
   - 요청은 IRQ 문맥에서 올라가고, 실제 처리는 메인 루프에서 보통 0~1프레임 안에 이루어진다.
3. **바로 그 창 안에서 BGM 정지 + 새 곡 시작이 처리기보다 먼저 일어난다.**

참고로 게임 오버처럼 정지와 시작 사이가 12~31프레임 떨어져 있으면, 그 사이에 요청이 처리되어 안전하다(MAME 관찰).

## 순정 롬에서 오랫동안 보고되지 않은 이유

추정이 포함되어 있으며, 근거를 함께 적는다.

- **확률이 낮다 (추정).** BGM 전환 1회당 대략 1/4000 수준으로 계산된다. 곡 한 바퀴가 약 4000프레임인데 그중 위험 창이 1프레임 정도이기 때문이다. 여기에 "한 구간에 67초 이상 머문 경우"라는 조건이 더 붙는다.
  - 이 수치는 측정값이 아니라, 곡 길이와 처리 간격으로 계산한 **추정**이다.
- **빠른 플레이로는 곡 끝에 도달하지 않는다 (추정).** 곡 끝까지 재생되지 않으면 요청 3 자체가 올라가지 않는다.
- **발생해도 원인 기록이 남기 어렵다 (추정).** 무작위 멈춤처럼 보이므로, 재현 조건을 정리하기 어렵다.
- **아케이드 판의 플레이 시간 자체가 적다.** 아케이드 판 Mr. Driller G 는 일본 한정 소량 출시였다는 것은 일반 정보이며, **확인 안 됨**.
- **순정 롬 실기에서의 자연 발생 기록은 찾지 않았다 / 모른다.**

## 기술 세부 (주소, 흐름, 증거)

### BGM 스트리밍 구조

- 2채널, 채널당 1KB 더블 버퍼.
  - 버퍼 주소: `0x803B3500 + ch*0x800 + toggle*0x400`
- 상태 기준 주소: `0x803B34E8`
- 요청 필드: `0x803B34D8` / `0x803B34DC`
  - `1` = 무음
  - `2` = 다음 1KB 채움
  - `3` = 곡 끝 / 되감기
- 재생 상태 필드(상태 기준 `+` 오프셋):
  - `+0x1018` : NAND 위치
  - `+0x1020` : pos
  - `+0x1038` : 곡 번호
  - `+0x1040` : 루프 플래그
- 곡 테이블: `0x802A79F8`, 형식 `{start, len}`.

### 정상 흐름

1. SPU 인터럽트(`0x80247548`, IRQ 문맥)가 약 3.3프레임마다 요청을 올린다.
2. `pos >= len - 0x400` 이면 요청 3(곡 끝/되감기)을 올린다.
3. 메인 루프(`0x80246194` → `0x80247BC8` → 처리기 `0x80247AE8`)가 요청을 처리한다. 보통 0~1프레임 안에 처리된다.
4. 요청 3 처리기(`0x80247318`)는 다음을 한다.
   - `s3 = len - pos` 바이트를 읽는다.
   - 나머지 `0x400 - s3` 바이트를 루프 시작 지점에서 읽는다.
   - **`s3` 에 대한 범위 검사가 없다.** ← 여기가 원인 지점.
5. BGM 시작 경로(`0x80247EB0`, 재생 중이 아닌 경우):
   - `pos = 0x400`, 첫 1KB를 읽고 `nand = start + 0x400` 으로 둔다.
6. 정지 경로(`0x8024802C`):
   - `song = -1`, `pos = 0`, `nand = -1`.
7. **두 경로(시작/정지) 모두 대기 중인 요청을 지우지 않는다.** 이것이 경쟁 상태의 발판이다.

### 버그 흐름

1. 곡 A 의 요청 3 이 대기 중이다.
2. 처리기가 돌기 전에 **곡 A 정지 + 곡 B 시작** 이 일어난다.
3. 처리기가 `s3 = lenB - 0x400` 을 계산한다.
   - 곡 10 기준: `0x10D520 - 0x400 = 0x10D120` (약 1.1MB).
4. 이 양을 1KB 버퍼에 읽어 넣는다.
5. RAM `0x803B3900` 부터 `0x803C5600` 까지가 덮인다. 덮이는 영역에는 다음이 포함된다.
   - NAND 리맵 테이블 `0x803B4690`
     - 덮인 뒤에는 엉뚱한 블록을 읽게 되고, `0xFF` 블록까지 읽는다.
   - 사운드 드라이버 / libspu BSS
   - libgpu 콜백 테이블 `0x803C4080`–`0x803C4130`
6. 다음 IRQ가 망가진 주소로 점프한다 → BIOS 오류 화면.

### 증거

- 크래시 당시 RAM `0x803B3500` 에 **곡 4(BGM 7, 레벨 곡)** 의 마지막 조각이 남아 있었다.
- `0x803B3900` 부터는 **곡 10(BGM 6, 곡 시작 `0x1F98260`)** 의 `start + 0x400` 부터 이어지는 연속 데이터가 있었다.
- 즉, 레벨 곡이 정확히 끝나는 순간 899m 경계의 BGM 전환이 겹쳤다는 뜻이다.

### 패치 롬과의 관계 (패치 무관 근거)

- 순정 롬과 패치 롬의 BGM 코드는 같다.
- 유령 블록 패치 15워드(`0x80201A58`–`0x80201A94`, `0x802021D4`)는 이 경로에 없다.
- 사용자가 제시한 가설 6개 중 맞는 것은 **"곡 루프 재시작"** 하나뿐이다. 나머지는 근거가 없다.
  - 시리얼/패치 타이밍: 근거 없음
  - 패치가 다른 코드를 손상: 근거 없음
  - 키커스 검사: 근거 없음
  - 메모리 배치 / MRA: 근거 없음
  - 코어 결함: 근거 없음

### 코어 영향 가능성 (확인 안 됨)

- 큰 블록 낙하 같은 무거운 프레임에서 메인 루프가 늦어지면 위험 창이 넓어질 수 있다. **확인 안 됨.**
- MiSTer 코어 타이밍이 MAME/실기와 달라 발생 빈도가 다를 수 있다. **확인 안 됨.**

## 수정 (5워드 표)

`s3 > 0x400` 이면 "곡이 바뀌기 전에 남은 오래된 요청" 으로 보고, 되감기 대신 평소 채움 경로로 처리하게 만든다. 정상 플레이 동작에는 변화가 없다.

적용 위치는 `0x80247398`–`0x802473A8` 이며, 이 자리는 빈 디버그 printf 블록이 있던 곳이다. 참고로 `0x80249C94` 는 아무것도 하지 않는 함수다.

| # | 주소 | 원래 값 | 새 값 | 명령 | 의미 |
|---|---|---|---|---|---|
| 1 | `0x80247398` | `3C04801E` | `2E620401` | `sltiu v0, s3, 0x401` | `s3 < 0x401` 이면 `v0 = 1` |
| 2 | `0x8024739C` | `3C03803B` | `14400012` | `bnez v0, 0x802473E8` | 정상 크기면 정상 되감기 경로로 |
| 3 | `0x802473A0` | `246334E8` | `00000000` | `nop` | 지연 슬롯 |
| 4 | `0x802473A4` | `00151080` | `10000054` | `b 0x802474F8` | 비정상(큰 `s3`)이면 평소 채움 경로로 |
| 5 | `0x802473A8` | `00431021` | `00000000` | `nop` | 지연 슬롯 |

## 검증

### GroovyMAME

- `race.lua`: 세이브스테이트에서 곡 시작 순간 요청 3 을 강제로 발생시킨다.
  - 순정 롬 / 유령 블록만 적용한 롬: **27프레임 후 BIOS 무한 루프** (MiSTer 증상과 같음).
  - 수정 코드: 계속 재생됨.
- 산소 u32 `0x80369CA0` 를 고정(죽지 않게)하고 60000프레임 진행, 곡 되감기 17회 → 무크래시.
  - 즉 **곡 반복 자체는 안전**하다.
- 콜드 부팅 `bootrace.lua` (새 nvram 폴더 사용):
  - 새 롬: RAM 에 20워드가 모두 존재하고, 강제 경쟁 상황에서도 4500프레임 무크래시.
  - 이전 롬: 28프레임 후 BIOS 루프.
- `driller-rom-patch` 의 `tests/verify.py` 86개 통과.

### 주의

- MAME 는 NAND 를 nvram 폴더(`nand0/1/2`)에 저장하고, 다음 실행에서 롬 대신 그 저장본을 사용한다.
- 따라서 **롬 교체 후 테스트는 반드시 새 nvram 폴더로** 해야 한다.

## 남은 일 / 확인 안 된 것

- 실기에서 899m 장면 재플레이 (미실시).
- 899m 경계에서 "정지 + 시작" 이 실제로 한 루프 안에 일어나는지 직접 관찰하지 못했다. RAM 흔적과는 일치한다.
- 위험 창 폭(0~1프레임, 약 17ms)의 실측값 없음 — 계산/관찰 기반.
- MiSTer 세이브스테이트 슬롯 2 는 크래시 이후 상태이므로, 불러오면 여전히 파란 화면이다.
- 곡이 구간마다 처음부터 시작하는지: **확인 안 됨**.
- 코어 타이밍이 발생 빈도에 미치는 영향: **확인 안 됨**.
- 아케이드 판 일본 한정 소량 출시/플레이 시간: **확인 안 됨** (일반 정보).
- 순정 롬 실기에서의 자연 발생 기록: 찾지 않았다 / 모른다.
- Driller 2 (`mrdrilr2j`)에도 같은 스트리밍 코드가 있다(되감기 `0x801662xx`, 요청 `0x801664C4`). 다만 빈 공간이 없어 미수정 상태다.
