# 2026-11-12 Mr. Driller G 붙은 블록 분리 버그 수정 (롬 패치)

코어(RTL) 변경은 없다. 게임 프로그램 버그이고 롬 패치로 고쳤다.
- 패치 도구: `D:\My_App_Project\driller-rom-patch` (git 저장소 아님)
- 연구 자료: 같은 폴더의 `research/split-bug/README.md`

## 증상 (사용자 보고, 유령 블록 패치 롬에서 발생)

조건: 아래 줄 블록이 연쇄로 반짝이다가 완전히 사라지는 바로 그 프레임에, 그 위 블록(D)을 판다.

결과: D 위에 붙어 있던 같은 색 블록 덩어리가 갈라진다. 반은 그대로 서 있고 반은 떨어진다.

원본 롬에서도 같은 현상이 일어난다. 2026-10-25 사용자 영상에 나온 분리가 이것이다.

## 원인

1. 프레임 루프의 3번째 패스(`0x802031D0`)는 다음 조건을 모두 만족하는 칸 T에 대해 구조 플러드 `0x802017C0`(T, T의 종류)를 부른다. 이 함수는 T를 다시 '서 있음'(상태 4)으로 돌리고 이웃 칸으로 퍼진다.
   - 상태 1 (낙하)
   - 이전 상태 4 (서 있음)
   - 아래 칸이 상태 8 (파기)
2. 좌/우/아래로 퍼질 때는 플래그표 `0x8029E8E8`의 bit `0x20`을 확인한다. 이 비트는 상태 2, 3, 4에만 있다.
3. 그런데 같은 프레임에 낙하 시작 플러드(`0x80200B70`, 색을 보지 않고 받침 0인 칸 전부)가 T의 짝 블록을 이미 상태 1로 바꿔 놓았다.
4. 그래서 짝은 건너뛰고 T만 다시 선다. 이것이 분리다.
5. 위 방향으로 퍼질 때는 위 칸 자신의 종류가 아니라 호출자(T)의 종류를 넘긴다. 그래서 위 블록의 같은 색 짝도 빠진다.
6. 기존 유령 블록 수정(2026-10-25/27)은 위 방향 검사만 고쳤고, 이 경로는 고치지 않았다.

## 가설 검증 (GroovyMAME + Lua로 RAM 워드 교체)

| 시험 | 원본 롬 | 유령 패치 롬 | 수정 v2 |
|---|---|---|---|
| 손으로 만든 배치 10종 x 사라짐 타이머 5 | 분리 7 | 분리 7 | 분리 0 |
| 트리거 시점 무작위 배치 200개 | 분리 44 | 분리 31 | 분리 / 유령 / 멈춤 0 |
| 무작위 플레이 100회 x 1500프레임 | (기준) | 원본과 동일 | 판 상태가 원본과 프레임 단위로 동일 |

## 해결

`0x802017C0` 함수를 125워드(`0x802017C8`-`0x802019C0`)로 다시 썼다. 스택 프레임은 원래와 같다.
- 이웃 검사에서 "상태 1이고 이전 상태 4"인 칸(이번 프레임에 막 낙하로 바뀐 칸)도 받아들인다.
- 위 방향은 위 칸의 종류에 `0x800` 비트가 있으면 그 종류를 넘긴다.
- 유령 블록 수정의 동작은 그대로 유지한다.

롬 패치 도구 변경:
- G에는 항상 145워드(유령 15 + BGM 크래시 5 + 블록 분리 125)를 전부 적용한다.
- 묶음별로 상태를 판정한다. 원본, 유령만 적용, 유령 + BGM 적용, 전부 적용 중 어느 롬이든 결과는 전부 적용된 롬이다.
- 시리얼은 맨 처음 묻는다. 형식이 틀리면 같은 질문을 다시 하고, 빈 입력이면 시리얼을 유지한다.
- `verify.py` 88개 항목이 모두 통과한다.

# 2026-11-12 Mr. Driller 2 BGM 스트림 크래시 수정 (롬 패치)

코어(RTL) 변경은 없다. Driller G의 BGM 크래시(2026-10-28, `docs/bgm-loop-glitch.md`)와 같은 게임 프로그램 버그를 Driller 2에서도 찾아 롬 패치 도구에 수정을 넣었다.
- 연구 자료: `D:\My_App_Project\driller-rom-patch\research\bgm-crash\driller2\README.md`
- 도구 설명: 같은 폴더 `README.md`의 "Driller 2 BGM 크래시 수정" 절

## 원인

- BGM은 1KB 버퍼 두 개를 번갈아 채우며 NAND에서 조금씩 읽는다.
- SPU IRQ가 "곡 끝" 요청(3)을 올리고, 메인 루프의 처리 함수가 되감기 함수 `0x80166264`를 부른다.
- 되감기 함수는 `남은 양 = 곡 길이 - 위치`를 범위 검사 없이 읽기 크기로 쓴다.
- 요청 3이 처리되기 전에 곡이 바뀌면, 새 곡 길이 - 0x400 (최대 약 1.4MB)을 1KB 버퍼에 읽는다. 메모리가 덮이고 BIOS SystemError 파란 화면이 뜬다.
- 곡 시작/정지 코드는 남아 있는 요청을 지우지 않는다. G와 같은 구조다 (G `0x80247318` = D2 `0x80166264`).

## 가설 검증 (GroovyMAME)

- 사용자 세이브 `mrdrilr2j` 5번에서 Drill을 누르면 스테이지가 클리어되고 곡이 바뀐다.
- 한 프레임 안의 순서는 곡 전환(0.4 ms) -> SPU IRQ -> 메인 루프 처리(약 6 ms)다.
- 곡 끝 IRQ 시각은 루프마다 +2.35 ms씩 밀린다: 4.9 -> 7.26 -> 9.62 ms.
- 3번째 루프에서는 IRQ가 처리 뒤에 와서, 요청이 다음 프레임까지 남는다.
- 그래서 세이브 로드 후 7887프레임에 Drill을 누르면 곡 전환과 겹쳐 파란 화면이 나온다. 메모리 조작 없이 버튼 입력만으로 재현된다. 7886과 7888은 정상이고, 창은 1프레임이다.
- World 버전(`mrdrilr2`)도 강제 주입 시험에서 같은 파란 화면이 나왔다.

## 해결

- G 수정과 같은 동작을 넣었다: 남은 양이 0x400보다 크면(오래된 요청) 읽지 않고 끝 처리 `0x801663F4`로 건너뛴다.
- Driller 2에는 G처럼 빈 디버그 블록이 없다. 그래서 함수 앞부분에서 기준 주소를 두 번 계산하던 것을 s2/s0에 한 번만 계산하도록 줄였다.
- 그렇게 생긴 자리에 `sltiu v0,s3,0x401` / `beqz v0,0x801663F4`를 넣었다. 22워드, `0x8016629C`-`0x80166314`.
- 프로그램 저장 방식:
  - 플래시 `dr2xvera.1a [0x62000, 0x380000)`에 type-1 암호(MAME `ns10crypt.cpp`)로 들어 있고, 0x80000마다 재초기화된다.
  - 수정 위치는 세그먼트 `0x180000`(초기 마스크 4)이다.
  - 도구가 세그먼트를 복호화하고 22워드를 바꾼 뒤 끝까지 다시 암호화한다.
- 세 버전(dr21/22/23)이 같은 위치에 같은 코드를 갖고 있다.
