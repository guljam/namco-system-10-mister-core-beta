# Namco System 10 코어 개발 착오 / 해결 기록

PSX_MiSTer(cd17b5a)를 기반으로 Namco System 10(NS10) 코어를 만들면서 겪은 문제와 잘못 짚었던 가정, 최종 해결 방법을 커밋 순서대로 정리한다.
현재 상태와 작업 방법은 `docs/handoff.md`에 있다.

## 한눈에 보기

| 단계 | 증상 | 원인 | 해결 (커밋) |
|---|---|---|---|
| ROM 보드 | 빈 NVRAM에서 게임 멈춤 | 28F640J5 명령 일부(E8 / 60) 누락, 쓰기에 뱅크 적용 | intelfsh 명령 전체 구현 (c202291) |
| DDR3 배치 | 프로그램 플래시 앞부분이 깨짐 | ROM 이미지(0x34000000)가 GPU 프레임버퍼 영역과 겹침 | ROM을 0x35000000으로 이동 (50eafa9) |
| CPU 캐시 | RAM 4 MB인데 데이터가 섞임 | 데이터 캐시 태그 / DMA 캐시 주소가 2 MB 기준 | 4 MB로 확장 (4a49ad4) |
| BIOS 부팅 | 파란 화면, `SYSTEM ERROR CODE=903` | kseg0 BIOS 페치가 i-cache 태그만 유효로 표시 | BIOS 페치 비캐시 처리 (fd08fe5) |
| MEM(N) 부팅 | `yshi_nand_table_check ... wrong` | 보드 RAM 0x1F500000 누락 | 16 KB SRAM 추가 (dfa2da4) |
| 그래픽 | mrdrilrg 화면 대부분 깨짐 | NS10 GPU VRAM 2 MB(1024줄), PSX 코어는 512줄 | System573 패치 0012-0021 이식 (a708bdf) |
| CPU 속도 | 13스테이지 슬로다운 | NS10 CPU 50.7 MHz(1.5배), 코어는 33.9 MHz | OSD CPU Turbo, 기본 High (29105e9) |
| 터보 부작용 | I/O 쓰기가 RAM 줄을 오염 | 데이터 캐시가 I/O / EXP 쓰기까지 받음 | RAM 쓰기만 캐시 (29105e9) |
| 사운드 | 음이 낮고 느림 | NS10 SPU는 66.15 kHz | 샘플당 768 → 512 clk (5d5de28) |
| 사운드 | 주기적 끊김 | 리버브 영역이 온칩 RAM 밖 → DDR3 비캐시 | 리버브 BRAM 128 KB (5d5de28) |
| 화면 전환 | 장면 전환 때 1-2 프레임 깨짐 (Cache Full) | PSY-Q `v_wait` 루프 타임아웃이 vblank 전에 만료 | 터보 중 타임아웃 시프트 15 → 16 (21a5eea) |
| 480i 게임 | Star Trigon / Gamshara 줄무늬, 깜빡임 | GPU가 필드 안에 못 그림(NS10 GPU는 1.5배) | 필드 락 + 텍스처 버스트 + 다중 줄 페치 (03258f0, cba4156, eda46d1) |
| 사운드 | 화면 좌상단 EA | 샘플 업로드 중 SPU가 512 clk 예산 초과 → 샘플 버림 | 밀려 있을 때 RAM 전송 대기 (7577f5b) |

## 1. ROM 보드와 부팅 (2026-10-18)

### 1.1 MEM(M) 플래시: 빈 NVRAM에서 게임이 멈춤 (c202291)
- 증상: 처음 부팅(빈 NVRAM)하면 게임이 저장 블록을 지우고 다시 쓰다가 멈췄다.
- 착오: 처음에는 읽기 경로만 MAME와 일치시키면 된다고 보고, 28F640J5 명령 중 읽기 / 상태만 구현했다. 쓰기에도 읽기와 같은 뱅크를 적용했다.
- 원인: 게임은 0x60/0xD0(마스터 락), 0x20/0xD0(지우기), 0xE8(쓰기 버퍼)을 쓴다. MAME `namcos10_memm nand_w`는 쓰기에 뱅크를 적용하지 않는다.
- 해결: intelfsh 명령 전체 구현, 쓰기는 뱅크 무시. Python 모델도 intelfsh의 1초 지우기 상태 타이머까지 따라가도록 수정. 빈 NVRAM mrdrilr2j 트레이스 2천만 벡터 불일치 0.

### 1.2 ROM 이미지와 GPU 버퍼가 DDR3에서 겹침 (50eafa9)
- 증상: 프로그램 플래시 시작 부분이 덮어써졌다.
- 원인: PSX GPU가 DDR3 0x34000000-0x343FFFFF를 render24 / 인터레이스 프레임 버퍼로 쓴다. ROM 이미지를 같은 0x34000000에 올렸다.
- 해결: ROM 이미지를 0x35000000으로 이동(0x34400000-0x3DFFFFFF가 비어 있고 세이브스테이트는 0x3E000000부터).
- 교훈: PSX 코어가 DDR3를 어디에 쓰는지 먼저 지도를 만든 뒤 영역을 배정한다.

### 1.3 4 MB RAM인데 데이터 캐시는 2 MB 기준 (4a49ad4)
- NS10 메인 RAM은 4 MB인데 CPU 데이터 캐시 태그와 DMA 캐시 주소가 2 MB 기준이라 위아래 2 MB가 겹쳐 보였다. 4 MB로 확장.

### 1.4 BIOS가 파란 화면 + `SYSTEM ERROR CODE=903` (fd08fe5)
- 증상: 파란 화면과 회색 사각형 4개, SIO1에 `spec77 ... CODE=903`, PC 0x68에서 RI 예외.
- 착오: 처음에는 ROM 보드(복호 / NAND)나 BIOS 이미지 생성 문제로 의심했다. Python 모델과 MAME가 비트 단위로 일치해서 ROM 쪽은 결백했다.
- 원인: NS10 BIOS는 kseg0(0x9FC2xxxx, 캐시 영역)에서 실행된다. PSX 코어의 i-cache 데이터 RAM은 SDRAM `ch1_cache` 버스트로만 채워지는데, BIOS 페치는 단일 읽기라 데이터는 안 쓰고 태그만 유효로 표시했다. BIOS 루프 두 번째 반복부터 엉뚱한 명령을 실행했다.
- 해결: BIOS 페치는 태그를 유효로 만들지 않음(비캐시와 동일). System573_MiSTer psx_patches/0005와 같은 버그. mrdrilr2j 어트랙트 진입.
- 교훈: 디버그 링(JTAG CPU 요청 트레이스, `ns10_trace`)으로 PC 흐름을 보는 것이 결정적이었다.

### 1.5 MEM(N) 게임이 NAND 테이블 검사에서 멈춤 (dfa2da4)
- 증상: mrdrilrg가 `yshi_nand_table_check ... the table for device 0 is wrong`에서 멈춤.
- 원인: MAME는 MEM(M)이 아닌 보드에서 0x1F500000-0x1F5FFFFF를 RAM("share3")으로 둔다. BIOS가 여기에 NAND 블록 표를 만들고 다시 읽는다. 이 영역을 구현하지 않았다.
- 해결: 16 KB SRAM(미러) + 바이트 레인(`exp1_be`)을 memorymux부터 최상위까지 연결. mrdrilrg 게임 진입.

## 2. 그래픽 기본 (2026-10-18)

### 2.1 mrdrilrg 그래픽이 크게 깨짐 (a708bdf)
- 원인: NS10의 CXD8561CQ는 VRAM 2 MB(1024줄)인데 PSX 코어는 Y를 512에서 감쌌다. CLUT 캐시 일관성 문제도 함께 있었다.
- 해결: 같은 PSX_MiSTer 기반인 System573_MiSTer의 GPU 패치 0012-0021 이식(CLUT 캐시 / rowlock, 10비트 Y, 512-1023줄은 DDR3 0x30800000). 패치 안의 디버그 상수는 끈 상태로.

### 2.2 480i → 480p 핵 옵션 (29105e9 추가 → 8450096 제거)
- 착오: 인터레이스 깜빡임을 줄이려고 PSX 코어의 480p 핵을 OSD에 넣었다.
- 결과: 512줄 버퍼와 그리기 추정 규칙을 쓰는 핵이라 2 MB VRAM 게임과 맞지 않았다(스프라이트 누락, 배경 비침, 줄만 보이는 그래픽).
- 해결: 옵션 제거, 대신 MiSTer 디인터레이스 Bob 사용.

## 3. CPU 속도와 터보 (2026-10-18 ~ 19)

### 3.1 13스테이지 슬로다운 (29105e9)
- 원인: NS10 CPU는 101.4912 MHz / 2 = 50.7456 MHz(PSX의 1.5배). 코어는 33.8688 MHz.
- 판단: 50 MHz CPU 클럭은 타이밍상 비현실적(PSX 코어 슬랙 0.1-0.3 ns). PSX 코어의 터보 모드를 OSD로 노출(기본 High). 사이클 정확하지 않다는 점은 사용자가 수용(MAME 동작이 기준).

### 3.2 터보를 켜자 I/O 쓰기가 RAM을 오염 (29105e9)
- 원인: 데이터 캐시(터보 Medium / High)가 워치독(0x1FB60000), 보드 RAM(0x1F500000) 같은 I/O / EXP 쓰기까지 받아서 RAM 줄에 별칭으로 기록했다.
- 해결: 0x800000 미만 RAM 쓰기만 캐시.

### 3.3 Cache Full에서 장면 전환 때 1-2 프레임 깨짐 (8450096 → 21a5eea)
- 착오 1: 처음에는 COMP 터보나 디인터레이스를 의심했다. COMP를 끄거나 Bob으로 바꿔도 그대로였다.
- 착오 2: 데이터 캐시의 오래된 데이터 경로를 의심해 코드 리뷰했지만 문제 경로가 없었다. 임시로 Turbo Cache Full / Half(/ Auto) 옵션을 두었다(8450096).
- 원인: PSY-Q libetc `VSync()` → `v_wait()`에 반복 횟수 타임아웃(`sll a1,a1,15`, 32768회)이 있다. MAME는 필드당 약 29000회를 쓰는데 Cache Full은 약 13% 빨라 vblank 전에 타임아웃 → 로딩 프레임 직후 필드 중간에서 화면 전환 → 그리기 목록이 vblank를 걸침.
- 해결: TURBO_CACHE 동안 명령어 0x00052BC0을 0x00052C00(시프트 16)으로 페치(i-cache 채움과 비캐시 페치 모두). 이 명령은 mrdrilrg / mrdrilr2 / gamshara / startrgn의 v_wait에만 한 번 있다. HW 트레이스: vblank 전 타임아웃 160 → 0. Cache Auto 모드 제거.
- 교훈: 프레임 단위 HW 트레이스(`ns10_gtrace`)와 MAME 탭을 나란히 비교해서야 원인이 보였다.

## 4. 사운드 (2026-10-18 ~ 19)

### 4.1 음이 낮고 느림 (5d5de28)
- 원인: NS10 SPU(CXD2938Q)는 101.4912 MHz / 2, 샘플당 768 클럭 = 66.15 kHz. 코어는 PSX 44.1 kHz(샘플당 768 clk1x)였다.
- 해결: 샘플 주기 512 clk1x.

### 4.2 그다음 주기적 끊김, 피치 흔들림 (5d5de28)
- 원인: 512 clk 예산으로 줄자 SPU가 오버런. mrdrilrg 리버브 작업 영역이 0x67FC0부터라 64 KB 온칩 리버브 BRAM 밖 → DDR3 비캐시 접근.
- 해결: 리버브 BRAM 128 KB(0x60000-0x7FFFF). 최대 밀린 샘플 15 → 1.

### 4.3 실패한 시도: SPU RAM을 SDRAM으로 (되돌림, 커밋 없음)
- SPUSDRAM=1(sdram ch3)로 옮겼더니 CPU 뒤 최저 우선순위 16비트 비캐시 접근이라 샘플당 최대 2600 clk, 항상 밀린 샘플 15.
- SDRAM 모드는 보이스 슬롯당 24 clk를 강제(576 > 512) → SPU가 한 번도 IDLE이 되지 않아 세이브스테이트 모듈이 부팅 중 리셋 반복(검은 화면, 오류 EF). 되돌림.

### 4.4 화면 좌상단 EA (7577f5b)
- 착오: 이전에는 "부팅 중 샘플 업로드 때만 생기고 소리는 정상"이라 보고 방치했다.
- 원인(JTAG 프로브로 실측): Gamshara가 로드 후 24-26초에 샘플을 업로드할 때 보이스 슬롯마다 RAM 쓰기가 끼어 샘플당 약 536 clk(예산 512, 평소 492-500). 밀린 샘플 15 초과 → 샘플을 버림 → EA.
- 해결: 밀린 샘플이 있으면 RAM 데이터 전송을 쉬고 먼저 따라잡음. SPU DMA는 FIFO가 빌 때만 다음 블록을 요청하므로 데이터 손실 없이 업로드만 조금 느려진다. 최대 밀린 샘플 15 → 1.
- 참고: 오버레이는 첫 오류 하나만 보여준다. 이후 보이는 ED(CPU 정지 512 사이클 이상, NS10 ROM 버스 대기)는 무해.

## 5. Star Trigon / Gamshara 480i 그래픽 (2026-10-19)

### 증상
- Star Trigon 어트랙트 일부가 0.2초마다 깜빡임, 스테이지 선택이 한 필드 + 검은 줄.
- Gamshara 캐릭터 선택 메뉴 누락, 타이틀 일부 깨짐.

### 잘못 짚었던 가정들
1. VSync 타임아웃 문제(3.3)의 재발 → CPU Turbo Off에서도 똑같이 깨져서 아님.
2. 2 MB VRAM 경로(10비트 Y, 텍스처 페이지 비트 11, 캐시 태그), 573 GPU 패치 옵션 → 모두 정상.
3. "MAME처럼 양쪽 필드를 다 그리면 된다" → 디버그 OSD Interlace Drawing MAME(21a5eea)으로 HW 테스트, 줄무늬가 찢어짐(tearing)으로 바뀔 뿐 해결 아님. 두 게임은 단일 버퍼 480i라서 표시 중인 필드의 줄을 건너뛰는 PSX 동작이 필수.
4. "MiSTer 성능 한계로 근본적으로 불가능한가?" → 아님. DDR3 대역폭이 아니라 코어 GPU가 DDR3 지연을 다루는 방식이 문제였다.

### 원인
- NS10 GPU 클럭은 50.7456 MHz(MAME), PSX GPU의 1.5배. 코어 GPU는 PSX 속도.
- `tools/gpumodel.py`(DuckStation 타이밍 모델): Gamshara 선택 화면 필드당 PSX 15.2 ms / NS10 10.2 ms, Star Trigon 최대 18.5 / 12.4 ms. 필드는 16.7 ms.
- 코어 GPU가 필드 안에 프레임을 다 못 그리면 필드가 바뀐 뒤 나머지가 반대 필드 줄에 그려졌다.
- 게임 패치 문제도, 코어 버그도 아닌 "GPU가 1.5배 느림" 문제.

### 해결 (3단계)
1. **Interlace Field Lock (03258f0)**: GPU, FIFO, GPU DMA가 모두 쉬고 있을 때만 그리기 패리티를 표시 필드에 맞춤. 넘친 프레임이 자기 필드에 계속 그림. 깜빡임은 사라졌지만 일부 아티팩트가 남음.
2. **텍스처 미스 버스트 (cba4156)**: 미스 한 번에 캐시 줄의 나머지 블록까지 한 번의 DDR3 지연으로 채움. Star Trigon 전부, Gamshara 선택 화면 해결. Gamshara 타이틀은 여전히 프레임 17.9 ms.
3. **다중 줄 텍스처 페치 (eda46d1)**: 미스 때 같은 캐시 블록의 다음 텍스처 줄 3개까지 연속 요청(인터레이스면 2줄 간격, 직전 미스가 바로 아래였으면 위 방향 = 뒤집힌 텍스처). 시뮬레이션: 타이틀 17.73 → 14.11 ms, 선택 화면 12.90 → 11.37 ms, VRAM 픽셀 동일. 사용자 확인: 모든 그래픽 정상.

### 이 과정의 착오
- 버스트 채움만으로는 작은 스프라이트(16텍셀 폭)가 많은 타이틀에서 오히려 약간 느려졌다(쓰지 않는 블록까지 읽음). 줄 단위가 핵심이었다.
- 첫 다중 줄 구현은 아래 방향만 읽어서, Gamshara 선택 화면의 뒤집힌 텍스처 폴리곤(op 2E)은 미스가 줄지 않고 오히려 느려졌다. 시뮬레이터 요청 로그로 y가 감소하는 것을 보고 방향 감지를 추가.
- 첫 빌드는 셋업 타이밍 -1.014 ns 실패: 전체 비트 수 = 줄당 비트 × 줄 수 곱셈을 DDR3 BUSY 경로에 넣었다. 곱셈을 빼고 줄마다 비트 카운터를 다시 적재하는 방식으로 바꿔 통과(커밋 전에 수정).
- 그 사이 HDMI PLL 슬랙이 -0.234 ns까지 나빠진 빌드가 있었다(MiSTer 프레임워크 영역, 배치 변동). 다음 빌드에서 +0.140 ns로 회복.

### 도구 쪽 착오
- GPU 트레이스 자동 저장(`/media/fat/ns10_gtwatch.py`)이 START 워드만 비교해서, 코어를 다시 로드하면(같은 run 1) 새 트레이스를 이미 저장한 것으로 보고 건너뛰었다. 앞 256바이트 비교로 수정.
- ModelSim 시뮬레이션이 필드당 20분 이상 → GHDL(MSYS2 LLVM)로 전환해 약 2-3분. GHDL 6.0.0-1 패키지가 설치된 LLVM 22와 안 맞아 6.0.0-3으로 교체, GHDL의 엄격한 범위 검사에 걸리는 부분은 시뮬레이션 전용 복사본(`sim/gpu/gen.sh`)에서만 우회.
- ModelSim 라이브러리 이름과 비교용 원본 폴더 이름이 같아 원본 파일이 지워진 적이 있다 → `sim/gpu/ref/`로 분리.
- 시뮬레이터의 DDR3 지연을 HW 트레이스와 맞춰(지연 8) 시뮬레이션 결과를 실기 예측에 쓸 수 있게 했다.

### 함께 사라진 증상
- MiSTer 소프트 리부트 후 Gamshara 실행 시 파란 줄과 그래픽 정지(소리는 정상)가 가끔 있었다. GPU 속도 개선 빌드 이후 여러 번 리셋하고 코어를 바꿔도 재현되지 않았다. GPU 과부하의 부작용으로 추정(재발 시 다시 조사).

## 교훈 요약
- **MAME를 기준으로, 비트 단위로 비교한다.** ROM 보드는 Python 모델 + MAME 트레이스 재생(불일치 0)으로 HW에 올리기 전에 검증했기 때문에, 부팅 문제를 CPU / 메모리 쪽으로 빨리 좁힐 수 있었다.
- **NS10은 PSX보다 1.5배 빠른 기계다.** CPU(50.7 MHz), GPU(50.7 MHz), SPU(샘플당 768 clk @ 50.7 MHz) 모두 같은 구조의 문제(13스테이지 슬로다운, v_wait 타임아웃, GPU 필드 초과, SPU 오버런)를 만들었다. 코어 클럭을 올리는 대신 병목(캐시, DDR3 지연, 대기)을 줄이는 방향이 통했다.
- **추측보다 측정.** HW 트레이스(`ns10_gtrace`), JTAG 프로브(SPUT), MAME 탭, GPU 시뮬레이터(GHDL)로 숫자를 본 뒤에야 원인이 확정됐다. 측정 없이 넣은 옵션(480p 핵, Interlace Drawing MAME, Cache Auto)은 모두 제거됐다.
- **시뮬레이션으로 결과 동일성을 확인한 뒤 빌드한다.** GPU 변경은 매번 VRAM 픽셀 동일을 확인하고 빌드해서, 실기에서 회귀가 없었다.
