# Mr. Driller G AI 플레이어(TAS 봇) 계획과 조사 결과

## 1. 목표
- GroovyMAME(일반 MAME 포함)에서 RAM을 읽어 사람이 못 하는 수준(TAS)으로 플레이하는 봇. 이후 MiSTer OSD "TAS" 항목으로 오토파일럿(사용자 입력 무시). 이후 2P 봇.
- 데모 화면부터 코인, 스타트, 스테이지/캐릭터 선택, 플레이, 랭킹 이름 입력("TAS")까지 사람 없이 진행.

## 2. 결정 사항 (2026-10-29 사용자 승인)
- 강화학습/신경망 대신 탐색(beam search) + 점수식 기반 평가 함수. 가중치는 자동 대량 실행으로 튜닝.
- 매 프레임 RAM을 보고 다시 판단하는 폐루프 방식(MiSTer는 MAME와 사이클 단위로 같지 않으므로 입력 기록 재생은 어긋남).
- 순서: MAME 실시간 봇 먼저, India로 검증 후 North. 계획기 언어는 C(MiSTer ARM에서도 실행).
- 봇은 RAM을 읽고 입력만 넣는다(RAM 쓰기는 테스트용). 봇 실행은 별도 nvram 폴더(사용자 랭킹 보호), 세이브 상태는 복사본만 사용.
- 플레이어 번호를 인자로 받는 구조(2P 봇 대비, 플레이어 구조체 간격 0x1B4).
- 최종 봇은 맵 시드 난수 조작을 하지 않는다. 어떤 맵이 나오든 그 맵에서 최고 수준의 점수와 플레이를 보여주는 것이 목표다. 난수 조작은 테스트할 때 다양한 맵 데이터를 얻는 용도로만 쓴다(사용자 결정 2026-10-29).

## 3. 단계
| 단계 | 내용 | 통과 기준 |
|---|---|---|
| 0' | 맵 생성/난수, 그리드 범위, 특수 블록, 플레이어-블록 상호작용 조사 | RAM만으로 화면 재구성, 맵 고정 여부 판정 |
| 1 | Lua 규칙 기반 봇 + 화면 상태 기계(데모~이름 입력) | India 노미스 반복 클리어, 기준선 기록 |
| 2 | C 게임 모델 + beam search, 퍼징 도구로 MAME와 대량 비교 | 모델 = MAME, 2000m 전 캡슐 노미스 |
| 3 | 세이브 상태 분기 오프라인 TAS + 시드(맵) 선택 | 실시간 봇과 격차 측정 |
| 4 | MiSTer: RAM 창을 DDR3로 미러링, ARM 데몬 계산, 입력 주입, OSD TAS | 실기에서 MAME 봇과 같은 수준(디버그 빌드) |

평가 함수 핵심: 캡슐 전부(하나 놓치면 약 60,000점 = 약 120초)와 노미스(목숨 30,000점 = 60초)는 필수 조건. 시간 보너스는 1프레임 8.3점, 연쇄 1칸 30점 = 3.6프레임. 블록/연쇄 점수는 레벨당 3만~5만이라 파기 순서를 골라 연쇄를 적극적으로 만든다.

## 4. 조사 결과 (2026-10-29, GroovyMAME 원본 mrdrilrg)
### 4.1 스테이지 전체 맵이 스테이지 시작 때 RAM에 있다
- 주소 0x8031B8C0, 1줄 = 필드 폭 W 바이트, 줄 n = 0x8031B8C0 + n*W, 1줄 = 1m.
- W: India 7(500줄), America 9(1000줄), Egypt/North 15(2000줄). 벽은 열 0과 열 W+1(종류 0x0801).
- 그리드(0x80326C48, 32줄, 줄 1936B, 칸 88B)는 링 버퍼가 아니라 플레이어를 따라 움직이는 창이다. 플레이어가 한 줄 내려가면 줄을 한 칸씩 위로 복사하고 맨 아래 줄 31을 새로 채운다(위로 올라가면 반대). 그리드 줄 r = 게임 줄 (깊이 + r - ([0x80369EB0] + 1)). India는 0x80369EB0 = 17이라 게임 줄 = 깊이 + r - 18(깊이 = P+0xF4). 서 있는 플레이어는 그리드 줄 17, 발밑이 줄 18. Egypt/North는 시작 때 줄 20에 게임 줄 0이 있었다(0x80369EB0 = 19로 추정, 확인 필요). India 600개 덤프에서 손대지 않은 줄 6943개가 이 식과 정확히 일치(나머지는 떨어져 쌓인 블록 1칸, 레벨 구분 블록 줄).
- 줄 채우기(버퍼 → 그리드) 코드: 모드표 0x80030008(인덱스 = 모드-10)로 스테이지별 해독 함수를 고른다. India 0x8020B164(값표 0x801DA48C), America 0x802095D0(값표 0x801DA3DC), Egypt/North 0x80208550(값표 0x801DA364). 아래로 스크롤 함수 0x801E5204가 그리드 줄 31에 버퍼 줄 (깊이 + 31 - [0x80369EB0])을 해독해 넣는다(이 시점의 깊이는 갱신 전 값).
- 값 → 그리드 종류(u16 +0x2A), 코드로 확인:

| 값 | 블록 | 종류 |
|---|---|---|
| 0~3 | 색 블록 4가지 | 0x0F0E + 값 |
| 4 | X블록 | 0x0B0D (0x801E84C4) |
| 5 | 산소 캡슐(23%) | 만들 때 2, 그리드에서는 0x0003 |
| 6 | 크리스탈(별 무늬, 레벨마다 색이 다름) | 0x0F12 (0x801E865C) |
| 7(India, Egypt, North) / 19(America) | 화이트 블록(베이지색 둥근 별, 아무 블록과도 붙지 않음, 사용자 확인) | 0x0C13 (0x801E8594) |
- 레벨 구분 큰 블록: 종류 0x6F15, 높이 7줄 x 필드 전체 폭, 100m 경계 직전(약 93~99줄)에 그리드 줄을 채울 때 끼워 넣는다(맵 버퍼에는 없음).
- 시작 영역: 맨 위 7줄(India, America) / 6줄(Egypt, North)은 맵 버퍼 대신 고정 무늬로 채워지고, 그 안에 캡슐이 1개 있다(4스테이지 모두 확인). 맵 버퍼의 해당 줄에는 캡슐이 없다.

### 4.2 맵은 스테이지 시작 순간 고정되고, 확정 버튼 프레임으로 바뀐다
- 같은 스테이지 시작 세이브에서 서로 다른 입력 두 가지로 134m까지 플레이: 손대지 않은 줄 141개 일치, 다른 줄은 모두 1칸 차이(떨어져 쌓인 블록). 즉 플레이는 맵을 바꾸지 않는다.
- 캐릭터 선택 세이브(6)에서 확정 버튼을 0, 1, 2, 3, 7, 31프레임 늦게 누르면 맵 해시가 모두 다르다. 1프레임 차이로 맵이 완전히 바뀐다.
- 의미: 시작 순간 전체 맵을 읽어 경로를 미리 계산할 수 있다. 확정 프레임을 골라 맵을 선택하는 난수 조작도 가능하지만, 최종 봇은 쓰지 않는다(어떤 맵이든 최고 수준으로 플레이하는 것이 목표). 난수 조작은 테스트 데이터 수집용.

### 4.3 산소 캡슐 수
- 맵 버퍼(시작 영역 뒤)의 캡슐 수 India 55, America 79, Egypt 103, North 103 + 시작 영역 캡슐 1개 = 56 / 80 / 104. 퍼펙트 에어 조건(0x8020CF2C: 먹은 수 < 56 / 80 / 104 이면 실패)과 정확히 같다. 즉 퍼펙트 에어 = 맵의 캡슐을 하나도 빠짐없이 먹기.
- 사용자 공략: X블록에 둘러싸인 캡슐은 X블록도 4개 이상 붙으면 사라지는 점을 이용해(블록을 떨어뜨려 X블록끼리 붙게 함) 없애서 먹고, 산소가 충분하면 X블록을 직접 파서 시간을 아낀다. 봇의 캡슐 경로 탐색에 두 방법을 모두 넣는다.

### 4.4 사용자 제보 버그
- 캡슐 재생성(사용자 제보, 원리는 코드로 확인, 실제 재현은 아직): 계단식 블록을 만들어 아래 캡슐을 먹고 10~13칸 이상 올라갔다 내려오면 캡슐이 다시 생긴다(푸치는 2칸 오르기로 쉬움).
  - 원리: 위로 스크롤 함수 0x801E53BC는 그리드 줄을 한 칸씩 아래로 옮기기만 하고 맨 아래 줄 31은 저장 없이 버린다. 다시 내려가면 0x801E5204가 그 줄을 맵 버퍼에서 새로 해독한다. 맵 버퍼는 플레이 중 한 번도 쓰이지 않는다(쓰기 탭 2400프레임, 캡슐 3개 먹는 동안 쓰기 0회). 그래서 그리드 맨 아래 밖으로 밀려난 줄은 처음 상태(캡슐, 파낸 블록, 연쇄로 사라진 블록 모두)로 돌아온다.
  - 플레이어는 항상 그리드 줄 17에 있으므로 캡슐을 먹은 줄(줄 17)이 줄 31 밖으로 밀려나려면 15칸 올라가야 한다(계산값). 사용자 기억은 10~13칸이라 실제 재현으로 확인한다.
  - 캡슐 점수가 k x 100으로 커지므로 점수 상한이 사실상 없어진다. 버그를 쓰지 않는 설정에서도 게임 모델은 "멀리 올라갔다 내려오면 아래 줄이 원래대로 돌아온다"를 반영해야 한다.
- 좀비 드릴러(우주 스테이지): 산소 0%대에서 화면 90도 회전 아이템을 먹으면 산소가 줄지 않는다. 50000m 이상에서 블록이 더 생성되지 않고 계속 떨어진다는 보고(미확인).
- 버그 이용 여부는 봇 설정(버그 없음 / 버그 사용)으로 나눌 예정.

### 4.5 화면 흐름(장면 번호)
- 장면 번호 0x802D80A8(u32), 선택 화면 보조 단계 0x802AC9C0, 게임 모드 0x80369B38. 새 nvram으로 전원을 켜고 코인 → 1P 스타트 → 버튼 1을 60프레임마다 눌러 확인(flowprobe.lua, 같은 입력이면 프레임까지 똑같이 재현된다).

| 장면 | 화면 | 모드 |
|---|---|---|
| 0 | 부팅(FIRST POWER ON, 경고문) | 0 → 1 |
| 1 | 타이틀(namco 로고, 데모) | 1 |
| 2 | 코인 투입 직후 | 1 |
| 12 | SELECT A MENU(1人でドリラー 등) | 1 |
| 18 | 메뉴 → 캐릭터 선택 전환(보조 단계 0~4) | 1 |
| 13 | SELECT A DRILLER, SELECT A STAGE(스테이지 커서 기본값 America) | 1 |
| 7 | 플레이(모드 11/12/13) → 게임 오버 뒤 결과 화면(RESULT, 모드 1) | 11~13 → 1 |
| 10 | RANKING 표시 | 1 |
| 11 | GAME OVER(패스워드 화면) → 장면 1로 돌아감 | 1 |

- 입력 이름: :IN1 의 "Coin 1", "1 Player Start", "P1 Button 1"(드릴/결정), "P1 Up/Down/Left/Right".
- 장면 18의 보조 단계(0x802AC9C0): 2 = SELECT A DRILLER(30초 제한), 3 = 캐릭터 확정, 4 = 전환. 장면 13 = SELECT A STAGE. 클리어하면 장면 8(스테이지 클리어 결과) → 22(이름 입력) → 17.
- 캐릭터 커서 0x802AC980: 육각형 고리. 시계 방향 이동 = 0 →(오른쪽) 1 →(오른쪽/아래) 3 →(아래) 5 →(왼쪽) 4 →(왼쪽/위) 2 →(위) 0. 반대 방향: 1 →(왼쪽) 0, 3 →(위) 1, 2 →(위) 0. 입력 후 3프레임에 바뀐다. 커서 번호 = 캐릭터 번호(0 스스무, 1 안나, 2 푸치 화면 확인, 4 타이조는 플레이 중 0x802EF0E8 = 4, P+0xAC = 3, P+0xB0 = 288로 확인). 0x802EF0E8은 플레이가 시작된 뒤에 써진다.
- 스테이지 커서 0x802D80BC: 0 = 우주(SPACE, 엔드리스), 1 = 북극(THE NORTH), 2 = 아메리카(기본값), 3 = 이집트, 4 = 인도. 왼쪽/오른쪽으로 1씩, 끝에서 멈춘다(순환 안 함). 사용자 정보: 위 = 왼쪽, 아래 = 오른쪽.
- 랭킹 등록 조건(실험): 깊이가 먼저, 같은 깊이(클리어)면 점수. 317m 17,500점이 10위 300m 39,000점보다 위(9위)에 들어갔고, 48m 203,550점은 들어가지 못했다. 사용자 경험(점수로 비교)은 클리어 기록끼리의 비교와 맞는다.
- 이름 입력(장면 22): 0x803BE724~726 = 이름 ASCII 3글자(처음 공백), 0x803BE72C = 입력한 글자 수, 0x803BE730 = 글자 커서(A = 0, 오른쪽 +1, 왼쪽 -1), 0x803BE73C = 남은 시간(프레임, 약 45초), 0x803BE720 = 기록 중인 랭킹 레코드 이름 주소. 버튼 1 = 글자 확정. 3글자를 넣으면 자동으로 끝난다. nametest.lua로 사용자 세이브 r(India 클리어)에서 "TAS" 입력 → 랭킹 1위에 TAS로 기록되는 것 확인(별도 nvram 폴더 사용).

### 4.6 무인 흐름 제어(drgbot.lua, 1단계 첫 부분)
- 전원 켜기부터 사람 입력 없이: 코인 → 1P 스타트 → 메뉴 → 캐릭터(커서 고리를 시계 방향으로 이동) → 스테이지(커서 비교) → 플레이 → 결과/랭킹/엔딩은 Start로 넘김(사용자 정보: 애니메이션, 카운트다운, 랭킹, 엔딩은 Start로 건너뛸 수 있다) → 이름 입력 "TAS" → 타이틀 → 다음 판.
- 시험(2026-10-29, 새 nvram, India + 타이조, 플레이는 임시 아래 파기 + 테스트용 산소 고정): 2판 모두 클리어, 랭킹 1, 2위에 TAS로 기록, 실제 시간 61초(2판).
- 플레이 부분(play 함수)은 아직 임시 코드다. 다음 단계에서 계획기로 바꾼다.

### 4.7 측정값
- GroovyMAME 헤드리스(-video none -nothrottle) 약 570% = 약 340fps.

## 5. 남은 조사
- 맵 생성기와 난수 함수 재구현은 우선순위를 낮춘다. 최종 봇은 난수 조작을 하지 않고(사용자 결정 2026-10-29) 스테이지 시작 때 맵 버퍼를 읽으면 충분하다. 난수 조작은 테스트용 다양한 맵 수집에만 쓴다(seedprobe.lua).
- 캡슐 재생성 버그 실제 재현(크래프트한 계단 + 캡슐).
- 크리스탈이 사라지는 타이머/조건, 화이트 블록이 붙지 않는 처리, X블록 타격 수 필드.
- 플레이어-블록 상호작용(깔림, 슬라이딩, 업어가기, 오르기 조건), 화면 상태(데모, 선택, 이름 입력) RAM 값.

## 6. 스크립트
- tools/drgai/g1probe.lua: 그리드 덤프(OB_STATE, OB_BR 입력 갈래, OB_EVERY, OB_ROWS).
- tools/drgai/seedprobe.lua: 캐릭터 선택에서 OB_WAIT 프레임 뒤 확정, 스테이지 시작 시 맵 해시 기록.
- docs/drillerg-analysis/lua/dump.lua: RAM 4MB 덤프.
- tools/drgai/rtap.lua: 주소 범위 읽기 탭(OB_A0, OB_A1), OB_W=1이면 쓰기 탭. g1probe.lua에 OB_SNAP=1(덤프마다 스크린샷) 추가.

- tools/drgai/nametest.lua: 이름 입력 자동화(RAM 커서를 읽어 목표 글자로 이동).

## 5. 블록 규칙과 1차 규칙 봇 (2026-10-29 후반)

### 5.1 블록 상태와 시간 (덤프로 측정)
- 칸 필드: +0x00 상태, +0x2A 종류, +0x39 사라짐 타이머, +0x3C 흔들림 타이머, +0x42 낙하 오프셋(부호 있음).
- 상태: 4 정지, 3 흔들림(타이머가 0까지 줄면 낙하), 1 낙하, 2 낙하 중 줄 바뀜 1프레임, 5→6 연쇄 사라짐(각 15프레임, 합 30), 8→9→10 판 칸 사라짐(5+10+1 = 16프레임), 7/12 레벨 클리어 때 얼어붙은 칸(구분 블록은 7).
- 낙하: 블록은 새 줄에 바로 들어가고 오프셋 약 9088에서 낙하 속도만큼 0까지 줄어든다. 그려지는 위치 = 줄 - 오프셋/10240. 플레이어는 블록이 줄 17에 다 내려온 순간(오프셋 0) 깔린다.
- 흔들림 시간 P+0x15C = 70프레임, 낙하 속도 P+0x15E = 1152(초반) → 1280 → 1536(깊은 곳) /프레임, 한 줄 = 10240.
- 플레이어 상태 P+0xD8: 7 = 깔림 또는 공기 0 (죽음 첫 프레임), 8/9 = 죽음 연출. (예전 문서의 "7 = air 0"은 틀림)
- 연쇄 사라짐 중인 칸(5/6)에는 걸어 들어갈 수 없다. 판 칸(8/9/10)에는 바로 들어갈 수 있다.
- 흔들리는 블록도 아래로는 팔 수 있다(3→8 10회 관찰). 옆으로 흔들리는 블록을 파려 한 1회는 실패(확인 필요).
- 공기 P+0x160(50000 = 0%, 150000 = 100%): 기본 감소 24/30/37/40 per frame (0-200m / 200-300 / 300-400 / 400-500m, India). X 블록 1개 = 약 -20800을 20프레임에 걸쳐(-1040/frame), 캡슐 = +20000을 20프레임에 걸쳐.

### 5.2 지지(붙음) 모델 - 게임과 대조해 확인
- 같은 종류(전체 u16)끼리 상하좌우로 붙어 한 덩어리가 된다. 색 블록, X 블록끼리, (수정, 구분 블록도 같은 규칙으로 둠). 캡슐과 흰 블록은 혼자.
- 덩어리는 칸 하나라도 바로 아래에 "지지된 다른 덩어리"가 있으면 지지된다. 맨 아래 줄 31과 맨 위 줄 0(창 밖은 모름)은 지지로 본다. 사라지는 중인 칸(5,6,8,9,10)과 얼어붙은 칸(7,12)은 고정된 지지다. 사라짐이 끝나면 그 위 덩어리는 다음 프레임에 흔들리기 시작한다.
- 대조 결과: India 2400프레임 흔들림 시작 323개 예측 일치, 오탐 0, 놓침 15(모두 창 맨 위 줄 0-1). America 497개 일치, 오탐 1, 놓침 24(모두 줄 0-1).
- 구현: tools/drgai/blockmodel.lua (덩어리, 지지, 낙하 시작 시각, 칸 (r,c)에 블록이 도착하는 프레임 수 = danger_map).
- 사용자 제보 규칙(아직 모델에 없음, 확인 필요): 흔들리는 블록의 지지 블록을 다시 파면 다시 흔들린다(지붕 없이 버티기, X로 둘러싼 캡슐 패턴 깨기에 씀). 위 블록이 착지한 직후 약 2프레임 안에 그 아래를 파면 흔들림 없이 바로 떨어진다. X 블록에 둘러싸인 캡슐 아래가 X가 아니면 그 아래를 미리 파고 계속 내려가면 캡슐이 흔들린 뒤 떨어져 먹어진다. 같은 색 덩어리 아래는 "지붕"이라 안전하다.

### 5.3 데모 화면
- 데모 = scene 6, mode 21(목표 50000, Space). 데모는 개발자가 녹화한 입력 재생이다: 플레이어 열 아래를 X 블록으로 바꿔도(1m에서 막힘, 원래는 23m) 방향 바뀜 프레임(328, 339, 390, 427, 460, 478, 616)이 그대로였다. 맵 버퍼 0x8031B8C0을 섞어도 데모는 영향 없음(데모 지형은 다른 곳에서 온다). 게임 안에 참고할 AI 루틴은 없다.

### 5.4 1차 규칙 봇 (tools/drgai/play_rule.lua, drgbot.lua OB_PLAY=rule)
- 매 프레임 그리드를 읽고 blockmodel로 칸마다 도착 시간을 계산한다. 위험(T<40)이면 옆으로 피함(걷기, 옆 색 블록 파기), 안 되면 아래로 파기. 평소에는 줄 17-31에서 다익스트라(걷기 12.3, 낙하 10240/속도, 파기 8, X = 5회 파기 + 공기 20%를 현재 감소 속도로 바꾼 프레임). 목표 = 공기 값(20000/감소)보다 싼 가장 가까운 캡슐, 없으면 30*줄 - 비용이 가장 큰 칸.
- 평가: OB_CDELAY(시험용, 확인 프레임 지연 = 다른 맵) 12개 맵, Taizou: 클리어 5/12, 깔림 26회, 공기 0 8회, 평균 깊이 약 405m, 클리어 평균 타이머 약 10500. (처음 배치 봇은 39m에서 깔림)
- 남은 깔림의 대부분: 떨어지는 덩어리가 플레이어를 따라 아래로 쫓아오는 경우(아래로 계속 파면 같은 속도로 따라옴), 옆 칸으로 걷는 중 깔림. 프레임 단위 반응 규칙으로는 한계 → 다음 단계는 블록 모델 + 플레이어 움직임 시뮬레이션으로 몇 초 앞을 탐색하는 계획기(원래 계획의 2단계, C).
- 알려진 문제: OB_CHAR는 커서 위치라 캐릭터 id와 다르다(OB_CHAR=2 → id 5, 3 → id 2 Puchi). 수정 필요.
