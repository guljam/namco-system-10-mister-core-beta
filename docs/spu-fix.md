# SPU 클럭 예산과 오버런 - 현황 및 개선안 (A / B)

작성 기준: 2026-10-20 정적 검토. 코드 변경 없음. 하드웨어/타이밍 리포트로 검증된 내용이 아니라
`rtl/spu.vhd`, 메모리 기록(`spu-ea-fix`, `ns10-hw-findings`)에 근거한 분석이다.

## 1. 배경

- NS10 실기 SPU(CXD2938Q)는 101.4912 MHz / 2 ≈ 50.75 MHz에서 샘플당 768클럭, 약 66.07 kHz
  (`rtl/spu.vhd:1472` 주석). PSX SPU는 33.8688 MHz에서 768클럭, 44.1 kHz. 즉 같은 구조에서 클럭이 1.5배다.
- 코어 SPU는 전체가 `clk1x`(33.8688 MHz)에서 돈다. 여기서 768클럭을 쓰면 44.1 kHz가 되어
  소리가 늘어지고 피치가 낮아진다(초기 PSX 구조 그대로 사용했을 때의 증상).
- 그래서 샘플당 클럭을 512로 줄였다 (`spu.vhd:918`, `:1899`). 33.8688 MHz / 512 = 66.15 kHz로
  실기(66.07 kHz)와 0.1% 차이이며 음정상 구별되지 않는다. **샘플레이트 측면에서 512는 올바른 선택이다.**

## 2. 현재 문제와 그 원인

| 항목 | 내용 |
|---|---|
| EA 오류 | SPU가 15샘플 넘게 밀리면 래치. Gamshara 샘플 업로드 시 발생. 7577f5b로 해결 (샘플이 밀려 있는 동안 RAM 전송 중지). 프로브 기준 최대 밀림 15 → 1. |
| 남은 오버런 | GPU 부하 시 초당 약 80회, 1샘플 수준. 메모리 기록상 청취 불가. |
| 근본 원인 | PSX SPU 상태기계는 idle에서도 샘플당 약 492~500클럭을 사용. 768 예산에서는 여유가 있었으나 512 예산에서는 거의 없음. 부하가 조금만 늘어도 한두 샘플 밀림. |

512클럭은 클럭을 올리지 않는 한 피할 수 없는 교환이다: 샘플레이트는 맞추고, 샘플당 연산 예산은 실기의 2/3가 된다.

## 3. 입력지연과의 관계 (같이 논의된 내용)

- SPU는 Key-On 후 1샘플(약 15~23 µs) 안에 발음한다. 소리 지연은 SPU가 아니라 게임 사운드 드라이버와
  MiSTer 오디오 출력 버퍼에서 생긴다.
- 1샘플 오버런은 위상 오프셋이 아니라 샘플 손상(반복/드롭) 문제이며, 화면과의 동기에 영향을 주지 않는다.
- Driller G의 평균 3프레임 입력지연은 게임의 프레임 파이프라인(입력 → 로직 → GPU 그리기 → flip) 구조 때문이며,
  SPU 개선과 직접 관련이 없다.

## 4. 개선안

실기와 같은 연산 예산(768클럭 / 샘플)을 확보하려면 SPU 클럭을 올려야 한다.

### 안 A - SPU를 `clk2x`(67.7376 MHz)에서 구동, 샘플당 1024클럭

- 67.7376 MHz / 1024 = 66.15 kHz, 샘플레이트 동일.
- 예산이 512 → 1024클럭으로 2배. 현재 사용량(약 500) 대비 약 2배 여유 → 오버런이 사실상 사라질 것으로 예상.
- 상태기계의 샘플당 사용 클럭은 그대로이므로 로직 변경이 적다.
- 필요 작업:
  1. SPU 레지스터 접근(CPU 버스 `clk1x`) 경계: `clk1x`/`clk2x`는 위상이 맞는 배수 클럭이므로
     이미 포트에 있는 `clk2xIndex`로 핸드셰이크 처리 가능.
  2. SPU RAM / DMA 경로가 `clk1x`에 묶여 있는지 확인 (`spu.vhd`에 `inclock => clk1x` 다수) - 경계 처리 범위 결정.
  3. 67.7 MHz 타이밍 만족 여부 (곱셈기: ADPCM, ADSR, 리버브 경로).
- 위험: 중간. 타이밍 클로저가 첫 관문.

### 안 B - `clk3x`(약 101.6 MHz)에서 구동, 2클럭마다 enable (약 50.8 MHz), 샘플당 768클럭

- 실기 클럭(50.75 MHz)에 가장 가까움. 샘플당 768클럭이라 PSX 원본 코드의 타이밍 가정을 그대로 유지.
- 예산이 실기와 동일(768). 안 A보다 여유는 작지만 **실기와 같은 조건**이다.
- 필요 작업:
  1. enable 기반 멀티사이클 경로 제약(SDC) 작성 - 레지스터 사이 2클럭 허용 경로 명시.
  2. 안 A의 1~2번과 같은 경계 처리 (`clk3x` 도메인 기준).
- 위험: 높음. 101 MHz에 걸리는 경로의 타이밍 클로저와 제약 정확성이 부담.

### 안 비교

| | 현재 | 안 A | 안 B |
|---|---|---|---|
| SPU 클럭 | 33.87 MHz (`clk1x`) | 67.74 MHz (`clk2x`) | ~50.8 MHz (`clk3x` / 2) |
| 샘플당 클럭 | 512 | 1024 | 768 |
| 연산 예산 (대 현재) | 1.0x | 2.0x | 1.5x |
| 실기 구조 일치 | 샘플레이트만 | 샘플레이트만 | 클럭/예산 모두 |
| 로직 변경 | - | 적음 | 적음 (+ SDC) |
| 타이밍 위험 | - | 중간 | 높음 |

### 그 외 (참고)

- 샘플당 작업 사이클 자체를 줄이는 방법(RAM 읽기와 보이스 처리 겹치기 등)은 클럭을 올리지 않고도
  여유를 만들 수 있으나 A/B와 별개 방향이며 비트 정확성 회귀 검증이 필요하다.
- 일부 보이스/리버브를 격 샘플로 처리하는 방법은 실기 동작과 달라져 부적합하다.

## 5. 권장

- **현재는 건드리지 않는다.** 남은 1샘플 오버런은 청취 불가이며, EA는 해결되었다.
- 다시 올릴 조건: 플레이 중 클릭음, 다른 게임에서 EA 재발, 또는 SPU 부하를 늘리는 기능 추가.
- 진행한다면 **안 A 우선**. 순서:
  1. 현재 빌드의 타이밍 리포트에서 SPU 경로 슬랙 확인 (67.7 MHz 가능 여부).
  2. 가능하면 안 A 구조 변경, 불가능하면 안 B 또는 사이클 절감 방향으로 전환.
  3. 검증: `python tools/ns10trace.py spu`로 최대 밀림 값, Gamshara 업로드 구간(코어 로드 후 약 24~26 s) 재생.

## 6. 미확인 사항

- NS10 SPU 클럭 값의 MAME 소스 대조는 이번에 하지 않았다 (`spu.vhd:1472` 주석과 메모리 기록에 의존).
- SPU RAM 및 DMA 경로의 실제 클럭 도메인 구조.
- 67.7 MHz / 101.6 MHz에서의 SPU 경로 타이밍 슬랙.

## 7. 구현 결과 (2026-10-21, 안 A, 브랜치 spu-fix)

- 안 A로 구현했다. SPU 전체가 clk2x, 샘플당 1024클럭. 자세한 내용은 `docs/fixes-2026-10-21.md`의 "SPU를 67.7 MHz(clk2x)로 이동" 절에 있다.
- 6절의 미확인 사항: SPU RAM / DMA 경로는 SPU와 함께 clk2x로 옮겼다(CPU 버스 / DMA 입력만 clk1x 경계). 67.7 MHz 타이밍은 전체 빌드에서 만족한다(디버그 빌드 기준).
- 실기: 4게임 각 2분, 드롭 0, 최대 stash 1. Star Trigon 부팅 드롭(이전 135)이 없어졌다.
