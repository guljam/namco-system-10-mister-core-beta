# 2026-10-22 수정 기록: Mr. Driller 2 데모 장면 전환 끊김 / 소리 멈칫 (ROM 버스 대기)

브랜치 `rom-bus` (spu-fix 89163cd에서 분기). 실기 확인 완료(사용자 육안/청취 + 트레이스).

## 증상

- mrdrilr2j 어트랙트 데모, 바이오스 화면 기준 실기 1:03~1:15 (MAME 1:02~1:08)에서 두 번 끊긴다.
  1. 실루엣 캐릭터(초록 배경) 등장: 아주 미세한 끊김.
  2. 새 캐릭터(하늘색 로봇) 등장: 화면 스터터링 + 소리가 미세하게 멈칫.

## 원인

### 게임이 그 순간 하는 일 (MAME로 확인)

- 스토리 데모의 장면 전환마다 게임은 플래시 ROM(EXP1, 0x1F400000 MEM(M) 뱅크 창)에서 그래픽을
  `lw` 복사 루프(PC 0x8017B668)로 한 번에 읽는다. 실루엣 장면은 16,528워드, 새 캐릭터 장면은
  30,856워드를 읽고, 바로 이어서 또 한 번 30,856워드를 읽는다(두 번 연속인 곳은 여기뿐이다).
- 데모의 소리는 키온이 아니라 **스트리밍**이다. SPU IRQ 핸들러가 RAM 링버퍼에서 SPU로
  DMA4(256워드 x 2, 약 55 ms 간격)하고, 링버퍼는 메인 루프가 플래시 bank 4에서 512워드씩 채운다
  (PC 0x8016221C). 이 채우기는 대량 복사가 **끝난 뒤에** 실행된다.
- 그래서 대량 복사가 길어지면 (a) 화면 갱신(GP1(05))이 여러 프레임 빠지고, (b) 링버퍼 채우기가
  늦어져 소리가 멈칫한다.

### 코어가 MAME보다 느렸던 이유

- 게임은 EXP1 버스 지연을 `1F801008 = 0x2F1730FF`로 설정한다(읽기 지연 RDelay 15, 16비트 폭).
- MAME psxcpu는 이 지연을 전혀 계산하지 않는다(읽기 비용 0).
- 코어 memorymux는 PSX 방식대로 33.8688 MHz에서 15클럭 + 1을 16비트 읽기마다 넣고, 그 뒤에
  롬보드(DDR3 ROM 캐시) 응답을 또 기다렸다. 32비트 `lw`는 16비트 두 번이므로 대기가 두 배가 된다.
- 측정: `lw` 1회 약 1.7 us(memorymux 1.24 us + 롬보드). 30,856워드면 약 53 ms로, MAME의 약 9 ms보다
  3프레임 이상 길었다.

## 가설 검증 순서

1. MAME Lua: 프레임별 플래시 읽기 수, SPU DMA, GP1(05), 디버거 브레이크포인트로 v_wait 반복 횟수
   (= 메인 루프 유휴 시간)를 기록했다. 문제 장면 = 대량 플래시 읽기 프레임으로 확인했고,
   스트림 채우기가 복사 뒤에 실행됨을 PC/뱅크 쓰기 순서로 확인했다.
   주의: MAME RAM 읽기 탭은 이 드라이버에서 동작하지 않는다. v_wait 반복은
   `-debug -debugger none` + `bpset 0x801af92c` (`d@(sp+10)` = 남은 카운터)로 얻었다.
2. GHDL CPU 시스템 시뮬(실제 CPU + memorymux, EXP1 = 0x2F1730FF, 512 `lw` / 512 `lb`):
   기존 `lw` 1.24 us / `lb` 0.77 us, 수정 0.36 us / 0.33 us. 체크섬 동일.
3. ModelSim `tb_ns10` (MAME 부팅~71 s 버스 트레이스 470만 벡터 재생, 모든 읽기 값 비교):
   롬보드 16비트 읽기 평균 8.29 -> 4.31 clk1x, 읽기 값은 수정 전과 완전히 동일.
   (수정 전/후 모두 같은 4,632건 불일치가 있는데, 2.06 s 이후 플래시 명령 모드로 0x40000을 읽는
   부분이다. MAME는 NVRAM의 플래시 사본(날짜 문자열)을, tb 이미지는 ROM 덤프(0x55)를 갖고 있어서
   생기는 테스트 이미지 차이이고 이번 수정과 무관하다.)

## 해결

1. `rtl/psx_top.vhd`: 새 입력 `romBusFast`가 1이면 memorymux에 주는 EXP1 memctrl 값에서
   RDelay / RecP / Float / PStrobe를 0으로 만든다(16비트 폭, autoinc, WDelay, Hold는 유지).
   EXP1 접근은 롬보드 wait 핸드셰이크만 기다린다 = MAME와 같은 "버스 대기 없음".
   `psx_mister.vhd`는 포트를 그대로 전달한다.
2. `rtl/ns10/ns10_romboard.sv`: 마지막으로 캐시에서 읽은 64비트 beat(`lat_beat` / `lat_data`)를
   보관한다. MEM(M) 뱅크 창 읽기가 같은 beat면 캐시 왕복 없이 바로 `S_RAW_DONE`으로 간다
   (순차 halfword 4개 중 3개). 리셋(다운로드 포함)과 모든 EXP1 쓰기(플래시 프로그램/지우기의 시작)에서
   무효화한다.
3. `NAMCOS10.sv`: 디버그 빌드에 OSD `ROM Bus Wait: MAME / PSX` (status[89], 기본 MAME)를 추가했다.
   PSX를 고르면 수정 전 버스 지연으로 돌아가 A/B 비교가 가능하다. 릴리스는 MAME로 고정된다.

## 실기 결과 (디버그 빌드, 로드 후 86.4 s부터 10 s 트레이스)

  (MAME는 2프레임).

- 사용자: 두 구간 모두 육안으로 고쳐졌음을 확인했다.

# 2026-10-22 추가: DDR3 고속 ROM 로딩, CRT Adjust, 로딩 중 검은 화면

브랜치 `fastload-crt` (main de9062d에서 분기). 참고: Tenkomori_Shooting_MiSTer (System 12 코어,
docs/FASTLOAD.md), ZN1-Capcom_MiSTer (crt_adjust.sv). 고속 로딩은 실기 확인 완료(아래), CRT Adjust는
사용자 CRT 확인 대기.

## 1. DDR3 고속 ROM 로딩

### 증상 / 배경

- 게임 선택 후 부팅까지 약 60-90초. ROM(34-52 MB)을 hps_io ioctl로 16비트 워드씩 받기 때문이다.
- Tenkomori 코어(약 50 MB)는 수 초 만에 로딩된다. MRA `<rom address="0x...">` 속성을 쓰면
  Main_MiSTer(`support/arcade/mra_loader.cpp` `rom_finish`)가 ROM을 ioctl로 보내지 않고
  `shmem_put(fpga_mem(address))`로 DDR3에 직접 복사하고, 코어에는 쓰기 없는 빈 다운로드
  (index, 길이)만 보낸다. 주소 범위 제한은 없고, ROM은 HPS 힙에 1 MB 단위로 모은다.

### 우리 코어에 적용하는 방법 (가설)

- 우리 코어는 원래 ROM 이미지를 DDR3 0x35000000에 **파일 내용 그대로** 둔다(롬보드가 실행 중에
  DDR3에서 읽는다). 따라서 Tenkomori처럼 DDR3 -> SDRAM 재전송 회로가 필요 없고, MRA에
  `address="0x35000000"`만 붙이면 Main이 지금과 같은 바이트 배치로 써 준다.
- 그러나 그대로 하면 두 가지가 깨진다.
  1. **설정 NVRAM**: 설정/랭킹 영역은 ROM 이미지 안(MEM(M) 0x40000-0x43FFF, MEM(N) NAND0 블록 1)에
     있다. 지금까지 MRA 순서는 config -> nvram -> ROM이고, ROM 다운로드가 nvram 영역을 건너뛰었다.
     고속 로딩은 ROM 전체를 memcpy하므로 먼저 받은 .nvm을 덮어쓴다. 또 `ns10_nvram`의 BRAM 사본
     (HPS 저장용)은 ROM 캐시 쓰기를 엿보아 채우는데, Main의 직접 복사는 이 경로를 지나지 않는다.
  2. **ROM 캐시**: `ns10_romcache`(2라인)가 DDR3가 뒤에서 바뀐 것을 모른다(reset이 1'b0 고정).

### 해결

- .nvm 다운로드(index 2)는 ROM 영역 위 스테이징(ROM beat 0x7F0000 = DDR3 0x38F80000)에 쓴다.
- ROM 다운로드가 끝나면 `rtl/ns10/ns10_nvload.sv`가 설정 영역을 ROM 캐시를 통해 한 beat씩 복사한다:
  .nvm이 있으면 스테이징 -> 영역, 없으면 영역 -> 영역(ROM 원본 그대로). 쓰기는 DDR3와 ns10_nvram BRAM에
  같이 들어가고, `game=0`이라 저장 요청은 생기지 않는다. 그 다음에 BIOS 부트 복사가 시작된다
  (`cpu_reset`에 need_nvl / nvl_busy 추가).
- ROM 다운로드 종료(`rom_end`) 때 ROM 캐시 라인을 무효화(`inval` 입력 추가).
- MRA 생성기 `tools/mkmra.py`: ROM index 0에 `address="0x35000000"`. MRA 순서는 그대로.
- 구버전 Main(address 무시)이면 ROM이 예전처럼 ioctl로 오고, 같은 nvload 경로로 끝난다.

### 검증 (시뮬레이션)

- `sim/ns10/run_nvload.sh` (tb_nvload.sv, ModelSim): MEM(M)/MEM(N) x .nvm 유/무. ROM 캐시에 옛
  데이터(A)를 올린 뒤 DDR3를 뒤에서 C로 바꾸고(고속 로딩 흉내) 스테이징 B. 결과: DDR3 영역과 BRAM이
  B 또는 C, 저장 요청 0, 영역 밖 쓰기 0, 재구성 1.5-2.9 ms. `+noinval`이면 옛 라인을 읽어 FAIL
  (무효화가 실제로 필요함을 확인).
- `sim/ns10/run.sh` (tb_ns10, 실제 ROM): mrdrilrg 52 MB / mrdrilr2j 40 MB, BIOS 부트 복사 불일치 0,
  MAME 버스 벡터 각 200,000개 불일치 0 (ROM 캐시 변경 회귀 없음).
- 처음 tb_nvload가 10분 넘게 출력 없이 멈췄다: 1클럭 펄스(rd_valid)를 `while(!rd_valid)`로 기다리다
  놓친 테스트벤치 버그. 모든 시뮬레이션에 벽시계 15분 제한(`timeout 900`), 시뮬레이션 시간 제한,
  대기 루프별 정지 감시(STALL 출력)를 넣었다(tb_nvload, tb_crt_sync, tb_ns10).

### 실기 확인 방법

- 디버그 빌드 JTAG 프로브 "LOAD": `python tools/ns10trace.py load` -> index 0 다운로드 시간,
  ioctl 워드 수(0이면 고속 로딩 경로), 설정 재구성 시간, ROM 종료 -> CPU 시작 시간, .nvm 로드 여부.
- 설정 저장: 게임 설정을 바꾸고 OSD를 열어 .nvm 저장 -> 다시 로드해서 유지되는지.

## 2. CRT Adjust (아날로그 15 kHz 출력의 화면 크기/위치)

- OSD 새 페이지 "CRT Adjust (analog)": CRT Adjust Off/On(기본 Off = 원래 신호 그대로),
  H-Size 0..+10/-12..-1(한 칸 약 3%), H-Position -16..+15(한 칸 16 CLK_VIDEO = 640폭 4픽셀,
  320폭 2픽셀), V-Position -16..+15 라인. 값은 CRT Adjust On일 때만 보인다(status_menumask H1).
- H-Size: Tenkomori `rtl/crt_hsize.sv`(라인 버퍼 리샘플, 실기 검증된 모듈) 그대로 사용. 한 라인
  지연이 생기므로 VSync를 한 라인 더 늦춘다. 픽셀 내용이 바뀌므로 HDMI 화면도 같이 늘어난다(OSD에 표기).
- 위치: 새 모듈 `rtl/crt_sync.sv`. Tenkomori `crt_shift.sv`는 VSync를 HSync 경계에 맞춰 다시
  만드는데, 우리 코어의 PSX GPU(`gpu_videoout_async`)는 480i에서 필드마다 VSync가 반 라인 어긋나는
  진짜 인터레이스를 낸다. HSync 경계로 맞추면 두 필드가 겹친다(인터레이스가 깨짐).
  그래서 HSync/VSync를 **시간으로** 지연시킨다(파형 그대로 이동). DE/블랭킹은 그대로라 HDMI는 영향 없음.
- 시뮬레이션에서 찾은 문제: 480i에서 VSync 간격이 필드마다 번갈아 다르다(테스트 모델 892500/899325
  클럭). "N클럭 앞당김"을 직전 간격으로 계산하면 한 필드 걸러 2라인 틀린다. 앞당김은 **두 펄스 전
  간격**(= 다음 간격)으로 계산하도록 고쳤다.
- 검증: `sim/crt/run.sh` (tb_crt_sync.sv): 240p/480i x 7개 설정, 모든 출력 펄스가 입력 펄스로부터
  정확히 offset+1 클럭, 펄스 폭 동일, 0 bad.

## 3. 로딩 중 검은 15 kHz 화면

- GPU는 `cpu_reset` 동안(ROM 다운로드, 설정 재구성, BIOS 부트 복사) 동기 신호를 내지 않아 CRT가
  동기를 잃었다. 그동안 GPU 기본 타이밍과 같은 검은 240p(3413 CLK_VIDEO/라인, 263라인, 320폭)를
  내보낸다(Tenkomori 방식). OSD/진행 화면이 아날로그에서도 보인다.

## 남은 일 (이번에 하지 않음)

- HDMI(vsync_adjust=2)에서 게임 진입 해상도 전환 때 검은 화면이 2-3초 길어진 문제: 측정 계획만 기록
  (20261019 rbf와 A/B, GP1 모드 변경 트레이스 vs MAME).

## 2026-10-22 추가 2: CRT Adjust를 아날로그 출력에만 적용 (HDMI 분리)

### 증상 (사용자 실기 확인)
- CRT Adjust의 H-Size, V-Position이 HDMI 화면에도 적용된다(H-Position은 HDMI에 영향 없음).
- HDMI 출력 중에 V-Position을 연속으로 바꾸면 HDMI 화면이 깨진 그래픽과 함께 멈추고, 리부트해야 돌아온다.

### 원인
- 코어의 VGA_* 하나를 아날로그 출력과 HDMI 스케일러(ascal)가 같이 쓴다. CRT Adjust를 VGA_*에
  넣었으므로 HDMI도 같은 신호를 받았다.
  - H-Size는 픽셀 자체를 다시 샘플링하므로 HDMI 그림도 늘어난다.
  - V-Position은 VSync를 움직인다. ascal은 VSync 상승 에지로 프레임을 끊고(i_vcpt 리셋,
    i_vmin/i_vmax로 세로 범위 측정, 인터레이스 판정), vsync_adjust=2 저지연 모드에서는 출력 프레임과
    HDMI PLL 미세조정이 입력 VSync에 묶여 있다. VSync 위치가 계속 바뀌면 이 측정이 흔들리고, 저지연
    동기 상태가 깨져 화면이 깨지고 멈춘다(리부트로만 복구).
  - H-Position은 HSync만 움직이고 ascal은 가로를 DE로 잡으므로 HDMI에 영향이 없었다.

### 수정
- sys/emu_ports.vh, sys/sys_top.v (MiSTer 프레임워크, `MISTER_CRT_ADJUST` 매크로일 때만):
  코어에 아날로그 전용 출력 CRT_R/G/B/HS/VS를 추가했다. sys_top은 아날로그 경로(scanlines -> OSD ->
  YPbPr/RGB/direct video)에 CRT_*를 넣고, HDMI 스케일러는 기존 VGA_*(원본 그림)를 그대로 받는다.
  CE_PIXEL, VGA_DE는 공통이다. 매크로가 없으면 예전과 같다(crt_* = vga_*).
- NAMCOS10.sv: VGA_*는 감마 보정 결과 그대로(CRT Adjust 없음). CRT Adjust(crt_hsize, crt_sync)는
  감마 뒤에서 CRT_*만 만든다. OSD의 "H-Size also resizes HDMI" 문구는 뺐다.
- NAMCOS10.qsf / NAMCOS10_release.qsf: `MISTER_CRT_ADJUST=1`.
- 결과: CRT Adjust 값을 어떻게 바꿔도 HDMI 입력 신호는 원본 그대로이므로 HDMI 쪽 그림, 동기,
  저지연 잠금이 바뀌지 않는다.

### 세로 크기(V-Size)
15 kHz CRT에서 세로 크기는 라인 수(게임이 정한 240/480i 라인)와 CRT 편향 회로가 정한다. 디지털로
바꾸려면 라인을 복제하거나 빼야 하고(240p에서 줄 간격이 불규칙해져 스캔라인이 고르지 않게 보임),
라인 수를 바꾸면 수직 주파수가 바뀐다. 그래서 넣지 않았다. 세로 크기는 CRT 자체의 V-SIZE(서비스 메뉴나
뒷면 조정)로 맞추는 것이 맞다. GBA_MiSTer에도 세로 크기 조정은 없다(사용자가 본 것은 위치 조정).

## 2026-10-22 추가 3: H-Position 0에서 CRT 떨림 (HSync / VSync 1클럭 어긋남)

### 증상 (사용자 실기, Gamshara, YPbPr CRT)
H-Position = 0인 상태에서 H-Size나 V-Position을 바꾸면 화면이 약 0.7초마다 조금씩 떨린다.
H-Position = 1로 두면 떨림이 없다.

### 원인 (시뮬레이션으로 재현)
- PSX GPU(gpu_videoout_async)는 VSync를 HSync와 같은 클럭에 올린다(480i 한쪽 필드는 반 줄 뒤).
- crt_sync_dly는 지연(오프셋)이 있으면 입력 상승 off + 1 클럭 뒤에 출력하고, 오프셋 0이면 입력을
  그대로 통과시켰다. H-Position 0이면 HSync는 그대로(0클럭), H-Size(VSync 1줄 지연)나 V-Position이
  있으면 VSync는 k줄 + 1클럭 뒤라서, VSync가 HSync보다 1클럭 늦게 시작했다.
- sys_top의 csync(YPbPr의 Y 동기, composite_sync=1)는 HSync 상승 순간 VSync가 이미 1인지로 수직 동기
  첫 줄을 만든다. 1클럭 늦으면 첫 줄 모양이 바뀌고 1클럭짜리 글리치 펄스가 생긴다(시뮬레이션 csync 펄스 폭
  비교에서 확인: 입력에 없는 1:1, 0:1706, 0:3412 등).
- CRT가 이 비정상 수직 동기 첫 줄을 매 프레임 불안정하게 받아 주기적으로 떨린다(0.7초 주기는 CRT 수직
  동기 회로 쪽 현상으로 추정, 미확인).
- H-Position ≠ 0이면 HSync도 off + 1 경로를 타서 둘이 같이 1클럭 밀리므로 정렬이 유지됐다.

### 수정 (rtl/crt_sync.sv)
- crt_sync_dly: 오프셋 0일 때도 1클럭 레지스터(sig_d)로 출력. CRT Adjust가 켜져 있으면 HSync와 VSync는
  항상 같은 off + 1 규칙을 따르므로 상대 정렬이 입력과 같다.
- crt_sync: CRT Adjust Off일 때는 예전처럼 완전한 통과(지연 없음).

### 시뮬레이션 (sim/crt/run.sh)
- tb_crt_sync에 sys_top의 csync 모듈(원본에서 추출)을 입력/출력 양쪽에 붙여, 출력 csync 펄스 폭 종류가
  입력과 같은지와 출력 VSync가 HSync 상승과 같은 클럭(또는 반 줄 뒤)에 시작하는지 검사를 추가했다.
- 수정 전 RTL: H-Position 0 + H-Size 경우 240p / 480i 모두 FAIL(재현). 수정 후: 18개 경우(H-Position 0 +
  V-Position만 / H-Size만 포함) 모두 PASS.

### 실기 (디버그 빌드 SEED 2, 21:26)
- HDMI 분리: 사용자 확인 - CRT Adjust 값을 바꿔도 HDMI 그림 / 동기 영향 없음, 멈춤 없음.
- 떨림 수정 빌드를 Gamshara로 배포, 사용자 확인 후 커밋 요청. 고속 로딩 정상(ROM 331 ms).
- 타이밍: 코어 클럭 setup 최소 +0.862 ns, hold 4개 코너 양수. clk1x -> clk3x(`ram_ena -> SDRAM_A`) +1.247 ns.
  HDMI 스케일러 `ascal` setup -0.623 ns(slow 100C, `o_hpix2.b[0] -> o_h_lum_pix.b[0]`, 배치 차이; ascal RTL
  변경 없음). 릴리스 빌드 전에 SEED로 줄이는 것을 권장.

### 구버전 Main_MiSTer(스트리밍 로딩) 확인
- MRA의 `<rom ... address="0x35000000">`는 Main_MiSTer mra_loader가 해석한다. DDR3 직접 로딩은
  Main 2020-02-16(80dcef4 "arcade: support for DDR3 direct loading")부터 있고, 그 전 Main은 속성을 무시하고
  예전처럼 ioctl로 보낸다. 두 경우 모두 다운로드 시작 / 끝 신호(ioctl_download)는 같아서 코어는 구분 없이
  ROM 끝에서 설정 영역을 다시 만든다. `<nvram>`은 Main 2021-01-03(7b8b6b1)부터라, .nvm을 쓰는 Main은
  모두 고속 로딩이 된다.
- 실기 확인(디버그 빌드 21:26): address 속성을 뺀 테스트 MRA(Mr. Driller G, .nvm 복사)로 스트리밍 경로를
  강제. LOAD 프로브: ioctl 워드 16,773,120+, index 0 전송 25.2초, 설정 재구성 0.5 ms, ROM 끝 -> CPU 시작 425 ms.
  DDR3 해시: 설정 영역 밖 ROM 이미지 = zip, 설정 영역 = .nvm. 테스트 MRA / .nvm은 보드에서 지웠다.
