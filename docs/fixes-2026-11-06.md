# 2026-11-06 Driller AI: 사람 플레이 데이터 파이프라인, 장면 벤치마크, X 트리거 확장

## 증상
- AI가 기다리지 못하고, 바로 옆 산소 캡슐을 놓치고, X 블록에 둘러싸인(특히 마름모) 캡슐을 못 먹는다. 사용자 시청 피드백은 docs/continue/handoff-2026-11-06.md.

## 원인(측정으로 확인한 것 / 가설)
- 확인: 17맵 시뮬에서 놓친 캡슐 252개 중 171개(68 %)가 상하좌우 4면이 X인 마름모형.
- 확인: 검색 예산을 4배로 늘려도 캡슐 수가 거의 그대로 → 후보 생성이 한계(계산량이 아님).
- 확인: 사람 플레이(모드 11, 1000~1580 m)는 캡슐의 약 60 %를 X 연쇄로 먹고 X를 직접 판 것은 판당 0~3번.
- 가설: 연쇄 트리거 후보가 "그 열 위에 X가 있는 블록"으로만 만들어져 마름모/위쪽 캡슐을 풀지 못함. 산소가 가득 찬 구간에서 캡슐 가치가 시간 손해보다 작게 계산됨.
- 확인: 캡슐 욕심(RT_CAPV)을 올리면 캡슐은 늘지만 압사가 늘어난다(0.06 → 0.18~0.41/맵).

## 단계 3: 시뮬레이터 수정 — 파는 중인 칸(상태 9/10)으로 걷기 시작 (psim.c)
- 증상: 사람 입력(공격 키 + 방향)을 시뮬레이터에 그대로 넣으면 몇십 프레임 안에 칸(열) 하나씩 어긋남 (평균 66프레임).
- 원인(데이터로 확인, D:/scratch_drgai/rp/dump/h11.bin 3257~3290 프레임): 파기 타이머가 15인 캐릭터에서, 파고 있는 블록이 상태 9(길게 파기, +0x39 ≤ 10)가 되면 플레이어가 그 칸으로 걷기 시작한다. 시뮬은 블록이 완전히 사라질 때까지 막혀 있다고 가정했다(약 9프레임 늦음). 타이조(타이머 3)는 차이가 거의 없어 놓쳤다. 걷기 판정은 낙하 판정처럼 그 프레임의 블록 갱신 전 상태를 쓴다.
- 해결: ps_step에서 갱신 전 좌우 칸이 상태 9/10이면 걷기 허용 (ps_walk9, 기본 1). 
- 결과: 사람 입력 열린 루프로 시뮬이 실제와 같이 가는 길이 평균 66 → 118 / 102 프레임(새 1000 m 3판 중 2판). 10프레임 안에 어긋나는 시작점 21~15개 → 2개. 17맵 시뮬은 그대로(타이조 45.53/0.06, digt15 44.29/0.06).
- 새 도구: rtai/diag/hopen.c(열린 루프 추종 길이), scen.c REPLAY=1(사람 입력으로 장면 재생).
- 새 사람 데이터: mrdrilirg_2026-11-06-* 3판 (1000 m 클리어, 캡슐 79/80/80, 걷기 832). 7판 벤치마크 기준선(X 연쇄 257장면: 같은 캡슐 65, 다른 캡슐 118, 못 먹음 73; 직선 82장면: 56/16/8).

## 단계 4: 정밀 시뮬 빔 탐색 후보 (agent.c RT_BEAM, 기본 꺼짐)
- 확인(오라클): 사람 입력을 개선된 시뮬에 넣으면 X 연쇄 캡슐을 60/120/240프레임 전부터 82/76/53 % 재현 → 시뮬에는 물리 규칙이 있다. 무작위 입력 롤아웃은 X 연쇄 38장면 중 19장면을 X 안 부수고 푼다 → 해법은 존재, AI의 후보/탐색이 못 찾는 것.
- 변경: `beam_search`: 6프레임 매크로 입력 7종(대기, 좌, 우, 아래 파기, 좌/우/위 파기)을 정밀 시뮬(ps_step)로 폭 W(기본 16) × 깊이 D(40) 빔 탐색. 순위 = 캡슐까지 경로 비용(X는 비쌈) + 캡슐 주변 X 개수 × 40. X를 부수거나 죽는 노드는 버린다. 찾으면 입력열(+파기 꼬리 30프레임)을 replay 후보로 넣고 기존 정확 검증이 점수로 고른다. Plan에 입력 버퍼(rep)를 넣어 후보마다 replay를 가질 수 있게 했다(g_rep 전역 제거).
- 옵션: RT_BEAM=n(캡슐 n개), RT_BEAMW, RT_BEAMD, RT_BEAMALL=1(닫힌 캡슐만이 아니라 범위 안 모든 캡슐). 진단 훅 agent_beam_test + scen.c BEAMTEST=1.
- 결과: 빔 단독 X 연쇄 38장면 중 19 해결(평균 1~2만 시뮬 프레임, 무작위의 1/100). 통합(7판 벤치마크, X 연쇄 257장면): 기준 같은 캡슐 65 / 못 먹음 73 → BEAM=2 BEAMALL=1: 68 / 64, BEAM=3 W=32 CAPV=2000: 75 / 63 (직선도 56 → 62).
  17맵(GAME_DIGT=15): 기준 44.29 / 사망 0.06 → BEAM=3 W=32 BEAMALL=1: 45.76 / 0.0 (클리어 프레임 8549 → 8654). CAPV를 올리면 캡슐은 늘지만 사망 0.18로 되돌아감.
- 비용: PC 한 판단에서 최대 약 220~370 ms(평균 프레임당 0.3 → 2 ms), ARM에서는 약 10배 → MiSTer에는 그대로 못 올림(폭/깊이 축소 또는 비동기 필요). GroovyMAME(PC, 워커 스레드)에서 먼저 검증할 것.
- 마름모(4면 X) 캡슐은 빔도 못 푼다(X 부수기 없이는 불가능해 보임, 사람은 공기가 높을 때 X를 하나 판다).

## 단계 5: 사람이 마름모/X 연쇄 캡슐을 푸는 방식 (15초 전 패턴 분석)
- 7판 567장면 분석(캡슐 먹기 전 900프레임): 입력 없이 기다리는 시간 40 %, 아래 파기 8 %. X연쇄 캡슐 43 %에서 캡슐 주변 X가 산소 손실 없이 3개 이상 한꺼번에 사라짐. 마지막 파기→터짐 중앙값 68프레임(대부분 가만히 대기), 터짐→먹기 중앙값 37프레임. X 직접 부수기는 평균 0.01회/캡슐.
- 장면 보기(diag/xpop_view.py, 파기 전 / 터지기 직전 / 직후 격자): 4개 이상 이어진 X 덩어리는 이미 있어도 안 터지고 있다가, **X 블록이 낙하해 덩어리에 닿는 순간(착지)** 연쇄가 시작되어 약 30프레임 뒤 한꺼번에 사라진다. 사람은 X 아래/옆 지지 블록을 파내 X가 떨어져 덩어리에 붙게 만든 뒤 기다린다.
- blocksim.c는 X(0x0B0D)를 연쇄 타입으로 이미 처리하므로 규칙은 시뮬레이터에 있음. 빔 탐색의 휴리스틱(주변 X 개수 감점)이 이 방향과 반대였다. 다음: "지지 블록 1칸 파기 → 100프레임 대기" 를 후보 간선으로 하는 다단계 탐색(여러 판단에 걸쳐 유지).

## 단계 6: 모든 칸 1칸 파기 + 대기 후보 (agent.c RT_XTALL, 기본 꺼짐)
- 오라클(diag/xtrig.c, blocks-only 시뮬 150프레임): 닫힌 캡슐 161개 중 1칸 파기 + 대기만으로 124개, 2칸 파기까지 하면 154개(96 %)가 열린다(열림 = 캡슐 이웃에 빈 칸).
- 변경: 기존 2a(X 연쇄 트리거) 탐색을 캡슐 주변 모든 일반 블록(행 -10..+6, 모든 열)으로 확장(RT_XTALL=1, 시뮬 프레임 RT_XTF=150). 성공 판정 = 파기 후 시뮬에서 파는 자리에서 캡슐까지 X 없이 도달(dijkstra < 600). 대기 시간 = 캡슐이 열린 첫 프레임 + 10(또는 +40).
- 결과 17맵: 기준 44.29 캡슐/사망 0.06 → XTALL 46.71 / 0.24 → XTALL+BEAM(3, W32, ALL) 47.06 / 0.06, 클리어 프레임 8549 → 8808. 사람 장면 벤치마크(7판)는 변화 없음(XCHAIN 같은 캡슐 63~65): 장면 시작 240프레임 전 상태에서는 파는 자리에 걷는 시간이 길어 후보가 대기 전에 밀리는 것으로 추정(미확인).
