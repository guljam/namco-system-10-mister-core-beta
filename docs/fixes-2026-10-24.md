# 2026-10-24 수정 기록: Mr. Driller 2 / G "Drill (Auto)"를 착지 동기 연사로 변경

## 증상 (사용자 보고)

- Drill (Auto)를 누르고 있으면 일반 블록을 손으로 리듬 있게 연타할 때보다 늦게 판다.
- X 블록(5번 파야 깨지는 블록)은 30연사 그대로 빠르게 잘 파진다.
- 사용자 추정: 연사가 너무 정확한 타이밍에 걸려서 착지한 그 프레임이 아니라 다음 프레임에 파진다.
  깊이 들어갈수록 낙하 속도가 바뀌어서 스테이지마다 손해가 달라진다.

## 원인 (MAME / GroovyMAME 트레이스로 확인)

게임의 드릴 판정 코드 (Driller 2 0x801327C8, Driller G 0x801F6CD4):

1. 플레이어 구조체 +1 바이트(쿨다운)가 0이 아니면 1 감소하고 판정을 건너뛴다.
2. 0이면 패드 **에지**(`cur & (cur ^ prev)`, 새로 누른 프레임만)의 0x200(Drill)을 본다.
3. 이 판정은 서 있을 때(상태 1)만 돌고, 낙하 중(상태 2)에는 돌지 않는다.

즉 **누르고 있는 것은 소용이 없고, 착지한 첫 프레임에 "새로 누름"이 있어야** 바로 판다.
고정 패턴 30연사(켬/끔을 프레임마다 번갈아)는 판 순간부터 착지까지 걸린 프레임 수가 홀수이면
착지 프레임이 항상 "끔" 프레임에 걸려 1프레임을 잃는다. 위상을 바꿔도 짝수일 때 같은 손해가 생긴다.
낙하 길이는 깊이, 캐릭터, 블록 배치에 따라 달라지므로 고정 패턴으로는 해결이 안 된다.

| 패턴 (Driller 2, MAME) | 착지부터 다음 낙하까지 프레임 |
|---|---|
| 10 또는 01 (30/s, 어느 위상이든) | 항상 8 (1프레임 손해) |
| 100 (20/s) | 7 |
| 손으로 이상적으로 누른 경우 = 게임 최소 | 7 |

X 블록은 깨질 때까지 서 있는 상태에서 쿨다운 후 다시 에지를 보므로 30연사가 그대로 먹힌다
(사용자 관찰과 일치).

### 참고: Driller G 테스트 모드 "DRILL CON SPD"

- G에는 누르고 있으면 일정 간격으로 에지를 만들어 주는 기능이 숨어 있다
  (설정 0x803C58B5 → 표 0x802A4A20 = 0,10,20..70 프레임).
- 설정 0x803C58B4가 0이 아닐 때만 동작하고 이 값은 버튼 배치도 바꾼다(Button4/5).
- 표를 1로 바꾸면 결과가 아래 해결책과 같았지만, G 전용이고 게임 설정을 바꿔야 해서 쓰지 않았다.

## 해결: 착지 동기 Drill (Auto)

플레이어마다:

```
fire = Drill(Auto) 누름 && !(게임 패드 cur & 0x200) && !(상태 == 2 || (상태 == 1 && 쿨다운 != 0))
```

- 게임이 이미 "눌림"으로 본 다음 프레임에는 떼고(그래야 다음에 새 에지가 생김),
  낙하 중이나 쿨다운 중에는 떼어 두었다가, 판정이 가능한 첫 프레임에 바로 누른다.
- 서 있는 동안은 켬/끔이 프레임마다 번갈아 30연사가 되고, 착지 프레임에는 항상 새 에지가 생긴다.
- 어떤 구조체가 그 플레이어인가: 대전 모드(Driller 2 모드 0x0A, G 0x0A Survival / 0x12 Race)는
  구조체 n = 플레이어 n. 1P 게임은 구조체 0이고, side 플래그(s16)가 그 플레이어 쪽일 때만 적용.
  게임에 없는 쪽 플레이어는 단순 켬/끔(메뉴 조작용).

### IRQ10 위치 변경 (Driller만)

게임은 프레임당 IRQ10 두 번 중 한 번의 IN1 읽기를 저장한다. 위 공식이 그 프레임의 플레이어 갱신
결과를 반영하려면 읽기가 갱신 뒤에 와야 한다. 대전 모드 P2 갱신은 vblank 뒤 3.3~6.5 ms에 끝나서
기존 1/4 프레임(4.2 ms) 읽기보다 늦을 수 있었다. 그래서 Driller 세트만 IRQ10을 **5/8, 7/8 프레임**으로
옮겼다(gamshara, startrgn은 1/4, 3/4 그대로).

## 구현

### GroovyMAME (먼저, 사용자 체감 확인 완료)

- `D:\github_clones\GroovyMAME` 브랜치 autofirefix, 커밋 2a226d2c064 (`namcos10.cpp` `drill_auto_fire`).
- 사용자 플레이 확인: "제가 예상하던 그 리듬감입니다".

### FPGA

- `rtl/ns10/ns10_autofire.sv` 다시 작성
  - PSX 메인 RAM 버스(SDRAM 채널 쪽: `sdram_req/rnw/dma/cache/addr/be`, 쓰기 데이터, `sdram_readack` +
    `ch1_dout32`)를 엿봐서 위 8개 워드의 그림자 레지스터를 유지한다.
    CPU 쓰기(바이트 마스크 적용)와 CPU 데이터 읽기(`ram_cache=0`, `ram_dma=0`)만 반영하고,
    DMA와 i-cache 라인 읽기는 무시한다.
  - 게임이 이 워드들을 매 프레임 읽거나 쓰므로 세이브스테이트를 불러와도 1프레임 안에 다시 맞춰진다
    (GroovyMAME 프로브로 확인: 패드/모드는 거의 매 프레임, side는 1P 모드에서 매 프레임,
    상태는 해당 구조체가 쓰일 때 매 프레임, 쿨다운은 서 있는 프레임마다 판정 직전에 읽힘).
  - 게임 선택: MRA 설정의 Driller 플래그(af_b2) + 보드 종류(MEM(M) = Driller 2, MEM(N) = Driller G).
  - 떼기 / OSD 열림 / Driller가 아님: 즉시 끔.
- `rtl/ns10/ns10_io.sv`: 입력 `irq10_late` 추가, 1이면 2x VBlank IRQ10을 5/8, 7/8 프레임에.
  `NAMCOS10.sv`에서 `af_b2`(Driller 세트)로 연결.
- 디버그 트레이스: `ns10_gtrace`에 제어 서브타입 6 "Drill (Auto) 상태"를 추가(변경 시와 매 vblank).
  `{pad P2 P1, fire P2 P1, btn P2 P1, versus, side, st1, st0, cd1, cd0}`.
  OSD "Trace GPU 10 s"로 기록 → `python tools/gputrace.py fetch t.bin` →
  `python tools/gputrace.py drill t.bin`(vblank별 상태 변화 시각과 IRQ10 ack 시각).

## 검증

1. `sim/ns10/run_autofire.sh [seed]` (ModelSim, `tb_autofire.sv` 새로 작성):
   `ns10_io`(5/8, 7/8) + `ns10_autofire` + RAM 버스 위의 Driller 게임 모델.
   - 모델: IRQ10 ISR 저장(랜덤 순번), vblank 뒤 패드 복사/쓰기, P1 갱신(1~2 %), P2 갱신(20~39 % 프레임),
     파기 → 3~8프레임 뒤 낙하 3~12프레임, X 블록 5타(타마다 쿨다운 1~3), 착지 시 가끔 쿨다운.
   - 잡음: DMA 쓰기/읽기, i-cache 라인 읽기(감시 워드에 쓰레기 데이터 포함), 다른 CPU 접근.
   - 검사: 판정 가능 첫 프레임(착지, 쿨다운 끝)마다 새 에지가 있는지. Driller 2 1P(P1쪽/P2쪽), 대전,
     Driller G 1P(모드 11), Race, Survival, 게임에 없는 플레이어의 켬/끔, 그림자 리셋(세이브스테이트) 후
     복구, OSD/떼기/게임 0 즉시 끔, IRQ10 위상. 시뮬 시간 제한, vblank 워치독, 15분 wall clock 제한.
   - 결과: 시드 1~8, 16~20 모두 PASS.
   - 처음 실패 3건은 모두 테스트벤치 문제였다: static task의 인자를 잡음 프로세스와 게임 프로세스가
     공유(automatic으로 수정), 잡음 CPU 쓰기가 side 워드에 쓰레기를 씀(실제 게임은 안 함, 제외),
     게임 전환 뒤 구조체 초기화 누락.

   (예전 연사 교대 검사는 `tb_autofire`로 옮김)
